# Hardware-Aware FP4 FlashAttention-4

**Authors:** Robert Hu

**arXiv:** [2609.04105](https://arxiv.org/abs/2609.04105)

**Categories:** cs.LG

**Submitted:** 2026-09-03

**Relevance:** 9/10 — matched: LLM inference efficiency and long-context serving

---

## TL;DR
This paper shows that on NVIDIA Blackwell GPUs, naively using FP4 tensor cores for attention doesn't speed things up because the softmax stage (score→probability conversion) becomes the bottleneck once the matrix multiplies get faster. The authors introduce Direct-P, a method that maps scores directly to FP4-quantized probabilities for noncausal (inference) attention, achieving up to 2.13× BF16 forward throughput, and a causal training path that reuses forward-pass quantization state in the backward pass for up to 1.14× speedup on a full 8B-parameter model update. They also find that using MXFP4 for probabilities/values in training consistently diverges, so their production training recipe keeps FP8 for those operands.

## First-principles breakdown

**The problem setup.** Attention computes `S = QK^T/√d` (similarity scores), `P = softmax(S)` (probabilities), `O = PV` (weighted output). This involves two matrix multiplications (QK and PV) with a softmax step sandwiched between them. NVIDIA's Blackwell GPUs have specialized hardware (tensor cores) that multiply 4-bit floating point (FP4) numbers much faster than 16-bit (BF16) numbers. The naive hope is: if both matrix multiplications use FP4, attention should get much faster. The paper shows this hope is wrong once you actually build the kernel, because the softmax step in between doesn't get any faster from FP4 hardware — it still needs to find the max score, compute exponentials, and produce a properly scaled probability tile — and this step sits directly on the "critical path" (the sequence of dependent operations that determines total latency, since PV can't start until P is ready).

**Why FlashAttention needs tiling and "online softmax".** Naively, computing softmax requires seeing the whole row of scores before you can normalize it. Since sequences can be long, storing the full S/P matrices is memory-expensive. FlashAttention instead processes keys/values in chunks ("tiles"), maintaining a running maximum, running sum, and running output that gets rescaled every time a new tile arrives (Equations 3-5). This lets it never materialize the full quadratic-size matrix.

**Blackwell hardware specifics.** Modern GPUs execute matrix multiplies asynchronously via a dedicated engine (`tcgen05`/MMA) that accumulates results into a small fast on-chip scratchpad called Tensor Memory (TMEM) — think of it as a very limited number of "slots" for in-flight results. A previous work (HAO AI Lab) designed a schedule where one execution unit (CTA) juggles two overlapping query tiles ("stages") to keep the hardware busy while waiting on dependencies. But TMEM only has enough space for two score buffers and two output buffers at head-dim 128 — there's no room for a third stage of look-ahead. This means whenever a score tile is being turned into a probability tile, that "storage slot" is occupied and can't be reused until the value-multiplication (PV) that consumes it is done — a storage-ownership constraint, not just a signaling/synchronization problem.

**FP4 number format tradeoffs.** FP4 numbers here use an "E2M1" payload (2 exponent bits, 1 mantissa bit) which only represents 8 discrete magnitudes (0 to 6), so it needs a shared "block scale" to represent a wider dynamic range: NVFP4 uses fine-grained, more precise scales (E4M3, per small block of 16), while MXFP4 uses a coarser, power-of-two scale shared per block of 32 values. The paper shows that naively quantizing softmax probabilities into FP4 loses a lot of precision (especially with NVFP4 unless "stabilized"), because probability values span a very wide dynamic range and small block scales can round to zero, causing whole blocks of information to vanish ("underflow").

**Direct-P (the main forward-pass contribution).** Instead of the standard approach of computing full-precision softmax first and only then compressing to FP4 at the end (wasting precision that's discarded anyway, while delaying when the FP4 payload is ready), Direct-P recasts probability creation as a "classification" problem: which of the 8 possible FP4 values should each score map to? They fit a simple linear (affine) function of the score that predicts the right FP4 bucket directly, skipping the expensive exponential-then-round pipeline for most cases (falling back to real hardware exponential ops only where needed for accuracy). They also compute the softmax denominator from the same rounded FP4 values that will actually be used, rather than from a separately-computed higher-precision sum — keeping numerator and denominator numerically consistent. Finally, they add a targeted numerical "guard" (Algorithm 3) for a few outlier model layers that produce very large scores that would otherwise underflow/overflow the FP4 representation, without slowing down the common case.

**The causal training path.** During training, backward pass needs gradients, which requires reconstructing probabilities. Instead of creating a fresh, separate precision path for this, the paper saves the FP4-quantized queries/keys, their scale factors, and the softmax normalizer from the forward pass, and reconstructs probabilities from that saved state during backward — avoiding redundant computation. Gradients themselves use FP8 formats (E4M3 for most, E5M2 for the output gradient dO, which needs more dynamic range because it has many near-zero values that FP8's other format would round to zero).

**Why MXFP4 fails in training.** Although MXFP4 probabilities/values are faster in isolated micro-benchmarks, when plugged into actual multi-billion-token training runs (with careful controlled experiments varying projection format while holding backward fixed), every configuration using MXFP4 for P/V eventually diverges (loss blows up, gradient norms explode), while FP8 P/V remains stable. This is an empirical/diagnostic finding, not a full mechanistic proof of why.

## Key insights

- **Genuinely new**: Direct-P's "skip the exponential, classify directly into FP4 buckets" trick for softmax—this is a clever reformulation that shortens a genuine bottleneck (the score-to-probability critical path) rather than just doing the same computation faster. The consistency fix of using the same rounded values for numerator and denominator is also a real, non-obvious source of error reduction.
- **Evidence quality**: Forward speedups (up to 2.13× on GB200) are measured on real hardware with matched kernels and specific shapes, and are reasonably well-supported. The accuracy/speed tradeoff is shown explicitly (Direct-P is faster but noticeably less accurate than HAO's FP8-probability baseline — cosine ~0.94 vs ~0.99).
- **The end-to-end training win is modest and comes mostly from the causal-backward reuse trick, not from full FP4**: only 1.14× on a full 8B update, and it's NVFP4-projections + FP8-P/V — not "full FP4" training. The authors are explicit that this is not pure-FP4 end-to-end training.
- **The MXFP4-divergence finding is a genuinely useful negative result**: it's a controlled, multi-arm factorial experiment (crossing projection format × P/V format) that isolates forward P/V format as the common cause of divergence, which is valuable for others considering this design space, even though the root mechanistic cause isn't identified.
- **Distillation of claim vs. evidence**: The headline "2.13×" and "1.14×" numbers are real but apply to narrow, specific configurations (particular shapes/batch sizes) — they are not general multipliers across all shapes (e.g., B300 was sometimes slower than GB200 at one shape; MXFP4/FP8 end-to-end update speeds were "tied" within noise).

## Caveats — stated and inferred

- **Not pure end-to-end FP4** (stated): "full FP4" refers only to the four attention operands, not the whole transformer; learned projections use E4M3/NVFP4 as a separate precision boundary.
- **Accuracy tradeoff is real and non-trivial** (stated): Direct-P is measurably less accurate than FP8-probability baselines (cosine ~0.94 vs ~0.99, larger relative-L2), and this is disclosed directly rather than hidden.
- **MXFP4 training divergence** (stated): explicitly reported as a negative result across every tested configuration, not cherry-picked away.
- **B300 results are not a clean hardware A/B** (stated): "the best stable records from the final SM103 tuning campaign, not a same-binary hardware A/B," and cross-run comparisons to HAO's published B200/GB300 numbers are explicitly flagged as using "different implementations and harnesses... establish[ing] scale rather than causal timing differences."
- **Single trajectory per training arm, no statistical replication** (stated): "there is one trajectory per route, these data do not support run-to-run variability or statistical-equivalence claims."
- **Short fixed-token update benchmarks conflated with training quality risk** (stated repeatedly): "these short fixed-token updates do not establish training quality," and initial-logit cosine against BF16 for the 8B update matrix is quite low (0.37–0.43), showing large per-step numerical deviation despite acceptable throughput.
- **Downstream task-accuracy evaluation is small-scale** (stated): ViT/BERT/SST-2 evaluations use held-input inference only (no training), and the authors note "the suite is too small to establish universal inference or training safety."
- **Root cause of MXFP4 divergence not isolated** (stated): "This is strong factorial evidence, but not a formal proof that one kernel instruction causes divergence"; separately, "the complete approximate-consumer recipe failed the observed distributed numerical gate; the failure was not isolated to that consumer."
- **Calibration constants are hand-tuned/task-specific** (inferred): the affine classifier constants (A, B) differ between a "generic fast fit" and Wan-specific values, and layer-wise adaptive calibration was tried and rejected because it didn't generalize across prompts — suggesting the method may require per-model/per-workload retuning rather than being plug-and-play.
- **Guard mechanism is manually targeted, not automatic** (inferred): the extreme-logit guard (Algorithm 3) is routed only to specific hand-identified layers (e.g., layers 27-29, 33-34/38-39) discovered via failure analysis, raising questions about how this generalizes to unseen models without similar manual debugging.
- **Baseline comparisons partly rely on the prior work's own published numbers rather than local reproduction** (stated/inferred): e.g., "HAO's stronger published NV/FP8 result is therefore included in the primary table rather than inferred from this local control," meaning some headline comparisons mix locally measured and externally reported figures under different conditions.
- **Wan video-diffusion quality degrades notably at more steps** (stated): at 20 steps, fast route quality drops to 0.85/0.53 (cosine/rel-L2) vs BF16, "accumulates more drift," and a held-out prompt performs even worse (0.82/0.58) — a real quality cost not fully resolved.
- **Distributed training comparison uses relatively small scale** (inferred): 64 GPUs, 100B tokens, one 8B model — modest by modern LLM pretraining standards, so generalization to larger-scale/longer-horizon training runs is not addressed in the paper.
- **Historical/superseded results mixed into appendices with explicit "do not transfer" warnings** (stated): the paper itself repeatedly warns readers not to use various historical timing/quality numbers as claims about the final recipe, indicating the reported system went through many false starts — a sign of an evolving, not fully mature, implementation.
