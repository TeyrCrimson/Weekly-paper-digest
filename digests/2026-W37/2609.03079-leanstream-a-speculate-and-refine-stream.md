# LeanStream: A Speculate-and-Refine Streaming Framework for Efficient on-Device LLM Inference

**Authors:** Renyuan Liu, Yuyang Leng, Kaiyan Liu, Yuzhou Zhong, Shaohan Hu, Chun-Fu, Chen, Peijun Zhao, Heechul Yun, Shuochao Yao

**arXiv:** [2609.03079](https://arxiv.org/abs/2609.03079)

**Categories:** cs.LG

**Submitted:** 2026-09-02

**Relevance:** 9/10 — matched: LLM inference efficiency and long-context serving

## TL;DR
LeanStream is an on-device LLM inference system that resolves the tradeoff between "wait for accurate activation predictions" and "prefetch weights early for I/O overlap" by continuously refining sparse-execution and caching decisions from *partial* GPU results rather than a one-shot prediction. It combines a lightweight thread-block-level GPU/CPU coordination primitive, a cheap "stacked learnable hashing" predictor, and an adaptive MPC-style controller that decides when to re-synchronize. On Mistral/Llama2/Qwen2.5-7B across Jetson Orin, Jetson Xavier, and a OnePlus 13 phone, it cuts memory use 4.8–7.5× and boosts throughput 1.6–2.1× versus prior systems (DejaVu, PowerInfer-2) at their best settings.

## First-principles breakdown

**The underlying problem.** LLMs are too large to fit in mobile/embedded DRAM, so weights are kept on SSD/flash and only the needed pieces loaded per token. Luckily, LLM feed-forward layers (which dominate model size) exhibit *activation sparsity*: for any given input, most neurons produce near-zero output and can be skipped, so you only need to fetch/compute ~20% of the weights (via ReLU/SwiGLU-style sparsity patterns).

**Why prior systems struggle.** To know *which* weight sub-matrices are worth loading, you need a predictor that looks at the activations of the current layer. But the most accurate signal (the finished, fully-computed layer output) only becomes available after the GPU has finished computing that layer — at which point it's too late to have started loading weights early, so I/O and compute are serialized (Fig 1a). To avoid that serialization, prior systems (DejaVu, PowerInfer-2, LLM-in-a-Flash) instead predict *before* the current layer finishes, using older/incomplete information — this lets I/O overlap with compute, but the guesses are worse, causing wasted fetches, extra computation on wrongly-predicted "active" neurons, and (if they add an in-memory cache to soften this) large redundant memory footprints (~3GB in some systems) and >3× excess compute.

**Core mechanism: speculate-and-refine.** Instead of picking one point in time to predict, LeanStream treats prediction as a *stream*: it starts an initial guess as early as possible, then keeps updating it as the current MLP layer computes in stages. Concretely (Section 3.2, Fig 2): the MLP for layer n is split into K priority-ordered chunks. As each chunk's partial output becomes available, it's added into a running "partial residual" that's fed to the predictor for layer n+1, so the neuron/weight priority list for the next layer keeps getting more accurate as more real computation trickles in — computation, I/O fetching, and cache-eviction decisions all get refreshed continuously rather than frozen at one snapshot.

**Enabling technical pieces, each solving a specific new problem this design creates:**

1. *Fine-grained CPU–GPU coordination without expensive syncs.* Doing this "trickle" refinement at high frequency would normally require frequent `cudaDeviceSynchronize`-style barriers, which are far too slow when invoked per small chunk (shown empirically: sync overhead balloons past the actual compute time as split count grows, Fig 3/Table 3). LeanStream instead exploits SoC unified memory: GPU thread-blocks check lightweight atomic flags to see if their needed weights have arrived (non-blocking), and the CPU asynchronously polls flags set by finished GPU thread-blocks to update I/O priorities — communication is asymmetric/many-to-one in either direction, avoiding kernel splitting and global barriers.

2. *Handling out-of-order weight arrival.* Because weights now arrive in priority order (not disk order), naive execution would need complex reindexing. LeanStream exploits that summing over hidden neurons in a SwiGLU MLP is permutation-invariant — so weights can just be appended to a buffer in arrival order and treated as one contiguous dense matmul, no reshuffling needed. It also groups co-activating neurons together on disk (learned via a contrastive/embedding-based clustering method, analogous to word2vec) to preserve larger sequential I/O reads despite the more scattered access pattern.

3. *Deciding how often to re-sync (an actual control problem).* More frequent coordination = better predictions but more overhead; less frequent = less overhead but staler predictions and I/O-GPU stalls. Because cache-miss rates vary a lot across layers and even across prompts for the same layer (Fig 4), a fixed offline schedule doesn't work. LeanStream frames this as a finite-horizon stochastic optimal control problem (explicit/receding-horizon MPC): it profiles, offline, how remaining I/O workload evolves under different synchronization-frequency choices and current queue state, solves a Bellman recursion offline, and bakes the result into a lookup table indexed by (layer, quantized remaining-load state). At runtime it just measures state and looks up the precomputed near-optimal coordination frequency — no expensive online solve.

4. *A predictor cheap enough to run at this frequency.* Standard small MLP predictors used by prior work (used per-layer) already cost more wall-clock time than the sparse GPU computation itself when invoked at higher frequency (Table 1) — they'd become the bottleneck. LeanStream's answer is "stacked learnable hashing": a differentiable multi-layer version of locality-sensitive hashing where each layer computes a binary hash code (via a learned hyperplane projection using XNOR+popcount instead of float matmuls) that indexes into a small learned lookup table of binary feature vectors. Stacking several such layers gives it more capacity like a deep net, but inference is just bitwise ops and table lookups — order-of-magnitude cheaper in latency and memory than even a binarized neural network (Table 6: 88-92µs and ~23MB vs. ~1.2-1.5GB/1.4ms for a full DNN predictor). To make it trainable, the authors use a straight-through estimator for the sign/hash function and a differentiable relaxation (Gumbel-softmax over an explicit enumeration matrix) for the discrete lookup step, so the whole thing trains end-to-end with backprop. It's reused for both next-layer neuron-activation prediction (classification) and cache eviction (regression on predicted reuse distance).

## Key insights

- **Genuinely new framing**: recasting the prediction-vs-overlap tradeoff as a continuous streaming refinement problem rather than a single-point decision (fresh-context vs. stale-context prediction) is the core conceptual contribution, and it's a reasonably clean unification of two previously separate design points (Fig 1a-c vs 1d).
- **Systems contribution likely the most solid evidence**: the thread-block-level non-blocking/asymmetric sync primitive has clear, measured overhead reduction versus device-level sync primitives (Table 3), and this is a fairly mechanical, verifiable claim.
- **Stacked learnable hashing** is a plausible, evidenced win for the specific niche of ultra-low-latency, low-memory on-CPU control signals — the size/latency numbers (Table 6) are dramatic and the idea of treating LSH as a differentiable indexing layer is a nice technical device, though it seems primarily an application of existing techniques (learnable LSH, differentiable relaxations) to a new use case rather than a fundamentally new ML idea.
- **The adaptive MPC-based controller** beating an offline-tuned "best static" configuration (Table 5) supports the paper's claim that runtime variability (cache misses, prompt-dependent sparsity) genuinely requires online adaptation, not just better offline profiling — this is a meaningful, testable finding given the cache-miss variability data shown (Fig 4).
- **Headline numbers (4.8–7.5× memory reduction, 1.6–2.1× throughput)** are the claimed top-line result and are evidenced by the throughput-vs-memory curves in Figure 8 across 3 models × 3 devices, which is a reasonably broad sweep.
- Accuracy is claimed to be preserved (Table 2) — worth noting the differences vs. baselines/dense are within noise-level fluctuations (some metrics for LeanStream are actually lower, e.g., Qwen2.5 TruthfulQA/Qasper at 80% sparsity), so "nearly identical" is a fair but not perfect characterization.

## Caveats — stated and inferred

- **Offline profiling cost is substantial and workload/hardware-specific** (stated): the MPC lookup table requires ~90 hours of offline profiling per device (Jetson AGX Orin), with 16 quantization bins × 20 samples per configuration per layer. This must presumably be redone per device/model combination, which the paper doesn't discuss as a deployment cost beyond mentioning the 90-hour figure.
- **No discussion of generalization of the offline-profiled controller/predictor across prompts, domains, or context lengths beyond the three tested datasets** (inferred) — given the paper's own finding that cache-miss behavior is prompt-dependent (Fig 4b), it's unclear how robust the offline-trained LUT and hashing predictor are to distribution shift at deployment time.
- **Energy cost is worse, not better** (stated): LeanStream consumes slightly more energy per token than PowerInfer-2/DejaVu (3.9J vs 3.5J/3.7J) and reaches higher peak GPU/CPU temperatures, because it keeps both CPU and GPU more continuously busy. The paper frames this as safe (no thermal throttling in a 2-hour test) but doesn't explore longer sustained runs or more thermally constrained devices.
- **Baselines may be somewhat dated relative to the fast-moving field** (inferred): DejaVu (2023) and PowerInfer-2 (2024) are the primary comparisons; "DejaVu+" is the authors' own modified variant (added LRU cache) rather than a published system, meaning one of three baselines is not independently validated by other researchers.
- **Limited hardware diversity for "mobile" claims** (inferred): only a single phone (OnePlus 13/Snapdragon 8 Elite) is tested; broader mobile SoC diversity (e.g., different vendors, older/lower-tier chips with less unified-memory support) is not addressed in the paper.
- **Reliance on unified memory architecture** (inferred): the core low-overhead coordination mechanism explicitly depends on the GPU and CPU sharing unified DRAM ("leverage the unified memory architecture of SoC"). This may not generalize to discrete GPU/host architectures or platforms without coherent unified memory, which the paper doesn't discuss as a limitation.
- **Truncated/opaque middle section**: the provided text has a gap ("middle of paper truncated") covering part of Section 4.3.6 (importance ratio/recall analysis) — some evaluation details in that region were not available for this summary.
- **No ablation isolating the streaming controller's benefit from the stacked-hashing predictor's benefit in the main headline numbers** (inferred) — Section 4.3 has separate ablations for prioritization components (Fig 11), cache policy (Table 4), streaming control (Table 5), and hashing efficiency (Table 6), but no single combined ablation showing how much of the total 1.6–2.1× throughput gain is attributable to each piece individually versus their combination.
- **Accuracy differences are sometimes negative for LeanStream** (inferred from Table 2): e.g., Qwen2.5-7B at 80% sparsity shows LeanStream scoring lower than DejaVu/PowerInfer2/original on Qasper (28.8 vs 29.5–31.1) and TruthfulQA (45.4 vs 46.1–47.9) — the paper characterizes results as "nearly identical" without flagging these specific regressions.
- **JPMorgan Chase disclaimer** (stated): the paper explicitly disclaims that it is not a product of JPMC's research department and makes no warranty about completeness/accuracy — a standard corporate disclaimer, but worth noting given co-authors' affiliation.
