# SGD-KV: Summarization Guided KV Cache Compression

**Authors:** Zeyu Liu, Woomin Song, Xuandi Fu, Sai Muralidhar Jayanthi, Vivek Govindan, Aram Galstyan, Sravan Babu Bodapati, Srikanth Ronanki

**arXiv:** [2609.03235](https://arxiv.org/abs/2609.03235)

**Categories:** cs.CL

**Submitted:** 2026-09-03

**Relevance:** 10/10 — matched: LLM inference efficiency and long-context serving

---

## TL;DR
SGD-KV compresses LLM KV caches by first identifying which attention heads specialize in "summarization" (hierarchical information aggregation across chunks) via a diagnostic task, then allocating more cache budget to those heads. On Qwen2.5-7B-1M and Qwen3-32B across long-context benchmarks (MRCR, ETHIC, BABILong), it claims state-of-the-art accuracy while cutting KV cache memory by up to 75%, outperforming prior head-aware methods like HeadKV and AdaKV at long context lengths (up to 1M tokens).

## First-principles breakdown

**The underlying problem.** Transformer LLMs cache the Key and Value tensors for every previously-seen token (the "KV cache") so they don't have to recompute attention from scratch at each generation step. This cache grows linearly with context length, so at contexts of hundreds of thousands to millions of tokens, the KV cache dominates GPU memory and becomes the practical bottleneck for long-context inference — not compute, but memory bandwidth/capacity.

**Why prior compression methods are limited.** To shrink the cache, you must decide which tokens' KV entries to keep. Early methods (StreamingLLM, H2O) used generic heuristics — keep recent tokens plus an "attention sink" of initial tokens, or keep tokens with high cumulative attention — applied uniformly, ignoring that different attention heads do fundamentally different jobs. Later work (PyramidKV, AdaKV, HeadKV, DuoAttention) got smarter by allocating budget per-head or per-layer, but they still classify head importance using retrieval-style diagnostics (e.g., "needle-in-a-haystack" tasks that find "retrieval heads" — heads good at pinpointing one fact). The paper's critique: retrieval is not the only cognitive job attention heads do. Tasks like multi-document synthesis or long dialogue require *aggregating and synthesizing information across many parts of the context*, not just fetching one needle. Heads good at that job aren't necessarily the same ones that retrieval-based diagnostics flag as important, so allocating cache based only on retrieval scores can starve the heads actually needed for summarization-style tasks.

**The paper's mechanism, step by step:**
1. **Diagnostic task (chunk-summarization).** Construct a long input by concatenating several independent short documents (from summarization datasets like CNN/DailyMail, DialogSum). Prompt the model to (a) count the number of distinct semantic chunks, and (b) produce keywords summarizing each chunk. This forces the model to both segment the document structurally and distill each segment's meaning — a proxy for hierarchical aggregation ability.
2. **Scoring heads.** For each attention head, compute an "importance score" Ih: for every output keyword token, find where that same keyword occurs in the source input, and measure the max attention weight from the keyword's generation position back to its strongest matching source occurrence, within the correct chunk. Average this over all valid samples. Intuitively: a head that pays strong attention from a generated keyword back to the specific place in the text it came from is doing useful aggregation work, and its score reflects that.
3. **Budget allocation.** Normalize scores across heads so they sum to 1. Reserve fixed budgets for "sink" tokens (first few) and a sliding window of recent tokens (since instructions tend to sit at the start/end of prompts). The remaining "middle" budget is distributed across heads proportionally to their normalized summarization score — high-scoring heads get to keep more of the middle-context KV entries. A water-filling-style correction reallocates budget that would otherwise overflow a head's max allocation (score too concentrated) toward other high-scoring heads that still have room, so nothing is wasted on heads that are capped out.
4. **Within-head token selection.** Once a head has its allocated slot count, apply a SnapKV-style method: use attention scores from a final observation window (e.g., last 128 tokens, ideally including the real query) to pick which specific tokens within that head's budget to retain.

This is essentially: (interpretability diagnostic) → (per-head importance score) → (budget allocation formula) → (standard eviction within budget). The novelty is entirely in step 1–2 (how "importance" is defined and measured), not the allocation/eviction machinery, which reuses ideas from HeadKV and SnapKV.

## Key insights

- **Genuinely new contribution:** the idea that "summarization heads" are a distinct functional class from previously known "retrieval heads" / "retrieval-reasoning (R2) heads," and that this class can be operationally identified via a keyword-attribution diagnostic over concatenated multi-document summarization data. Appendix A.3's IoU analysis (cross-dataset overlap of top-ranked heads, and divergence from retrieval/R2 heads in the 20–60th percentile range) is the evidence supporting that these heads are a stable, distinguishable set rather than noise or a repackaging of retrieval heads — this is the paper's most substantive empirical claim.
- **Practical performance claim:** budget allocation guided by this score beats HeadKV and AdaKV (existing head-aware SOTA) on MRCR and ETHIC, especially as context length grows toward 1M tokens, at a fixed 25% cache budget. The gap widens at longer contexts, which is consistent with the claimed mechanism (aggregation matters more as the number of documents/turns increases).
- **Secondary but practically useful finding:** the diagnostic summarization prompt itself works as a good "proxy query" for token selection when the real user query is unavailable at compression time (Table 3, query-unaware/proxy-query ablation) — this could matter for real deployment settings like caching a document once before knowing what will be asked of it.
- **What's NOT well supported:** "state-of-the-art performance... without compromising model accuracy" is oversold by the abstract. Table 1 shows SGD-KV actually underperforms FullKV substantially at most context lengths (e.g., 34.16 vs 43.29 at 1M on Qwen2.5; 40.13 vs 46.42 at 64k on Qwen3) and even underperforms HeadKV/DuoAttention on Qwen3-32B at 32k (62.02 vs 65.72/60.36 — mixed, not uniformly best). It's the best head-aware compression method in most settings, not accuracy-neutral relative to full cache.

## Caveats — stated and inferred

- **Base model required fine-tuning to be usable at all** (stated): the off-the-shelf Qwen2.5-7B-Instruct-1M checkpoint "exhibits poor performance" on MRCR, so the authors fine-tuned it on a custom mix (MRCR, GraphWalks, BABILong-derived, plus regularization data) before evaluating. This means the reported numbers for that model reflect a bespoke fine-tuned variant, not the released checkpoint — limiting reproducibility/generalization claims and creating a confound (is SGD-KV's advantage partly an artifact of what the model was fine-tuned on?).
- **Only two base models tested, both from the Qwen family** (inferred): no cross-architecture validation (e.g., Llama, Mistral, Gemini-family), so generalization of "summarization heads" as a universal phenomenon is unverified.
- **Baselines adapted/handicapped in ways that could favor the proposed method** (stated): DuoAttention is evaluated without its intended fine-tuning step ("we do not finetune LLMs on retrieval datasets") and instead repurposed with R2 scores — a modification not validated by DuoAttention's original authors. HeadKV's identification process was also not rerun post-SFT because it "got worse" with the new configuration, so the original checkpoint's config was kept for baselines — an inconsistent evaluation protocol between methods.
- **AdaKV baseline performs implausibly badly** (inferred): in Table 1, AdaKV scores 10–30% across the board versus 60–95% for other methods on the same task — an outlier so large it suggests either a misconfiguration/unfair setup or a bug, and it undermines confidence in the comparison's fairness without further explanation in the text.
- **Selective/omitted results due to compute constraints** (stated, but flagged honestly): "we omitted some results for DuoAttention... and AdaKV" in the budget-sweep ablation (Appendix A.6), and results at 1M context were dropped for some head-configuration ablations "due to time and computational resource constraints." The authors assert omissions don't change conclusions, but this is asserted, not demonstrated.
- **No error bars / variance reporting** (inferred): all tables report single point-accuracy numbers with no repeated runs, confidence intervals, or seeds — normal for compute-heavy long-context evals but means small deltas (e.g., 0.1–2 points on ETHIC) shouldn't be over-interpreted as robust wins.
- **Diagnostic task construction relies on synthetic concatenation of unrelated documents** (inferred): "summarization ability" is defined by an artificial task (stitching together unrelated short articles) that may not fully represent naturalistic long-document or multi-turn dialogue structure the method is ultimately evaluated on; construct validity of the diagnostic is asserted via the IoU generalization check but not tested via a held-out human-graded summarization quality metric.
- **Ceiling effects acknowledged for ETHIC** (stated): "smaller performance margins between methods on ETHIC... are likely attributable to a performance ceiling imposed by the base models' capabilities," meaning that benchmark provides weaker discriminative signal between methods than MRCR.
- **NeurIPS Workshop paper** (inferred from context: "Efficient Reasoning" workshop) — workshop papers typically undergo lighter review than main-track papers, consistent with some of the above methodological looseness (baseline handling, omitted results, single-family model testing).
- Not addressed in the paper: computational/latency overhead of running the diagnostic task itself (extra forward passes needed to compute per-head scores before deployment), memory/compute cost of the water-filling redistribution at inference time, and behavior on non-English or code-heavy long contexts.
