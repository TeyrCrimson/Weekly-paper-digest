# BeaconKV: Key-Value Cache Compression Guided by Beacon Queries for Efficient Large Reasoning Model Inference

**Authors:** Janghyeon Kim, Minsoo Kim, Kyuhong Shim, Jungwook Choi

**arXiv:** [2609.04971](https://arxiv.org/abs/2609.04971)

**Categories:** cs.LG, cs.CL

**Submitted:** 2026-09-04

**Relevance:** 9/10 — matched: LLM inference efficiency and long-context serving

---

## TL;DR
LRM inference (long chain-of-thought decoding) blows up GPU memory because the KV cache grows linearly with sequence length, and existing compression methods evict tokens based only on recent queries, which the authors show fails to predict "Thought Revisiting Tokens" (TRT) — decoding steps that re-attend to distant early context like the original task plan. BeaconKV fixes this by maintaining a small set of "beacon queries" (geometrically diverse representatives of past queries, selected via an online farthest-point-sampling algorithm) alongside recent queries, using both to score which KV pairs to keep. Across four open-source reasoning models and four benchmarks, BeaconKV claims up to 5.8× memory reduction and 4.3× throughput gains while nearly matching full-cache accuracy, beating prior methods by up to 31.7 accuracy points under tight budgets.

## First-principles breakdown

**The problem.** In a Transformer decoder, every generated token's key and value vectors get cached so future tokens don't need to recompute attention over the whole sequence — this is the "KV cache." Its size grows linearly with the number of tokens generated. Large Reasoning Models (LRMs like DeepSeek-R1, Qwen3) deliberately generate very long chain-of-thought traces (tens of thousands of tokens) before answering, so the KV cache becomes huge — the paper cites 77GB for a 4B model at 32K tokens/batch-16, nearly saturating an 80GB GPU. This limits how many requests you can batch and how long a model can "think."

**Why prior compression fails.** To shrink the cache, existing methods (SnapKV, RPC, R-KV) periodically evict low-importance KV pairs. Importance is estimated by taking the queries from the most recent few decoding steps ("observation queries"), computing attention weights between those queries and all cached keys (via the standard softmax(QKᵀ/√d) formula), and keeping only the top-scoring keys/values. The implicit assumption: what recent tokens attend to now is a good proxy for what future tokens will need. This works for "local" attention patterns (most tokens just look at nearby context) but breaks for tokens that jump back to distant, already-"stale" context.

**The core observation (TRT).** The authors analyze attention patterns in actual reasoning traces and find a subset of decoding steps — "Thought Revisiting Tokens" — whose queries attend strongly to far-away positions (e.g., the original problem statement or an early-formulated solution plan), not to nearby tokens. This happens across many layers/heads, not in one isolated spot, and occurs sporadically and unpredictably, so recent-query windows rarely catch it. When keys for that stale-but-important context get evicted (because nothing recent attended to them), the model loses access to it and reasoning degrades.

**Geometric insight.** Critically, TRT-triggering queries aren't random: measured as pre-RoPE (pre-positional-encoding) embeddings, they cluster into a handful of similarity groups in embedding space — i.e., many different global/TRT queries across a trace point in similar directions. This means you don't need to remember every past query to anticipate future revisits — a small set of "representative" queries per cluster suffices.

**The mechanism (BeaconKV).**
1. *Beacon queries*: Instead of only keeping the last N queries, maintain a compact set of geometrically diverse past queries (beacons) that summarize the clusters of global/TRT query directions seen so far.
2. *Continual Farthest Point Sampling (FPS)*: To pick representative queries without storing full history (expensive, especially under Grouped Query Attention), the algorithm keeps a small bounded buffer per head; once full, it runs FPS (greedily pick the point farthest — least cosine-similar — from already-selected points) to downsample the buffer back to a minimum size, repeating this "fill-and-compress" cycle indefinitely with bounded memory.
3. *Positional alignment trick*: Beacon queries are re-assigned RoPE positions at the *current* decoding step (simulating "if a TRT happened right now, would it attend to this key?"), while recent queries keep their original positions (preserving normal local-attention signal).
4. *Scoring*: Attention weights are computed between the combined observation set (beacons + recent) and all cached keys. Because TRT signals are rare-but-strong (sparse, high-magnitude), the paper uses max-pooling across observation queries/heads rather than averaging — averaging would dilute a single beacon's strong signal against a background of many local queries.
5. *Eviction*: keep prefix tokens, the most recent tokens, and the top-K scoring KV pairs; evict the rest, periodically as the cache fills.

This is training-free — no fine-tuning or extra learned modules, just a smarter, geometry-aware selection of which queries to use for importance scoring at eviction time.

## Key insights

- **Genuinely new**: the identification and characterization of Thought Revisiting Tokens as a systematic failure mode of recency-based KV eviction in long CoT reasoning, plus the empirical finding that these tokens' queries cluster geometrically (pre-RoPE), which is what makes compact "beacon" summarization possible at all. This diagnosis (Figures 1–4, attention-distance and cosine-similarity/PCA analysis) is the paper's most original contribution, distinct from the engineering method itself.
- **Method contribution**: Continual FPS is a practical, bounded-memory way to approximate offline/naive FPS or K-means clustering online; the paper's own ablation (Figure 7) shows it nearly matches these more expensive offline alternatives while using far less memory — this is a solid, evidence-backed claim, not just asserted.
- **Evidence supports**: accuracy gains under constrained budgets (Figure 8, Table 1–3) and efficiency numbers (Table 4, 5.8× memory reduction, throughput gains) are shown with fairly direct measurements (peak memory, tokens/s, latency) against multiple baselines (RPC, SnapKV, R-KV) and are reasonably convincing as claimed.
- **Ablations are informative and support the design choices**: the recent/beacon query split (16/16 is best trade-off, Table 1), max vs. mean aggregation (max wins, Table 2), and the "Initial+Recent" baseline comparison (Table 3) showing that simply keeping the first tokens isn't sufficient — the dynamic, evolving beacon selection matters, not just "keep some old context."
- **Distinguish claim vs. evidence**: "generally outperforms" (their own wording) is honest — Figure 8 shows BeaconKV winning most but not all budget/benchmark/model combinations; the headline "31.7 percentage points" and "5.8×"/"4.3×" figures are single best-case numbers from specific configurations (Qwen3-14B/AIME24/1024 budget; Qwen3-4B efficiency table), not universal averages.

## Caveats — stated and inferred

- **Stated**: Evaluation is limited to reasoning-focused tasks (math, code, GPQA) on open-source LRMs; the authors explicitly say generalization to non-reasoning workloads (long-context retrieval, summarization, general long-context generation) "remains insufficiently explored" (Appendix C).
- **Stated**: BeaconKV introduces multiple hyperparameters (number of beacon queries, recent queries, KV budget) that were fixed across experiments rather than tuned per model/task; the authors note "the optimal settings may vary across models and tasks" and leave systematic sensitivity analysis and adaptive/dynamic hyperparameter adjustment to future work.
- **Stated (Impact Statement)**: only open-source models and benchmark settings were tested, so transfer to other generation workloads/production settings needs further assessment; also flags a dual-use concern (cheaper long-horizon reasoning could lower cost of misuse).
- **Inferred**: The added Continual FPS computation introduces real overhead — Table 4/5 show BeaconKV's decoding latency is slightly higher than RPC/SnapKV at matched batch sizes (e.g., 8926.9s vs 8672.5s for RPC at 2K budget; 7790.9s vs 7593.7s at 1K), and Table 1 shows beacon-heavy configurations can massively increase latency (10871.3s at n_beacon=31 vs ~4200s for balanced/baseline settings) — the "4.3× throughput" headline is a comparison to uncompressed Full KV, not to the other compression baselines, which show much smaller or even negative relative efficiency gains.
- **Inferred**: All accuracy comparisons are against other training-free KV-eviction baselines (RPC, SnapKV, R-KV); the paper does not compare against the "trainable module" class of methods (TRIM-KV, LightThinker, Fast KVzip) or sparse-attention methods (Quest, Multipole Attention, SeerAttention-R) that it discusses in Related Work, so it's unclear how BeaconKV stacks up against those alternative paradigms.
- **Inferred**: Results rely on a specific local-attention-distance threshold (200 tokens) to classify "global" vs "local" queries (Appendix B) and on hand-picked layer/head examples (layer 18 head 16, layer 6 head 18, etc.) for the illustrative figures — these are demonstrative single-sample visualizations (e.g., "AIME24 sample-0"), not statistics aggregated over the full benchmark, so the qualitative TRT story, while plausible, rests on a small number of showcased examples in the main text.
- **Inferred**: Hardware evaluation is limited to a single GPU type (A100 80GB) and one mid-size model (Qwen3-4B) for the efficiency/throughput numbers; no results are given for how memory/throughput gains scale with larger models (e.g., Qwen3-14B) or multi-GPU/other accelerator setups.
- **Inferred**: No error bars or variance are reported for the accuracy curves in Figure 8 despite averaging over multiple runs (8 for AIME24, 4 for others), making it hard to judge whether some of the smaller accuracy gaps between BeaconKV and baselines are statistically meaningful.
