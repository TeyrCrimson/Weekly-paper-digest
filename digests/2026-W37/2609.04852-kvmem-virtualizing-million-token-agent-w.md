# KVMem: Virtualizing Million-Token Agent Workspaces on a Consumer GPU

**Authors:** Di Chai, Leye Wang, Zeshen Su, Zhiguo Xia, Zhihang Yu

**arXiv:** [2609.04852](https://arxiv.org/abs/2609.04852)

**Categories:** cs.LG

**Submitted:** 2026-09-04

**Relevance:** 9/10 — matched: LLM inference efficiency and long-context serving

---

## TL;DR
KVMem lets a long-running LLM agent keep a "virtual workspace" of up to millions of tokens by storing overflowed context as reusable KV cache (not text) across GPU, host RAM, and NVMe, and re-selecting a bounded, query-relevant subset of that KV state at each agent step instead of summarizing or re-prefilling text. Across three long-context agent benchmarks and a real SWE-agent trajectory (DeepSWE), it beats compaction-based memory management on both task success and speed, and runs a 1M-token workspace on a 24GB consumer laptop GPU. The core trick is treating already-computed attention state as a pageable resource, analogous to virtual memory, rather than discarding it once it falls out of the active context window.

## First-principles breakdown

**The problem.** An LLM agent (think: a coding assistant working in a repo over many hours) keeps accumulating "workspace" content — file reads, tool outputs, logs, edits. Two hard limits get hit: (1) even if the model's context window is big enough, the KV cache (the per-token attention key/value tensors the model needs to keep in GPU memory to avoid recomputing) can be too large to fit in GPU memory alongside weights and other buffers; (2) eventually the raw history itself exceeds even the model's native context window (e.g., 256K tokens but the task history is 1M+ tokens).

**Why prior approaches fail.** The standard fix is *compaction*: periodically ask the model to summarize old history into a shorter text blob, optionally paired with *retrieval* (storing full old text externally and pulling snippets back in when needed). Two failure modes:
- Compaction is lossy and has to guess up front what will matter later. The paper gives a clean argument: if two different histories compress to the same summary, and a future question's answer depends on the part that differs, the summary can never answer it correctly — information is provably discarded before you know if it's needed.
- Retrieval fixes the "what if we need the detail later" problem by keeping raw text around, but retrieved text has to be **re-prefilled** — i.e., the model has to redo the expensive forward pass over tokens it already processed once earlier in the session, wasting compute that was already spent.

**The key idea.** By the time text falls out of the active context, the model has already computed its KV state (the attention keys/values used at every layer/head). That KV state is exactly what would need to be recomputed on retrieval. So instead of throwing it away and keeping only text, keep the KV state itself, parked in a hierarchy of GPU memory → host RAM → NVMe disk, like OS virtual memory paging. When old context becomes relevant again, load the KV tensors back instead of recomputing them from text.

**Three engineering problems this creates, and KVMem's answers:**

1. *When to recall* ("step-level memory scheduling"): re-deciding which historical chunks matter is itself expensive if done too often. The authors empirically measure attention drift (KL divergence between attention distributions in consecutive windows) across real agent rollouts and find attention stays nearly constant *within* an agent step but jumps sharply *across* step boundaries (37x higher divergence). So KVMem only recomputes which historical KV "blocks" to bring in once per agent step (after prefill, before decoding), not continuously.

2. *What to recall* ("query-conditioned KV retrieval"): scanning millions of tokens' worth of KV tensors per step is too slow. KVMem breaks history into small blocks (32 tokens each) and, for each block, computes a "Mean-K" — the average of that block's key vectors (with position information removed, since RoPE position encoding is tied to absolute position and blocks get moved around later) per attention layer/head. This gives one compact vector per block instead of a vector per token — a huge compression of the retrieval index. At query time, the current query vectors are compared against these Mean-K summaries with a scaled-dot-product + softmax scoring, similar to attention itself but at block granularity, to rank which historical blocks are relevant. They show attention is very concentrated (top-8 of ~103 blocks capture ~66% of attention mass), justifying that a small selected set suffices.

3. *How to recall* ("tiered KV management"): once you know which blocks to bring back, you must physically move data from NVMe/RAM to GPU and slot it into new positions in the active context without expensive copies or numerical corruption. Key mechanics: RoPE positional encoding baked into keys is only valid for a specific position, so blocks moving to new positions need "re-RoPE" (strip old position info, keep a position-independent raw K as ground truth, re-apply RoPE at the new position); GPU pages are reused via a page table (like OS memory paging) instead of copying; blocks likely to leave the active view are proactively staged out to RAM/disk *before* they're evicted (overlapped with ongoing computation) so eviction isn't on the critical path; frequently-reused blocks are kept in RAM rather than falling back to slow NVMe (better than plain LRU); and transfers are batched/pipelined (gather → transfer → scatter+re-RoPE run concurrently on different hardware resources) rather than done as many small, latency-bound operations.

They built all this into a custom inference engine ("QW3", C++/CUDA for Qwen models) because existing serving engines (vLLM, SGLang, LMCache) don't expose the combination of low-level control over KV placement, RoPE, and page tables needed to support a constantly-changing sparse execution view.

## Key insights

- **Genuinely new framing**: casting "context overflow" as a virtual-memory problem — decoupling the addressable workspace (huge) from the resident execution view (small, bounded by GPU/context limits) — rather than a text-compression problem. This is the paper's central conceptual contribution, and it's a reasonable, well-motivated reframing rather than just an incremental optimization.
- **Empirical grounding for the scheduling design** (attention drift analysis, KL divergence at step boundaries vs. within steps) is a nice piece of evidence that the "once per step" recall granularity isn't arbitrary — it's grounded in measured model behavior, at least on 8 SWE-bench Lite rollouts.
- **Mean-K block index** is a lightweight, model-native (not a separate embedding model) way to make retrieval scale to million-token histories; the claimed benefit (small index footprint, ~9.5GB for 10M tokens vs. full KV) is plausible engineering, and demonstrated concretely in Table 4.
- **Evidence supports**: on the benchmarks tested, KVMem generally matches or beats compaction and compaction+RAG on task utility while being much faster to recover context (claimed 11.4–53.8x lower recovery latency), and it demonstrably runs a 1M-token workspace at ~50 tok/s on a 24GB consumer GPU — a concrete, verifiable systems capability.
- **Real, not just simulated, agent gains**: the DeepSWE experiment (actual Claude Code agent harness solving repo-level coding tasks) shows a real end-to-end improvement (43.8%→48.4% Pass@1, 81.3%→93.8% Pass@4) plus efficiency wins (55% less prefill time), which is stronger evidence than the controlled/replayed benchmarks alone since it captures compounding effects on live agent trajectories.
- **What's claimed but less rigorously supported**: "generally achieves higher task utility" is a hedge — the results are not uniformly better than Compact+RAG (e.g., roughly comparable at 512K on AgentLongBench), and the fidelity claim ("reused KV state preserves strong utility") is asserted from aggregate benchmark scores, not a controlled fidelity-vs-fresh-prefill comparison.

## Caveats — stated and inferred

- **Not equivalent to recomputation, by the authors' own admission** (stated): reusing historical KV via re-RoPE is "not mathematically equivalent" to recomputing text under the newly assembled context; they only show aggregate task-level utility is preserved, not that individual attention patterns are faithfully reproduced.
- **Retrieval can still miss relevant blocks** (stated): the paper explicitly notes task-relevant blocks may be missed by the retrieval mechanism, and suggests a larger execution view is needed as mitigation — i.e., the system doesn't guarantee recall correctness.
- **Storage/backing capacity is finite and papered over** (stated): when the backing KV store itself fills up (Bm reached), the system falls back to conventional text compaction — the "virtualization all the way" story has a compaction escape hatch that undercuts the headline claim in the worst case; described as "future work" to handle better.
- **Deployment scope is narrow** (stated): requires a custom inference engine with low-level control over KV allocation/positional encoding/tiering; cannot be layered over black-box LLM APIs (i.e., not usable with closed API models like GPT-4/Claude API directly), and multi-user/concurrent serving is unaddressed.
- **Single-session, single-user evaluation only** (inferred): all benchmarks and the DeepSWE trial appear to be single agent session at a time; no evaluation of contention when multiple agent workspaces compete for shared GPU/storage, despite this being flagged as important for real deployment.
- **DeepSWE comparison to public trajectories is not controlled** (stated): the comparison to Gemini/DeepSeek/Claude Sonnet/Kimi public DeepSWE numbers uses a different harness (mini-swe-agent vs. Claude Code), so it "does not constitute a strictly controlled model comparison" — the authors flag this themselves, meaning the favorable Pass@4 comparison should be discounted.
- **Small sample size for the headline agent-trajectory result** (inferred): only 16 tasks × 4 seeds = 64 rollouts per configuration for the DeepSWE evaluation; a 4.7-point Pass@1 gain (28 vs. 31 successes out of 64) is a small absolute difference in raw counts, and no statistical significance testing or variance/confidence intervals are reported.
- **Benchmark task selection caveat is only partially addressed** (stated as a positive, but worth flagging): they say tasks were chosen "without filtering... according to difficulty, trajectory length, or expected behavior," which guards against cherry-picking, but this is a self-report with no independent verification.
- **Hyperparameters (execution-view budgets) are tuned per benchmark** (inferred): the active-context budget varies by benchmark/scale (32K/64K/100K/128K tokens) — reasonable for fair comparison across scales, but no ablation is shown on sensitivity of KVMem's performance to this budget choice, so it's unclear how much of the gain depends on generous or well-tuned budget selection.
- **No ablation isolating the three mechanisms' individual contributions** (inferred): step-level scheduling, Mean-K retrieval, and tiered KV management are all bundled into every experiment; there's no ablation showing how much each piece (e.g., block size, sink/recent retention, host-memory reuse policy) contributes versus a simpler baseline within KVMem itself.
- **Hardware/model-specific results** (inferred): all experiments use Qwen3.6/3.8-27B on custom-quantized (Q8/NVFP4) weights with a custom engine (QW3); generalization to other model families/architectures (e.g., non-RoPE models, different attention variants like MLA) is not addressed in the paper.
- **"Lost in the middle" explanation for KVMem beating Full Context is speculative** (stated as "one possible explanation"): the authors themselves flag this as a hypothesis, not a proven mechanism, when KVMem outperforms Full Context on AgentLongBench.
