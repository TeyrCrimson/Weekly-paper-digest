# Event-Based Person Detection for Maritime UAV Search

**Authors:** Zijie Ning, Patrick Vandewalle

**arXiv:** [2611.23088](https://arxiv.org/abs/2611.23088)

**Categories:** cs.CV

**Submitted:** 2026-11-17

**Relevance:** 9/10 — matched: Onboard object detection from a moving UAV

---

## TL;DR
The authors test whether event cameras (which detect per-pixel brightness changes instead of capturing full frames) can better detect small, hard-to-see people in blurry maritime UAV search footage compared to conventional frame-based detectors. Using simulated events generated from the public MOBDrone rescue dataset, they show the event-based RVT-T model substantially outperforms YOLOv8n and RT-DETR-R18 under realistic exposure blur (15.63% vs 6.89%/9.44% AP50:95 at 100ms exposure), with the advantage growing as exposure time increases. They also show RVT-T runs in real time (~136ms, 2.02J/sample) on a Jetson Orin Nano, suggesting onboard deployability.

## First-principles breakdown

**The problem.** Maritime search-and-rescue UAVs need to spot people in open water — tiny, low-contrast targets against a featureless background. Two things hurt detection: (1) low light forces longer camera exposure times to gather enough light, and (2) UAV motion during that exposure smears the target across pixels (motion blur), especially damaging for already-small targets. Faster flight (to cover more search area) makes this worse because it increases motion during any given exposure window. So there's a tension: you want fast search + reliable low-light detection, but conventional (frame) cameras degrade under exactly those conditions.

**Why event cameras might help.** A standard camera integrates light over an exposure window and outputs one static image. An event camera instead has each pixel independently report a discrete event `(x, y, τ, p)` whenever its local brightness changes by more than a threshold — τ is the timestamp, p is the polarity (brighter=ON or darker=OFF). Because each pixel reports changes immediately rather than accumulating light over tens/hundreds of milliseconds, there's no "smearing" — temporal resolution is very high and dynamic range is wide. In principle this sidesteps the exposure-blur tradeoff entirely: you get fine-grained motion information without needing a long light-gathering window.

**Why this hasn't been tested for maritime search before.** Event cameras are a different sensor; there's no large annotated maritime dataset shot with real event cameras pairing exposure-matched frames with events, and existing event-detection research (e.g., automotive datasets like Gen1, 1Mpx, detectors like RED, RVT, SAST, LEOD) has focused on road scenes, not small targets over featureless water.

**What this paper actually does, step by step:**
1. **Data**: Take the MOBDrone dataset (66 aerial rescue videos with person/boat/etc. annotations). Instead of needing a real event camera, use the **v2e simulator**, which takes ordinary video and synthesizes plausible events by modeling what a real event sensor's pixel response and noise would produce (contrast threshold 0.2, noise mostly disabled for cleanliness). This "video-to-event" trick lets them reuse existing annotated footage.
2. **Paired conditions**: From the same source video/timestamps, they build (a) original frames, (b) brightness-reduced frames, (c) synthetic "exposure-integrated" frames that mathematically simulate what a longer exposure (50/100/200ms) would look like by averaging radiance over that window (Eq. 1), and (d) simulated event histories (four 50ms windows, each split into 10 fine 5ms bins, 2 polarities = 20 channels per window, 4 windows = full 200ms history). All are resized/padded to a common 640×640 canvas, preserving the correspondence to the original annotation boxes.
3. **Models compared**: 
   - **RVT-T** (Recurrent Vision Transformer, Tiny) — processes the sequence of 4 event-representation frames, carrying a memory state forward across them (like an RNN combined with spatial attention) so it integrates information over the full 200ms history before producing one detection at the end.
   - **YOLOv8n** — a standard lightweight single-frame object detector, trained separately on each exposure condition's frames.
   - **RT-DETR-R18** — a transformer-based single-frame detector, also trained per exposure condition.
   Each is trained from scratch on train/val/test splits where entire source videos (not just frames) are held out for test, to prevent leakage between near-duplicate frames of the same recording.
4. **Evaluation**: Standard COCO-style AP metrics (AP50, AP50:95, APS for small objects), plus precision/recall at a fixed operating point, computed on 843 held-out test samples spanning 5 videos.
5. **Embedded deployment test**: They port the trained models to a Jetson Orin Nano (an embedded GPU board suitable for UAV payloads) and measure FP16 latency, power draw, and energy per sample to see if the event pipeline (which is heavier — processes 4 time-steps, not 1 image) can still run in real time.

**Key result mechanics**: the event-based detector's input encodes temporal change directly, so when a frame-based detector's single image gets blurred by motion over a longer exposure, it loses the sharp edge information needed to localize a tiny person; the event stream, by contrast, keeps registering edge-crossing events throughout the window regardless of exposure length (since events aren't tied to "exposure" — they're generated continuously). This explains why increasing simulated exposure duration hurts frame detectors progressively but leaves the (exposure-independent) event detector's accuracy unchanged, widening the AP50:95 gap from 1.33pp (50ms) to 10.82pp (200ms) relative to RT-DETR-R18.

## Key insights

- **Core claimed contribution**: a reproducible, synthetic (v2e-simulated) event-vs-frame evaluation protocol built on public MOBDrone footage, enabling event-based maritime detection research without needing a real event camera or new data collection. This is a genuinely useful methodological contribution since no annotated real-event maritime dataset exists.
- **Evidence-supported finding**: under matched, simulated exposure blur, the event-based RVT-T detector clearly outperforms two modern frame-based baselines (YOLOv8n, RT-DETR-R18) on person AP50:95, AP50, recall, and small-object AP, and the gap widens monotonically as simulated exposure lengthens (50→200ms). This is a real, reasonably well-controlled comparison (same splits, same canvas size, same scoring protocol).
- **Important nuance supported by the data, not just the headline number**: on the *original* (non-blurred) frames, RVT-T and RT-DETR-R18 are statistically tied (15.63% vs 15.64%), and under *reduced brightness* (not blur), RT-DETR-R18 actually beats RVT-T (15.29% vs 13.65%). So the event-camera advantage is specifically tied to *motion blur*, not low light or sensing in general — a more precise and more defensible claim than "event cameras are better for maritime detection."
- **Practical feasibility claim**: RVT-T retains full accuracy under FP16 quantization and runs at ~136ms/2.02J per sample on a Jetson Orin Nano — a real embedded device, which the authors argue supports real-time onboard use. This is a legitimate, measured (not simulated) deployment result, though "real-time" at ~7 samples/sec is modest and the comparison frame models are 2–6x faster/cheaper.
- **A caveat the paper itself surfaces as a finding, not just a limitation**: RVT-T's recall gain comes with lower precision than YOLOv8n (48.67% vs 51.10%) and water-surface motion (waves, reflections) generates competing false-positive events — i.e., the event advantage isn't unambiguous win, it trades off against more false alarms for a human operator to review.

## Caveats — stated and inferred

- **Entirely synthetic event data, no real event camera used** (stated) — all "events" are generated by the v2e simulator from ordinary video, not captured by physical event sensors; simulator fidelity to real event-camera noise/response characteristics is unverified in this maritime context.
- **Synthetic/simulated exposure blur rather than real motion-blurred captures** (stated) — the 50/100/200ms "exposure" frames are mathematically integrated from video radiance (Eq. 1), not actually captured by a camera at that exposure; real optical/sensor exposure effects (saturation, rolling shutter, real noise) are not modeled.
- **Small, narrow test set**: 843 samples drawn from only 5 held-out source videos, with all three models getting near-zero AP on one of those videos (stated) — results are sensitive to very few recordings; generalization across sea states, lighting, and camera motions is explicitly flagged by the authors as future work, not yet tested.
- **Absolute detection performance is low across the board** (inferred) — even the best AP50:95 is 15.63%, meaning the "winning" model still misses/mislocalizes the majority of people; the comparison is about relative gaps, not about a solution that's actually reliable for real rescue operations.
- **Single training seed, no augmentation, limited hyperparameter exploration** (stated: "a single training seed," "augmentation disabled") — raises risk that reported gaps partly reflect training variance rather than a robust architectural advantage; no ablation on seed variability or augmentation impact is reported.
- **RVT-T has a large inherent advantage in input information**: it processes a full 200ms temporal history (4 timesteps × 20 channels) while frame baselines get a single static image — this is a confound the authors acknowledge indirectly (RT-DETR-R18 ties RVT-T on original/brightness conditions) but don't fully ablate (inferred) — e.g., no baseline frame model given multiple frames/a temporal stack to control for the "more temporal information" advantage, only single-frame YOLOv8n/RT-DETR-R18.
- **Precision/recall tradeoff and false positives from water motion** (stated) — RVT-T's higher recall comes with lower precision than YOLOv8n, and wave/reflection-induced events are an explicit source of false detections; the practical cost to rescue operators (more false alarms to review) is acknowledged but not quantified beyond one aggregate precision number.
- **Energy/latency cost is substantially higher for the winning model** (stated) — RVT-T needs ~6x the latency and ~9x the energy of YOLOv8n per sample; whether 136ms per sample (~7 Hz) is actually sufficient for real-time wide-area search at UAV flight speeds is asserted ("allowing real-time processing") but not rigorously justified against a required frame rate or flight-speed/coverage analysis.
- **No comparison against any other event-based detector architectures** (inferred) — despite citing RED, SAST, LEOD as alternative event detectors, only RVT-T is evaluated; it's unclear whether results are specific to RVT-T or would hold across event-based architectures.
- **Checkpoint-selection criteria differ across models** (stated: AP50:95 for RVT-T/RT-DETR-R18 vs. YOLOv8n's "combined AP50 and AP50:95 fitness" via its built-in validator) — inconsistent model-selection procedures across baselines could introduce an uncontrolled advantage/disadvantage (inferred).
