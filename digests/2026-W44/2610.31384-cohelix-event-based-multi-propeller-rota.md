# CoHelix: Event-Based Multi-Propeller Rotation-Rate Tracking with Shared Projective Geometry

**Authors:** Radim Spetlik, Tobiáš Vinklárek, Jan Klivan, Tomáš Kestřánek, Matouš Vrba, Jiří Matas

**arXiv:** [2610.31384](https://arxiv.org/abs/2610.31384)

**Categories:** cs.RO

**Submitted:** 2026-10-22

**Relevance:** 8/10 — matched: Onboard object detection from a moving UAV

---

## TL;DR
CoHelix is a recursive (Kalman) filter that tracks the rotation rates of four coplanar propellers from a moving event camera by estimating a single shared homography (image geometry) alongside four independent per-propeller rotation states, with each accepted event's geometry measurement improving the shared map used to interpret all future events across all propellers. On a moving-camera benchmark it achieves 62.9% "lock" (time spent within 2% of ground-truth rate) versus 39.8% for HelixTrack and 22.2% for EventPro, and on a private target-follower dataset it reaches 95.9% versus 56.2% and 61.1% respectively. The core ablation shows that letting all four propellers jointly constrain the shared geometry (instead of one) is the single biggest driver of this gain, lifting lock from 3.4% to 62.9%.

## First-principles breakdown

**The problem.** A multicopter has four propellers, each with two blades spinning fast. A camera (here, an event camera, which outputs asynchronous per-pixel brightness-change events rather than frames) watches the drone while itself moving relative to it. To estimate each propeller's shaft rotation rate (RPM) from the stream of events, a tracker has to solve two coupled problems simultaneously: (1) figure out *where* each propeller is in the image at every instant — which keeps changing because the camera is moving relative to the rigid airframe (a projective/perspective effect) — and (2) figure out, within that region, how fast the blades are spinning (a temporal/phase effect). Get the geometry wrong and you misassign events to the wrong propeller or the wrong angular position, corrupting the rate estimate; get the rate wrong and you can't validate the geometry.

**Why it's hard — three specific nuisances:**
1. *Background clutter*: as the camera moves, static scene texture swept across the propeller's circular swept area ("annulus") also triggers events, mixing with genuine blade events.
2. *Near-identical propellers*: with four similar-looking propellers, it's ambiguous which events belong to which propeller unless geometry is tracked accurately.
3. *Half/double-rate ambiguity*: a 2-blade propeller looks identical after a half-turn (180°), so a tracker locked onto twice the true rate (or half) fits the event timing just as well as the correct rate — a classic frequency-doubling/aliasing trap that a naive error metric (mean absolute error) won't expose, since brief lock-losses get averaged away.

**Why prior approaches fail.** 
- *EventPro*: clusters events to find each propeller's center and estimates rate from an "adaptive" batch of recent events — but assumes a static camera and keeps no persistent state for how perspective changes over time.
- *HelixTrack*: updates a per-event phase filter (good — reacts fast), but each propeller has its *own* separate homography (projective map), refined only periodically via batched Gauss-Newton optimization over accumulated events, not after each new event. So four propellers never pool their geometric evidence, and geometry corrections lag behind individual events.

**What CoHelix does differently (the mechanism).** Because all four propellers are rigidly mounted on the same flat plane (coplanar), one 6-parameter homography H (scale, rotation, 2D translation, and 2 perspective terms) can describe how the whole rotor plane projects into the image at any instant — rather than needing four separate, independently-drifting homographies. Each propeller still gets its own 3-parameter rotation state (phase, angular rate, angular acceleration).

The pipeline for each incoming event:
1. **Predict**: use current H and each propeller's rate/acceleration to predict where blades should be.
2. **Admit**: reject events far from any projected propeller ring (cheap spatial check), then map the event back into the flat "rotor plane" via H⁻¹ to determine which propeller it belongs to and whether it's within the valid radial band around that propeller's ring.
3. **Measure**: compute a phase residual (does the event's angle match where a blade should be?) and, if applicable, geometry residuals (radial distance from ring, boundary violations, polarity-direction consistency, blade-silhouette shape, and periodic centroid matching) — all with carefully tuned weighting functions.
4. **Update**: phase residual updates only that propeller's 3-parameter state via a standard Kalman update (no rejection — because when phase is wrong after a gap, you still want to correct it). Geometry residuals update the shared 6-parameter H via a Kalman update too, but *only if* the residual passes an "innovation gate" (a statistical sanity check that an update isn't wildly inconsistent with current uncertainty — this guards against one bad/misassigned event corrupting the geometry that all four propellers depend on).
5. **Propagate**: the corrected H is what the *next* event, from any of the four propellers, gets mapped through — this is the coupling mechanism: evidence from any one propeller's geometry observation improves interpretation of every other propeller's subsequent events.

Additional engineering devices: a "drift observer" periodically fits an ellipse to accumulated events per propeller and nudges the shared geometry's translation/scale if the fitted centers drift from a slow-moving reference (catches systematic drift the per-event filter alone misses); phase-gap handling resets phase uncertainty (but keeps rate/acceleration) after long event gaps, since an abrupt phase correction is expected; and validity checks on candidate geometry updates (finite values, bounded scale/translation changes, positive depth in front of the "projective horizon," bounded matrix condition number) guard against numerically degenerate updates.

**Evaluation metric — "lock".** Rather than only mean absolute/relative RPM error (which conceals brief but critical losses of tracking, including falling into the half/double-rate trap), they define lock: at every 5ms timestamp, is the estimate within 2% of synchronized ground truth (from an IR tachometer or optical gate)? Lock is the fraction of all evaluated propeller-time meeting that bar; a missing estimate counts as unlocked.

## Key insights

- **Genuinely new**: the core architectural idea — one shared homography updated per-event from pooled geometric evidence across multiple rigidly-coupled rotating objects, decoupled from separate per-object rotation dynamics — is the paper's real contribution. This is a reasonably clean generalization of per-event Kalman tracking to a multi-object setting with a shared, jointly-observable constraint (coplanarity + rigidity).
- **Best-supported finding**: the controlled ablation (Table 4 / Sec 4.4) isolating "how many propellers contribute to the shared geometry" (1→4) shows lock rising from 3.4% to 62.9% with everything else fixed. This is the paper's strongest, most directly-controlled piece of evidence that joint geometric constraint — not just better per-event phase tracking — drives the gains. The authors are honest that this comparison conflates "more spatial support" with "more total geometric measurements" (more events contributing), and a follow-up fixed-budget experiment (Sec 4.4/S6.3) that tries to equalize event counts across 1 vs 4 contributors shows both collapse to ≤2.9% lock — meaning they could not cleanly separate "spatial diversity" from "quantity of evidence," so the clean causal story is weaker than the headline ablation implies.
- **Per-event (Kalman) vs windowed (batched Gauss-Newton) geometry updates**: claimed +23.1 point lock improvement, but the 95% CI is wide ([3.7, 43.5]), and the comparison bundles together three confounded factors — solver type, uncertainty treatment, and update schedule — so the paper itself cautions this doesn't isolate which factor matters.
- **Headline benchmark numbers** (62.9% vs 39.8% vs 22.2% on TQE; 95.9% vs 56.2% vs 61.1% on target-follower) are the strongest practical result — consistent wins across nearly all individual recordings (10/12 vs HelixTrack, 12/12 vs EventPro) — but these are relative wins against two specific prior methods under the authors' own reimplementations/reruns, not an absolute accuracy guarantee (e.g., 62.9% lock still means the tracker is "locked" only ~2/3 of the time on the harder dataset).
- Other internal design choices (restricting homography to 6 vs full 8 parameters, retaining vs clearing phase-geometry cross-covariances, using all measurements vs one-per-event) were tested but the confidence intervals straddle zero — the authors explicitly state these do NOT establish a benefit, and they kept the simpler/cheaper choice by default rather than because it was proven better.

## Caveats — stated and inferred

- **Rigid, coplanar assumption** (stated): the shared homography approach requires propellers to be rigidly mounted and coplanar; flexing airframes, non-coplanar mounts, or independent motion between propeller hubs would break the method, per the authors' own "Limitations" section.
- **Requires manual/annotated initialization** (stated): all methods (including baselines) start from annotated ring locations, and CoHelix/HelixTrack additionally need known rotation signs — so this evaluates rate-tracking *after* localization, not detection from scratch.
- **High sensitivity to calibration quality** (stated): a mere 5% increase in supplied ring radius drops target-follower lock from 95.9% to 65.7%, concentrated in one recording, and even shows non-monotonic behavior (one random offset gives 0.8% lock, a larger offset of the same type gives 96.8%) — the authors state this does not establish a monotonic tolerance bound, which is itself a red flag about robustness/brittleness.
- **Narrow evaluation scope** (stated): only two quadcopters, one event sensor type (IMX636/Metavision), and no test of other cameras, airframes, or scenes.
- **Target-follower ground truth not independently verified** (stated): "No second sensor independently verifies this reference" for the optical-gate rate measurement on the private dataset.
- **Neither method runs in real time** (stated): real-time factors are well below 1 for both CoHelix and HelixTrack; CoHelix is faster on one dataset, slower on the other — so no clear efficiency win, and this is run single-threaded on CPU, not an embedded/onboard setting relevant to the motivating application (closed-loop drone control).
- **Homography (geometry) accuracy itself is never scored** (stated): "We do not score homography error" — so claims about *why* the method works (accurate shared geometry) rest on the downstream rate-lock metric only, not direct verification of the geometric estimate.
- **Confounded ablations** (stated/inferred): several key comparisons (contributor count vs. event budget, per-event vs windowed updates, measurement fusion vs single-measurement control) are explicitly acknowledged by the authors to change multiple factors at once (spatial support + measurement quantity; solver + uncertainty + schedule), weakening the causal claims behind the design choices. Several reported deltas (cross-covariance retention, 6- vs 8-parameter homography, multi- vs single-measurement fusion) have 95% CIs crossing zero, meaning the paper's own statistics say "not established," yet these are still presented as support for the final design.
- **Private dataset not released/reproducible by others** (inferred): the target-follower dataset is described as "private," and EventPro/HelixTrack results are the authors' own reimplementation/rerun ("not results certified by its authors"), so independent replication of baseline numbers isn't straightforward.
- **Lock threshold and evaluation protocol chosen partly to match prior work** (inferred): the 2% lock criterion is inherited from HelixTrack for comparability; while sensitivity to 1%/5% thresholds is checked and ordering holds, the core metric design (what counts as "locked") is itself a modeling choice that determines which failures are penalized (e.g., brief dropouts vs. systematic bias), not an externally standard measure.
- **Limited generative-AI disclosure** (stated): the authors note that "OpenAI Codex assisted with manuscript drafting, experiment automation, analysis and presentation" — the extent of AI involvement in result analysis/automation is not further detailed in the text, which is a transparency point worth flagging though not necessarily a flaw in the science itself.
