# Agentic AI Defense: Decode-Time Provenance Binding for MCP

**Authors:** Eric Yocam, Varghese Vaidyan, Paris Kalathas, Patrick Tague, Bruce DeBruhl, Yong Wang

**arXiv:** [2610.31974](https://arxiv.org/abs/2610.31974)

**Categories:** cs.CR, cs.AI, cs.MA

**Submitted:** 2026-10-22

**Relevance:** 9/10 — matched: Document-borne prompt injection

---

## TL;DR
This paper shows that steganographic payloads hidden inside an email-signature image (via LSB, DCT, or metadata tricks) can bypass text-based prompt-injection defenses entirely and still "launder" instructions into a multi-agent MCP pipeline once a tool decodes the image. The authors fix this with "decode-time provenance binding" — an MCP-layer mechanism that cryptographically signs an "untrusted" label the instant any concealment-reversing tool runs, and independently tracks lineage/taint so a compromised agent can't fake trust by swapping labels. On their testbed, undefended systems leak 100% of attacks, keyword/regex scanners leak 62.5%, and their mechanism blocks 100% of attacks while restoring full legitimate-task completion via an audited "trusted promotion" path.

## First-principles breakdown

**The setting.** Modern LLM "agents" don't just chat — they read external content (emails, documents, images) and take actions (send mail, export data) via the Model Context Protocol (MCP), a standardized way for an LLM to call tools. In realistic deployments, a coordinator agent dispatches multiple worker agents that hand results to each other before anything is actually executed.

**The underlying vulnerability class: indirect prompt injection.** If an agent treats external content as instructions, an attacker can hide a command inside data the agent will read (e.g., "forward the saved passwords") and the agent may obey it, even though no human issued it. This is the #1 risk on OWASP's LLM Top 10.

**Why prior defenses exist and how they work.** Two dominant defense families:
1. *Content scanning* — inspect incoming text for suspicious phrases/patterns ("ignore previous instructions") and block matches.
2. *Provenance/taint tracking* — don't judge what text says, just track where it came from. Anything returned by a tool gets labeled "untrusted," and untrusted data is forbidden from triggering sensitive actions (sending mail, exporting files).

Both families assume the dangerous content arrives as **text** that a scanner or label-assigner can see at the moment a tool returns it.

**The attack: "cross-modal trust laundering."** The authors break that assumption. They hide an instruction inside an ordinary-looking logo in an email signature using three techniques:
- *LSB (least-significant-bit) steganography*: overwrite the lowest bit of pixel color values with payload bits — invisible to the eye, pixel data looks almost unchanged.
- *DCT (discrete cosine transform) steganography*: the same frequency-domain trick JPEG compression uses — embed bits by nudging a mid-frequency coefficient in each 8×8 pixel block up or down.
- *Metadata steganography*: stash the (Base64-encoded) payload in a PNG's text metadata chunk — the image pixels are literally untouched.

Because the image contains no suspicious *text*, content scanners (which look at text) see nothing, and because the payload is inert pixel noise until something decodes it, email security gateways pass it straight through. The payload only becomes an "instruction" when, deep inside the agent pipeline, some tool (an OCR step, a steganography extractor, a metadata parser) decodes the image. At that point the decoded text gets relayed between worker agents as if it were ordinary trusted intermediate output — the instruction has been "laundered" from an untrusted image into the trusted text control flow, and an existing provenance scheme that only labels at *text-tool return* never catches it because the dangerous transition happened one step earlier, at decode time.

**The defense: decode-time provenance binding.** The core idea: stop trying to detect whether an image is poisoned (an arms race against ever-better steganography) and instead *contain* anything that comes out of a decoding step, regardless of content. Mechanically:
- The MCP layer (a trusted intermediary all tool calls must pass through) maintains a registry `D` of "decode tools" (anything that reverses concealment: stego extractors, OCR, Base64/metadata decoders) and a registry `C` of "critical tools" (dangerous sinks: send email, export secrets, write files, payments).
- The instant a decode tool returns output, the layer mints a binding record: the payload, the tool, a trust label (`Untrusted` if produced by a decode tool or derived from anything already untrusted — trust is "contagious" through dependencies), the dependency list, and an **HMAC** (a cryptographic signature keyed with a secret that never leaves the layer) over all of it. Agents only ever see an opaque handle to this record, never the raw label or the key — so they can't forge a "Trusted" version.
- The layer also keeps, per execution context, a running **taint set** of which untrusted decode-origins have touched that context — an independent ledger, not something any agent reports.
- Before any critical tool executes, `EnforceCritical` runs: it ignores whatever label an agent *claims*, instead reconstructing the true lineage from the layer's own ledger (walking the full dependency chain) and checking the context's taint set. If any ancestor is untrusted, the HMAC doesn't verify, or a dependency can't be resolved, the call is blocked.

The key design insight is *why two mechanisms are needed together*: the HMAC alone stops forged labels but a compromised agent could still attach a legitimate "Trusted" label from an unrelated benign call while hiding the fact that the real decision was driven by untrusted input ("valid-label substitution"). The independently-maintained context taint catches this because it doesn't rely on what the agent presents — it's the layer's own record of what actually entered that execution context. Conversely, the ledger alone wouldn't survive a relay to a separate trust domain that doesn't share the ledger — that's where the signature matters. Hence both are necessary and non-interchangeable (confirmed by their ablation).

**Trusted promotion.** Since treating *everything* decoded as permanently untrusted would break legitimate workflows (e.g., paying an invoice whose amount was OCR'd from a scan), the system adds an explicit, audited "promotion" step where a human/policy authority can re-label a *specific* decoded value as Trusted, logged in the ledger — restoring usability without reopening the general vulnerability (an attacker can't invoke this promotion themselves).

## Key insights

- **Genuinely new contribution**: identifying that existing provenance/taint defenses label trust at the *text-tool-return* boundary, and demonstrating a concrete, realistic carrier (steganographic email-signature logos) that slips underneath that boundary entirely. This is a real gap the authors explicitly show a related system (NeuroTaint) itself disclaims handling.
- **Mechanistic novelty is modest and explicitly scoped**: the authors themselves state "we claim neither provenance nor steganography as novel; we claim their decode-time junction" — i.e., the contribution is combining known primitives (HMAC signing, taint/lineage tracking, mediated enforcement) at a new binding point (decode time) rather than inventing new cryptography or new steganalysis.
- **What the evidence actually supports**: within their testbed, the mechanism reduces attack success from 100% (undefended) / 62.5% (keyword or regex scanners) to 0%, resists a specifically-constructed "valid-label substitution" attack that a naive agent-trusting taint baseline would miss, and the four-component ablation cleanly shows each piece (decode marking, HMAC, lineage tracking, sink mediation) defends against a distinct attack variant — this is a reasonably rigorous internal validation of the mechanism's logic, not just an end-to-end black-box number.
- **Overhead is claimed negligible**: ~17µs of pure crypto per critical call, and even the full enforcement path (ledger insert + dependency-closure walk) stays under 0.1ms for realistic lineage depths — this is a credible, low-cost claim for a security control since it's a straightforward engineering benchmark.
- **The 0% vs 62.5% comparison is somewhat the headline number but it's comparing against a curated attack bank specifically designed to defeat keyword/regex matching** (eight evasion variants including homoglyphs, zero-width chars, Base64, token-splitting) — so the "evidence" that text scanners fail is almost tautological given the bank was built to break exactly that defense type, not an independent demonstration that this is how real-world attacks would distribute.

## Caveats — stated and inferred

- **Small-scale, controlled testbed** (stated): 24 payloads, 3 carriers, 8 evasions, one cover logo, one small local model (Qwen2.5-0.5B-Instruct), and only a keyword/regex scanner plus an in-house-built taint tracker as baselines. The authors explicitly call this "not a production-scale measurement."
- **No comparison against a modern/state-of-the-art provenance or learned detector system** (stated): the authors note their in-process taint baseline is "an unsigned, agent-mediated taint design... not a state-of-the-art provenance system," and they explicitly defer comparison to published systems like CaMeL, MELON, NeuroTaint to a qualitative table (Table I) rather than a head-to-head empirical test.
- **No real production email-agent deployment** (stated): evaluation runs on their own controlled summarizer pipeline, not an existing production workflow; this is listed as future work.
- **Security proof depends on an assumption that's acknowledged as potentially violated** (stated): the "fully mediated execution context" assumption (iv) — that the layer sees *all* lineage — is explicitly flagged as the mechanism's "load-bearing obligation." An agent that paraphrases a decoded instruction into free text outside the mediated channel is explicitly stated as *not* covered ("outside the model by construction").
- **Decode-set completeness is a manual, unverified configuration burden** (stated): if any concealment-reversing tool is accidentally left out of the admin-curated allow-list `D`, the attack succeeds silently and this is deemed "not a defeat of the mechanism" — which is a somewhat self-serving framing of what is, in practice, a real operational failure mode.
- **Scope limited to actions, not content integrity** (stated): the defense can still let a laundered instruction corrupt the natural-language summary text the agent produces — it only blocks critical tool calls, not reasoning/output corruption. The residual summary-corruption rate is not measured, only acknowledged.
- **Imperceptibility claims are partially walked back** (stated): PSNR/SSIM metrics show the DCT carrier at only ~18dB/0.94 SSIM, and the authors concede these pixel-distortion metrics don't establish genuine perceptual imperceptibility, especially for DCT — leaving this claim weaker than the abstract's emphasis suggests.
- **Legitimate-task evaluation is extremely small** (inferred): only 3 legitimate tasks were tested to measure the 67%→100% completion-rate improvement from trusted promotion — a single false block out of 3 tasks is not a statistically meaningful sample, and this is the paper's key "doesn't hurt usability" evidence.
- **Deterministic security decision decoupled from the LLM** (inferred): since the authors state "the security decision is made by the deterministic layer and does not depend on the model," the choice of a tiny 0.5B local model as the "agent" driving the pipeline is somewhat irrelevant to the security result but may make the "legitimate task completion" and "agent behaves realistically" aspects of the evaluation less representative of production-grade agents (larger/more capable models might behave differently around tool-call triggering, paraphrasing, etc.).
- **Proof sketch is not machine-checked** (stated): the authors explicitly defer a "fully machine-checked proof" and "formal treatment of lineage completeness" to future work — the security argument is a hand-written reduction to HMAC unforgeability plus an assumption, not a verified proof.
- **Ablation and substitution tests are run in the same synthetic testbed** (inferred): all the strong claims (blocks valid-label substitution, survives relay tampering, forged-label detection) are demonstrated on the authors' own constructed scenarios within their own implementation, so there's no independent/adversarial red-team validation outside the paper's own test harness.
