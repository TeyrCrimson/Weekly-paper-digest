# Reading the Room: Scale-ambiguous Semantic Registration of Sparse VSLAM Maps to Floor Plans in Partially Built Environments

**Authors:** Bjorn Stragier, Emilia Szymańska, J. Micah Prendergast, Lukas Rosenberger Schmid

**arXiv:** [2610.29647](https://arxiv.org/abs/2610.29647)

**Categories:** cs.RO, cs.CV

**Submitted:** 2026-10-21

**Relevance:** 6/10 — matched: Metric and temporally-consistent monocular depth

---

## TL;DR
This paper tackles aligning sparse, scale-ambiguous monocular VSLAM maps to symbolic 2D floor plans of partially-built construction sites — a problem no prior method fully solves because it combines unknown scale, cross-modal (point cloud vs. symbolic drawing) matching, missing structure, and visually repetitive scenes. Their system, "Reading the Room" (RR), defines one robust, class-balanced semantic-geometric energy function that both scores candidate global alignments and is directly optimized for local refinement. Across 33 real construction sequences, RR beats classical and learned baselines by 4.5x (unconstrained) to 7.6x (with a user-provided anchor point) in trajectory error.

## First-principles breakdown

**The problem.** Imagine you walk through a half-built building with a 360° camera. A VSLAM (visual SLAM) algorithm reconstructs your path and a sparse 3D point cloud of what it saw (corners of walls, windows, etc.) — but only up to an unknown *similarity transform* (unknown rotation, translation, AND scale, since a monocular camera can't tell if it's looking at a small room from close up or a big room from far away). Separately, there's a 2D floor plan — a symbolic, to-scale architectural drawing — that shows the *intended* final building. The goal: figure out the transform that maps the VSLAM map onto the floor plan, so you know where the camera trajectory actually was in real-world, plan-relative coordinates (useful for progress tracking, etc.).

**Why this is hard (four compounding issues):**
1. *Unknown scale* — monocular VSLAM has no absolute metric reference.
2. *Cross-modality* — the VSLAM output is a noisy point cloud; the floor plan is a clean symbolic drawing. There's no natural one-to-one feature correspondence between "point cloud point" and "pixel in a CAD drawing."
3. *Partial construction* — much of what's in the floor plan (future walls, stairs) doesn't exist yet, so matching against the full plan is misleading.
4. *Visual repetitiveness* — construction sites are full of near-identical corridors, walls, and columns, which both degrades VSLAM's own quality and removes the distinctive landmarks that registration algorithms normally latch onto (causing "perceptual aliasing" — many wrong alignments look locally plausible).

Prior work each addresses at most one or two of these: cross-view localization methods (e.g., LaLaLoc, F3Loc) assume known scale and a fully-built site; SLAM-with-floorplan-prior methods (FP-Loc) assume LiDAR (metric) and a complete building; dense map-alignment methods (region decomposition, graph matching) need a dense reconstruction that sparse VSLAM can't provide; manual-marker methods sidestep the problem by requiring physically placed fiducials.

**The core mechanism — one energy function for everything.**
- First, *preprocessing* reduces the dimensionality gap: it estimates the "up" direction via PCA (the least-variance eigenvector of the point cloud is assumed vertical, since most points lie on floors/walls/ceilings), strips out floor/ceiling points (keeping the 15th–85th percentile height band, since floor plans don't show these), and flattens everything to a 2D bird's-eye view. This turns the problem from a 7-parameter 3D similarity transform (Sim(3)) into a simpler 4-parameter 2D one (Sim(2): scale, rotation, x/y translation). A vision-language segmentation model (SAM3) optionally labels each point as wall/window/stairs/unlabeled.
- Second, the *energy function* L_sem scores any candidate transform by: for each labeled 3D point, project it into the floor plan and measure its distance to the nearest same-class floor-plan pixel (precomputed as a distance-transform image per class, so lookup is O(1) per point). This distance is "truncated" (capped) so outlier/clutter points can't dominate, then passed through a Huber loss (quadratic near zero for smooth gradients, linear further out for robustness) for a given class. Then, critically, the result is averaged *per class first, then across classes* — so a rare-but-informative class like "stairs" counts as much as the abundant "wall" class, instead of being drowned out. This single scalar function is used for literally every stage: scoring random initialization candidates, scoring network-matched candidates, and as the differentiable loss for gradient-based refinement.
- Third, *global initialization* has two modes. (a) If a user taps one rough point on the floor plan corresponding to a known trajectory point ("anchor"), the search reduces to just finding scale+rotation around that fixed point — done by randomly sampling 20,000 (rotation, scale) pairs and picking the one with lowest energy. (b) Without an anchor, they use a cross-modal dense feature-matching network (RoMa, fine-tuned from MatchAnything weights on a synthetic dataset they generated by augmenting 100 real floor plans — cropping, sparsifying, randomly blacking out regions, adding noise/jitter — to mimic partial construction and VSLAM sparsity). Rather than trusting RANSAC's "largest inlier set" (which fails when the scene is self-similar, since a wrong-but-locally-consistent match can have a huge inlier set), they take the top 1000 matches, fit closed-form transforms (Umeyama/Procrustes) from 200 random 2-point samples, and pick the lowest-energy one.
- Fourth, *local refinement* takes the best candidate and directly minimizes L_sem over the 4 continuous parameters using L-BFGS (a quasi-Newton gradient optimizer), using the function's closed-form gradient, for up to 5000 iterations.

This is essentially "coarse-to-fine registration," but the novelty is using the exact same scoring function at every stage rather than switching objectives, which keeps the whole pipeline consistent and lets global search effectively pre-select good basins of attraction for the local optimizer.

## Key insights

- **Genuinely new**: a single unified, differentiable, class-balanced robust energy function used for both global candidate scoring and local gradient-based refinement — avoiding the usual mismatch where a discrete matching stage and a continuous refinement stage optimize different objectives.
- **Genuinely new**: using scoring-by-energy-function rather than RANSAC-style inlier counting for cross-modal feature match selection — the paper's own ablation (Table III, "Match") supports this: their energy-based candidate selection beats RANSAC (14.82/4.34 vs 20.40/12.23 mean/median ATE overall), specifically because self-similar construction scenes make "most inliers" a misleading criterion.
- **Supported by evidence**: large, consistent improvements over baselines are demonstrated with real ablations isolating each design choice (semantic weighting, class-balanced aggregation, global init scoring vs. grid search, local refinement vs. none, anchor accuracy robustness). The claim that the global initialization stage (basin-finding) matters more than local refinement is directly supported (refinement adds "only" ~24% median ATE improvement, while global strategy changes the error by multiples).
- **Claimed but only partially supported**: "first effective solution to this problem" — true relative to tested baselines, but the method still fails outright on the hardest site (Site C, 0% recall at any threshold, mean ATE ~43m), so "effective" is qualified. The headline 4.5x/7.6x improvement numbers are real but are improvements over weak baselines (see caveats) rather than evidence of solving the task well in absolute terms.
- **Robustness claim supported**: anchor-position noise barely hurts performance (median ATE only 4.4% worse than using ground-truth anchor), which is a reasonably strong, directly-tested result.

## Caveats — stated and inferred

- **stated**: Registration remains unreliable on the hardest site (Site C) — low coverage (28.7%) and structural symmetry drive all methods, including theirs, into wrong (e.g., 180°-flipped) solutions; 0% recall at 1/3/5m thresholds even for RR.
- **stated**: An oracle lower bound (fitting trajectory directly to ground truth) still has ~1m residual error due to VSLAM drift/imperfect loop closure — meaning even "perfect" registration can't fully close the gap; the authors explicitly defer non-rigid, floor-plan-conditioned deformation to future work.
- **stated**: Symmetric/self-similar environments remain an open problem; the paper explicitly flags "further mechanisms to resolve symmetric ambiguities" as future work.
- **stated**: Hyperparameters (τ=25px, Huber δ=10px) were chosen "without notable parameter tuning" and used across all experiments — the authors note this but it means sensitivity to these choices is unverified.
- **inferred**: Dataset scale is modest — 33 sequences across only 3 sites (14 floors, 2 countries) all captured with the same custom LiDAR+360°-camera device and same VSLAM pipeline (OpenVSLAM). Generalization to other VSLAM systems (e.g., ORB-SLAM3), camera types, or a broader range of building styles is untested.
- **inferred**: Baselines may be somewhat mismatched/weak for this exact task: SIFT+RANSAC fails almost completely (32/33 runs) and classical ICP/region-decomposition methods (Shahbandi & Magnusson) were "designed" for dense LiDAR maps, not sparse VSLAM — so the large reported multiples (4.5x–7.6x) partly reflect baselines operating far outside their intended regime rather than a tight competitive comparison against methods built for this exact setting (the paper itself states no existing method directly addresses this problem).
- **inferred**: Ground truth itself is produced via "manually aligned" LiDAR trajectories by an expert — introducing a potential source of human-labeling error/bias in the metric used to judge all methods, not independently verified.
- **inferred**: The semantic class set is very small and fixed (wall, window, stairs) — performance on floor plans with richer/different semantic schemas, or where SAM3 segmentation quality is worse, is not evaluated.
- **inferred**: The synthetic fine-tuning dataset for the matching network is generated from only 100 labelled drawings (expanded to 2000 pairs via augmentation) — a small base set whose diversity may not generalize to floor plans stylistically different from the training distribria.
- **inferred**: Runtime results (Table IV) are reported on a single high-end desktop CPU/GPU (i9-10900K + RTX 3090) with no discussion of performance on embedded/robot-class hardware, despite motivating the work with "robotic construction applications."
- **not addressed in the paper**: Any discussion of failure detection/confidence calibration — i.e., whether the system can tell the user when its own alignment is likely wrong (which would matter a lot given Site C's outright failures) is not addressed.
