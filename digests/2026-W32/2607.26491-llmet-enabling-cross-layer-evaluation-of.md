# LLMET: Enabling Cross-Layer Evaluation of Emerging M3D Memories for Energy-Efficient LLM Serving

**Authors:** Ming-Yen Lee, Hanchen Yang, Faaiq Waqar, Harsono Simka, Tushar Krishna, Muhammed Ahosan Ul Karim, Shimeng Yu

**arXiv:** [2607.26491](https://arxiv.org/abs/2607.26491)

**Categories:** cs.AR, cs.AI, cs.ET, cs.LG

**Submitted:** 2026-07-29

**Relevance:** 9/10 — matched: LLM inference efficiency and long-context serving

---

## TL;DR
LLMET is a cross-layer simulator that models how emerging monolithic-3D (M3D) on-chip memory — gain-cell "eDRAM" built into the chip's back-end interconnect layers — affects the energy cost of serving LLMs, by jointly tracking cache-aware operator scheduling and device-calibrated power/area numbers. Across A100, B200-like, and Jetson-class edge platforms, scaling on-chip L2 cache from tens of MB to GB-scale using M3D technology cuts prefill energy by up to 44% and decode energy by up to 30-80%, but the benefit is highly workload- and phase-dependent (short prompts can actually get worse). The paper's main contribution is the simulator itself plus a design-space study, not a new memory device or LLM algorithm.

## First-principles breakdown

**The problem.** Serving an LLM means repeatedly moving two huge things — model weights and the KV cache (stored keys/values from attention) — between the GPU's tiny on-chip SRAM (tens of MB) and its off-chip High Bandwidth Memory (HBM, many GB). Moving a bit off-chip costs roughly 100x more energy than moving it on-chip. As models and context windows grow, this data movement, not the arithmetic itself, dominates the energy bill of inference. Two phases behave differently: *prefill* (processing the whole prompt at once) is compute-heavy but still moves a lot of data; *decode* (generating tokens one at a time) is memory-bound because it reloads all the weights and the growing KV cache for every single new token.

**Why bigger on-chip cache would help, and why it hasn't scaled.** If you could keep more weights/KV data on-chip, you'd avoid HBM round-trips. But conventional on-chip memory is SRAM built in the same 2D plane as the logic transistors, so making it much bigger means burning die area (and money) that could otherwise host compute. Stacking separate SRAM dies on top of the processor (like AMD's 3D V-Cache, ~96MB) helps but each stacked layer is tens of micrometers thick, so heat can't escape and you're capped at a modest number of layers.

**The M3D fix.** Instead of bonding a separate SRAM chip, monolithic 3D (M3D) integration builds memory cells directly *within* the back-end-of-line (BEOL) interconnect stack that sits above the transistors — using new "amorphous oxide semiconductor" (AOS) transistors instead of standard silicon ones. This BEOL layer is only a few micrometers thick (vs. tens of micrometers for bonded dies), so it dissipates heat much better and can be built denser, in principle scaling on-chip capacity into the hundreds of MB to GB range using a "2T gain-cell" (2T-GC) memory cell design. The open question the paper poses: does having that much on-chip memory actually translate into system-level energy savings for real LLM serving workloads? Nobody had built a tool that connects device-level memory technology choices all the way to system-level LLM energy numbers.

**Why existing simulators can't answer this.** The paper surveys prior LLM-system tools (Table 1: Calculon, Vidur, GenZ, LLMCompass, DynamoLLM, LLMServingSim 2.0). Each is missing at least one of three things needed here: (1) support for non-SRAM emerging memory technologies with realistic circuit-level energy/area models, (2) a scheme that changes how operators are tiled/fused as cache size changes (most assume one fixed tiling strategy regardless of cache size, so they can't show how off-chip traffic shrinks as cache grows), and (3) a fine-grained, per-component (DRAM/L2/L1/systolic array/vector unit/interconnect) energy breakdown rather than just aggregate latency or area/cost.

**LLMET's mechanism, step by step:**
1. **Front-end tracing**: Given an LLM architecture and a hardware config, LLMET generates a per-operator execution trace: operator type, tensor shapes, chosen tile sizes, bytes moved at each memory level (register file, L1, L2, DRAM), and compute cycles per functional unit.
2. **Capacity-aware mapping**: For each matrix multiply, if the available L2 can hold one operand, that operand is pinned on-chip and the other is streamed from DRAM in tiles; the *remaining* capacity picks among four fusion/tiling regimes (an algorithm, not a fixed choice) — this is the key mechanism that lets the tool show how off-chip traffic scales with cache size, which fixed-tiling tools cannot do.
3. **Operator fusion for attention**: QK^T and softmax·V are scheduled head-by-head so intermediate logits/softmax stay on-chip and only Q/K/V and the final output touch DRAM, when the per-head working set fits in cache. For grouped-query attention, shared KV heads are pinned across a query group when cache is large enough, avoiding redundant KV reloads — especially important beyond 16K-token contexts.
4. **Back-end PPA (power/performance/area) modeling**: Compute units are modeled from ASAP7 7nm RTL synthesis; SRAM and the new 2T-GC M3D memory are modeled with a circuit-level model called NS-Cache (using the 2T-GC device model and 3D area costs instead of 2D H-tree area for the M3D case); interconnects are modeled with NeuroSim; HBM/LPDDR energy comes from foundry-reported per-bit numbers. This means technology parameters (e.g., a not-yet-fabricated GB-scale M3D cache) propagate directly into energy/area estimates rather than being guessed from profiling.
5. **Validation**: die-area estimates are compared against real, published NVIDIA A100 numbers and match within 7%.

Using this, the authors sweep cache size (SRAM baseline up to GB-scale M3D) across three regimes — server (Llama-70B on 2×A100), technology-scaling (Llama-405B on 8×B200-like), and edge (Llama-3.2 1B INT4 on Jetson-like) — and report HBM traffic, energy, and area.

## Key insights

- **Genuinely new**: the simulator itself — combining (a) circuit-calibrated energy/area models for a memory technology that isn't yet mass-produced at scale, (b) cache-capacity-dependent operator fusion/tiling (rather than fixed tiling), and (c) fine-grained per-component energy breakdown — is the paper's real contribution, and Table 1 makes a reasonably convincing case that no prior tool combines all three. This is a tooling/methodology contribution, not a new hardware or algorithm.
- **M3D vs planar SRAM**: at GB-scale capacity, M3D 2T-GC keeps chip area overhead to ~23% (vs. baseline 40MB) while planar SRAM scaling is called "prohibitive" due to H-tree routing overhead — and M3D also has lower per-bit access energy than SRAM at the same capacity per Table 2. This is the paper's clearest quantitative "why M3D specifically" claim.
- **The headline energy numbers are real but conditional, not universal**: 44% prefill energy reduction (A100, Llama-70B, 16K context), 24% (B200-like, Llama-405B, 32K context), 30% decode reduction (edge, 8MB→256MB). These are best-case points on a curve, not typical/average savings — the paper itself shows savings saturate and even reverse (negative for some workloads in Figure 1, e.g. short-context edge prefill costs *more* energy with bigger cache).
- **The paper's most nuanced and probably most defensible finding** is the workload-dependence: bigger cache helps prefill mainly for long contexts and helps decode broadly once near full model residency, but for short-prompt edge prefill, added L2 access energy can outweigh reduced DRAM traffic — so "bigger on-chip cache = better" is explicitly not a universal claim, contrary to what a naive reading of the abstract's percentages might suggest.
- Claimed "first" status ("the first LLM system simulator that can propagate device-level design choices all the way to system-level serving energy") is an assertion the paper supports via its literature comparison table but which readers should treat as the authors' framing rather than an independently adjudicated fact.

## Caveats — stated and inferred

- **B200-like platform is extrapolated, not measured** (stated): "parameters extrapolated from disclosed Blackwell performance metrics relative to the A100 baseline" and the 3nm node uses NeuroSim projections aligned with an industry roadmap (IRDS), not measured silicon — so the 405B/B200 results rest on an extra layer of estimation beyond the validated A100 case.
- **Validation is limited to die area only** (stated/inferred): the 7% error validation covers total die area and core area against published A100 numbers; there is no validation of actual measured *energy* or *performance* numbers against real hardware, only area. Energy/latency accuracy is therefore unverified against ground truth.
- **M3D 2T-GC memory itself is not yet fabricated at GB scale** (stated implicitly): the paper explicitly frames this as "forward-looking evaluation of memory technologies that have not yet been fabricated at full capacity" — i.e., the core enabling technology is largely simulated/projected from smaller-scale device models (NS-Cache), not demonstrated at the capacities being touted (up to 4GB).
- **Cherry-picked-looking headline numbers** (inferred): abstract numbers (44%, 24%, 30%) are the best points along swept curves (specific sequence length, batch size, cache size combinations) rather than typical/average savings; the body text shows saturation, reversals, and workload-dependence that don't make it into the abstract framing.
- **No comparison against alternative energy-saving techniques** (inferred): the paper compares cache-size scaling under M3D vs SRAM, but doesn't benchmark against other established energy-reduction approaches (e.g., quantization beyond the edge INT4 case, KV-cache compression/eviction like H2O, speculative decoding, disaggregated serving) as alternatives or complements — so it's unclear how this cache-scaling benefit stacks up against or combines with other known techniques.
- **Heuristic mapping limitation acknowledged** (stated): the authors note that "some FFN layers under 128MB and 256MB caches still rely on heuristic mapping, so the selected tiling may not always minimize traffic under limited search space" — i.e., the tool's own mapping search is incomplete/heuristic in some configurations, which could bias reported savings.
- **Edge full-residency numbers explicitly flagged as unrealistic/aspirational** (stated): the authors themselves caveat that 512MB–1GB edge cache results are "an aspirational upper bound rather than a near-term edge-cache target" given area constraints on real edge silicon — a rare and welcome self-imposed caution, but it means part of the reported edge savings (up to 75-80% decode energy) doesn't reflect near-term deployable hardware.
- **Simulation-only evaluation overall** (inferred): all energy/traffic results come from the LLMET simulator; there is no physical prototype of an M3D-cache-equipped LLM accelerator, so real-world effects (thermal throttling under sustained load, manufacturing yield/cost at GB-scale M3D, circuit-level noise/reliability of gain-cell memory) are not addressed in the paper.
- **No discussion of cost or manufacturing yield** (inferred): area/energy are modeled, but the practical cost of fabricating GB-scale BEOL memory (yield, reliability, refresh overhead of gain cells, which need periodic refresh like DRAM) is not addressed in the paper.
- **Single model family per regime** (inferred): each deployment regime is evaluated on essentially one model per class (Llama-3.1-70B, Llama-3.1-405B, Llama-3.2-1B) — generalization to other architectures (e.g., different attention variants, MoE models) is not addressed in the paper.
