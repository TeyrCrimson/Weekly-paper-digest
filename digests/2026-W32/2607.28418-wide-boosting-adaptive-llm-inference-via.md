# WIDE: Boosting Adaptive LLM Inference via Token-level Dynamic Width Pruning

**Authors:** Haozhe Hu, Hao Wu, Peiran Yin, Chao Han, Yunpu Ma, Xiaoyu Shen

**arXiv:** [2607.28418](https://arxiv.org/abs/2607.28418)

**Categories:** cs.AI, cs.CL, cs.LG

**Submitted:** 2026-07-30

**Relevance:** 9/10 — matched: LLM inference efficiency and long-context serving

---

## TL;DR
WIDE is a dynamic pruning framework that lets each token independently choose which attention-head groups and FFN-channel groups to compute, pushing dynamic sparsity from today's layer/sublayer granularity down to a "neuron-block" level. To make this fine-grained, input-dependent sparsity actually run fast on GPUs, the authors pair it with a kernel co-design (mask reordering + multi-level predicated skipping) that avoids the gather-scatter overhead that normally kills dynamic-sparsity speedups. At 50% sparsity on Llama3.1-8B/3.2-3B, WIDE retains far more zero-shot accuracy than prior static and dynamic pruning baselines while delivering near-theoretical kernel speedups (up to 1.98x prefill, 4.95x decode) and 1.68x/1.55x measured end-to-end acceleration.

## First-principles breakdown

**The problem.** Serving LLMs efficiently often relies on pruning — removing redundant weights/structures. *Static* pruning (e.g., removing whole layers, heads, or neurons based on calibration data) is simple and hardware-friendly, but it applies the same cuts to every input, so at high sparsity it damages accuracy because not every token actually needs the removed capacity.

**Why dynamic pruning helps, but not enough.** *Dynamic* pruning uses a lightweight router to decide, per token, how much compute to spend (Mixture-of-Depths, D-LLM, SkipGPT). This adapts to the input, but existing methods mostly decide at the level of "does this token execute or skip this whole layer/sublayer" — a coarse, all-or-nothing decision. A token might only need part of a layer's capacity, but coarse routing forces it to take all or none.

**Why fine-grained dynamic pruning has been impractical.** Once you let each token choose a different subset of neurons/heads (not just skip whole layers), the resulting sparsity pattern is irregular across tokens. Naively implementing this requires converting routing masks into index lists and gathering/scattering only the "active" rows into GEMM/attention kernels. This causes (1) device-to-host synchronization that breaks CUDA Graph replay, and (2) large extra memory traffic/storage (the paper shows this overhead can dominate wall-clock time, Fig. 3), so the theoretical FLOP savings never show up as real speedups.

**What WIDE actually does:**
1. *Pruning units.* In attention, the atomic prunable unit is a GQA-aligned group of query heads (sized to match the query-heads-per-KV-head ratio), so K/V caching stays intact — only Q/O compute for a head-group is skipped, never K/V. In the FFN, the atomic unit is a contiguous block of intermediate channels (in the up/gate output dimension and down-projection input dimension), with block size G chosen to match GPU GEMM tile sizes.
2. *Router.* A tiny bottleneck network (down-project to rank r, then up-project) maps each token's hidden state to a binary execute/skip decision per group. During training, Gumbel-Softmax gives a differentiable relaxation of this discrete choice; at inference it's a hard argmax.
3. *Two-stage training.* Stage 1 freezes the backbone and trains only the router (plus a sparsity-target loss term) — "router calibration." Stage 2 optionally adds LoRA adapters to the backbone's linear layers to recover quality lost to pruning.
4. *Making it fast: mask reordering.* Instead of gather-scattering per-token, WIDE sorts the binary mask within each routing group so active tokens cluster into contiguous prefixes of GEMM tiles — turning ragged, token-level sparsity into GPU-tile-level (CTA-level) regularity, with only one boundary tile per group needing special handling.
5. *Multi-granularity skipping.* On top of the reordered layout, a single predicate is evaluated at three levels: level 0 skips an entire fully-inactive CTA tile (hardware-agnostic); level 1 skips inactive rows during data loading (architecture-dependent, e.g., cp.async vs. TMA gather); level 2 skips inactive tensor-core (MMA) fragments (warp-level, architecture-dependent). This preserves the original dense GEMM/attention pipeline shape (so producer-consumer pipelining/barriers stay well-defined) while progressively cutting wasted work. Three custom kernel families (GEMM-MN, GEMM-K, and a modified FlashAttention) implement this for Q/Up/Gate projections, O/Down projections, and attention respectively.

## Key insights

- **Genuine novelty (architecture):** moving dynamic, differentiable, token-level routing decisions below the layer/sublayer level down to head-groups and channel-groups, within a single end-to-end trainable framework covering both prefill and decode. Prior width-level dynamic methods (PolarSparse, FastForward) were restricted to one of prefill or decode only.
- **Genuine novelty (systems):** the mask-reordering + 3-level predicated skipping scheme is presented as the first mechanism to make fine-grained, per-token dynamic sparsity translate into near-ideal GPU speedups rather than being swallowed by gather-scatter overhead — this is as much a systems contribution as a modeling one, and the paper explicitly frames "dynamic pruning needs to be co-designed with the execution path" as its main takeaway.
- **What the evidence actually supports:** on Llama3.1-8B/3.2-3B, WIDE retains 85–90% of dense accuracy at 50% sparsity (vs. ~50–75% for the strongest static/dynamic baselines), across both calibration-only and LoRA-recovered settings, on 7 zero-shot tasks plus WikiText2 perplexity — a reasonably broad and consistent evaluation for the accuracy claim. Kernel-level benchmarks (Triton, CUDA Graph replay) show speedups close to the theoretical ceiling, and a real end-to-end measurement (ELANA-style profiling) shows 1.68x/1.55x on an actual RTX 5090 — this is a real, measured (not just simulated) systems result.
- **Group size G is an interpretable, tunable knob:** quality is fairly robust across G (16–512), but kernel efficiency (especially GEMM-K/GEMM-MN) needs G ≥ 128 to approach ideal speedup — a genuine, quantified trade-off rather than a single cherry-picked setting.
- **Interpretability finding (weaker evidence):** routing is very non-uniform — attention gets pruned far more (66.2%) than FFN (28.5%), and case-study visualizations suggest FFN routers preferentially keep "content" tokens and skip function words. This is presented via a handful of qualitative examples (case studies in the appendix), not a systematic quantitative analysis, so it should be read as suggestive rather than established.

## Caveats — stated and inferred

- **stated:** Inference experiments were "mainly conducted on GPUs with sm120 architecture (NVIDIA RTX 5090)"; the finest-grained skipping (intra-block loading/MMA skip) is only available via a low-level CuTe/CUTLASS implementation, while the more portable Triton/Tilelang DSL implementations only support coarser CTA-level skipping. An additional sm90+ atomic-writeback optimization is explicitly deferred as "future work" because it doesn't fit sm120's shared-memory budget — the practical speedup is architecture- and implementation-dependent.
- **stated:** Router execution, sorting, and zero-init overhead account for ~16.7% of total prefill latency and ~29.1% of total decode latency even in the best case — a non-trivial fixed cost that caps how close real speedups get to the theoretical GEMM-level numbers.
- **stated:** Under a uniform (forced 1:1 attention/FFN) sparsity constraint, accuracy drops more sharply at larger group sizes before LoRA recovery, though the authors report LoRA recovers most of the loss.
- **inferred:** End-to-end and layer-wise latency figures (Fig. 4, Fig. 8) are reported at batch size 1; how routing/kernel behavior holds up under realistic multi-request continuous batching, paged KV-cache serving, or mixed sequence lengths is not shown — only isolated kernel-level benchmarks sweep batch size.
- **inferred:** Evaluation is limited to two model sizes from a single family (Llama3.1-8B, Llama3.2-3B); generalization to larger models (e.g., 70B) or other architectures (Mistral, Qwen, MoE models) is not addressed in the paper.
- **inferred:** Several calibration-only static baselines produce degenerate perplexity (e.g., Shortened-taylor at 4.85e7, D-LLM at 504) at 50% sparsity, suggesting these baselines are essentially broken in that regime — this makes WIDE's relative margin in the calibration-only table look larger than a comparison against well-tuned baselines might; the LoRA-recovered comparisons are more informative but still show large gaps.
- **inferred:** For the SkipGPT baseline, the authors state they "additionally increase the router rank r to match the router capacity of WIDE" — a reasonable fairness adjustment, but it means baseline configurations were tuned post hoc by the paper's own authors rather than using each baseline's officially reported best settings, which is a mild self-reported-baseline risk.
- **not addressed in the paper:** wall-clock/compute cost of the two-stage training pipeline (router calibration + LoRA) in terms of total GPU-hours, which matters for practical adoption cost.
- **not addressed in the paper:** integration with production serving stacks (vLLM/SGLang) at scale, multi-GPU behavior, or robustness under distribution shift (e.g., calibration data from RedPajama vs. deployment domains).
