# AngelSpec: Towards Real-World High Performance Inference with Speculative Decoding

**Authors:** Hong Liu, Rui Cen, Junhan Shi, Guangshuo Qin, Jiebin Zhang, Tianyu Liu, Runzhi Fan, Guoliang Zhao, Ruobing Xie, Kai Zhang, Song Liu, Guanghua Yu, Jianchen Zhu

**arXiv:** [2607.25852](https://arxiv.org/abs/2607.25852)

**Categories:** cs.CL

**Submitted:** 2026-07-28

**Relevance:** 9/10 — matched: LLM inference efficiency and long-context serving

## TL;DR
AngelSpec is Tencent's unified training/serving framework for speculative decoding that argues no single drafter architecture wins across all workloads, so it trains two specialized drafters — an autoregressive multi-token-prediction (MTP) model for open-ended chat and a block-parallel diffusion model (DFly) for code/math — and adds a runtime component (D-cut) that dynamically allocates target-model verification compute across concurrent requests. On the Hy3-A21B model, DFly raises average accepted draft length by ~30% and delivers 1.98–2.40× speedup over plain autoregressive decoding, beating a prior method (DFlash) by 10.5–11.8% throughput; D-cut adds a further 3–15.7% throughput on live production traffic at high concurrency. The paper's contribution is as much the released open-source training framework as the individual architectural/algorithmic tricks.

## First-principles breakdown

**The base problem: speculative decoding.** Normal LLM decoding generates one token per forward pass through the (expensive) target model — slow because each pass is compute-heavy but only yields one token. Speculative decoding speeds this up without changing output quality: a small, cheap "drafter" model proposes several candidate future tokens, then the big target model verifies all of them in a *single* forward pass using rejection sampling. If the drafter's proposed distribution overlaps well with the target's, many tokens get accepted per verification round, so the wall-clock cost of one target pass is amortized over multiple committed tokens. The speedup is driven by two numbers: how many draft tokens get accepted (acceptance length) and how expensive one draft+verify round is.

**Why one drafter design doesn't fit everything.** There are two broad drafting paradigms:
- *Autoregressive multi-token prediction (MTP)*: a lightweight module bolted onto the target model that predicts the next few tokens one at a time, reusing the target's hidden states/embeddings/output head. It's cheap and stable but each additional draft position requires another sequential mini-step, so it doesn't scale to long proposals well.
- *Block-parallel (diffusion-style) drafting*: predicts an entire block of future tokens in one parallel forward pass (bidirectional/non-causal), so drafting latency barely grows with block length. Great when continuations are long and predictable (code, math), but weaker when many different continuations are equally plausible (open-ended chat), because a non-causal block can't fully model position-to-position dependencies within the block, and the "right" continuation is genuinely ambiguous for a while (high entropy) — so verifying a whole long block often wastes compute.

The paper's core observation: real traffic mixes both regimes, and prior work tunes one drafter against an averaged benchmark mix, which under-serves both extremes. AngelSpec instead trains two separate drafters, each matched to its regime, rather than forcing one architecture/data mix to do everything.

**MTP fix — Training-Time Test (TTT) and acceptance-aligned losses.** A known problem with reusing an MTP module recurrently at inference (to draft depth >1) is train/inference mismatch: during training the module normally sees ground-truth ("teacher-forced") tokens at every depth, but at inference depth k≥1 it must consume its *own* earlier (possibly wrong) predictions. This causes errors to compound, so deeper draft positions get accepted far less often. The fix (borrowed from EAGLE-3's TTT idea): during training, unroll the same shared MTP block autoregressively across depths, feeding each depth's own sampled prediction into the next, so it learns to recover from its own mistakes like it must at inference. They also swap the training objective: cross-entropy → KL divergence → a blended KL/Total-Variation (TV) loss → an end-to-end multiplicative TV objective that directly approximates expected accepted length (since acceptance probability under rejection sampling equals 1 minus the TV distance between target and draft distributions). They further curate training data: diverse conversational/long-context/agentic trajectories, and critically, they generate training data by rolling out the *frozen target model itself* rather than using original human/other-model reference answers, so the drafter learns the target's actual token-level behavior instead of a mismatched distribution.

**Block-diffusion fix — DFly.** Building on a prior method called DFlash (projects several target-model layers' hidden states through one shared fully-connected transform to condition every draft layer identically) and DFlare (a lighter per-draft-layer weighted mixture of target-layer features, so different draft depths see different views of the target), DFly combines both: a shared globally-transformed context (rich but generic) plus a layer-specific refinement (specialized but cheap), fused via RMSNorm. Second, because parallel block drafting predicts all block positions independently (no visibility into what token was actually chosen at earlier block positions), DFly adds a lightweight "hidden-correction" autoregressive head after the parallel backbone: it feeds the previously realized token's embedding through a small SwiGLU correction into each subsequent block position's hidden state before the LM head, converting independent marginal predictions into predecessor-conditioned ones — while keeping the expensive backbone itself fully parallel. Training again moves from a position-aware weighted KL/TV cold-start (D-PACE weighting, which weights each depth's loss by how likely earlier positions are to survive) to the end-to-end TV objective. Finally, they fine-tune on domain-specific code/math data (from OpenCodeInstruct, OpenCodeReasoning, Big-Math) to specialize DFly further toward long, structured continuations, at a small cost to chat performance.

**Serving-time fix — D-cut.** Even with a good drafter, a fixed verification depth (how many draft tokens to check per step) is suboptimal in production because (a) different requests/domains have very different real acceptance lengths, and (b) the marginal latency cost of verifying one more token depends on current batch size/load/hardware. D-cut treats verification capacity as a shared, budgeted resource across all concurrent requests in a batch rather than deciding per-request in isolation. It estimates each request's expected useful draft depth from the drafter's own token-level confidence scores (cumulative product of per-token confidences approximates survival probability), then picks a global "keep ratio" (25%/50%/75%/100% of the batch's total draft positions) that maximizes estimated total accepted tokens divided by a pre-profiled runtime cost for that (batch size, ratio) pair. It then packs the retained token positions from all requests into one dense batch for target verification — this doesn't change what tokens get accepted for a request once verified (still standard target-model rejection sampling), it just decides how deep to bother checking.

## Key insights

- **Genuinely new framing**: treating drafting-structure choice as a workload-heterogeneity problem (chat vs. code/math have different optimal drafter types) rather than searching for one universal best drafter — this is the paper's central conceptual contribution, and the ablations (Table 3, Table 6) do support that specialization by domain and by "thinking mode" gives real gains.
- **DFly's architectural combination (hybrid conditioning + hidden-correction head) is incremental but validated**: it's explicitly built by combining pieces from two prior papers (DFlash, DFlare) plus a correction-head idea from other recent papers (DSpark/TreeFlash-style), and the ablation in Table 4 shows each addition contributes a measurable, if modest, incremental gain (3.77→4.40→4.56/4.60→4.75 average accepted length). The evidence supports the claim of improvement over DFlash specifically, on their benchmarks.
- **D-cut's contribution is validated on live production traffic**, not just synthetic benchmarks (Section 4.4, Figure 4) — this is a stronger form of evidence than most speculative-decoding papers offer, and the reported acceptance-length drop (≤2.8%) versus throughput gain (up to 15.7%) is a real measured trade-off, not just a theoretical argument.
- **Training framework release (AngelSpec) itself is presented as a contribution** — disaggregated hidden-state generation, long-context TTT sharding, unified support for both drafter paradigms. The paper argues this is useful infrastructure, but the text gives less rigorous evidence for framework-level claims (mostly descriptive) compared to the drafter/D-cut results.
- The paper is upfront that MTP and DFly are *not* meant to replace each other — MTP remains better for chat (Table 3, Table 7 show MTP-3 winning on MT-Bench), so the "key insight" is complementary specialization, not a single dominant method.

## Caveats — stated and inferred

- **Thinking-mode/data-matching brittleness (stated)**: Table 6 shows a no-think-trained drafter's accepted length collapses from 4.79 to 3.29 when evaluated in high-think mode — the authors explicitly conclude separate drafters must be trained and deployed per thinking mode, meaning the system needs multiple specialized checkpoints per target model, adding deployment/maintenance complexity.
- **D-cut is admittedly not free and not always beneficial (stated)**: the paper explicitly says "D-cut is not assumed to be free" — selector/packing overhead exists, current implementation only supports piecewise CUDA graphs (not fully captured graphs), and budget selection currently sits on the critical path (synchronization point) rather than overlapping with target execution; these are called out as current implementation limits the authors are "actively working to remove."
- **No uniform gain across all workloads (stated/implied by data)**: DFly underperforms MTP on MT-Bench-style chat in Table 7 (MTP-3 beats DFly-8 at c64, 2.53× vs 2.44× speedup on GSM8K-ish rows and specifically on MT-Bench numbers), and DFly's speedup over AR degrades at very high concurrency (c64) relative to mid concurrency — the system's advantage is domain- and load-dependent, not universal.
- **Middle-truncated text limits full verification (inferred)**: the provided full text is truncated in the middle (marked explicitly), so parts of the deployment/results discussion, additional ablations, and the full "AngelSpec framework" implementation details could not be assessed here.
- **Single hardware/model-family evaluation (inferred)**: quantitative throughput results are reported only for Hy3 model variants (Hy3-A21B, Hy3-295B-A21B) on specific GPU setups (H20, TP=8) and Qwen3-8B for draft-quality-only comparisons; generalization to other model families, other accelerators, or other parallelism strategies is not demonstrated in the given text.
- **Comparisons are against a limited baseline set (inferred)**: the main throughput comparison is against autoregressive decoding and DFlash (and DSpark/MTP for draft-quality tables only); it's not addressed in the paper whether comparisons were made against other recent adaptive-verification-depth methods cited in Related Work (e.g., SpecDec++, DySpec, Talon), so the D-cut throughput claims rest on comparison to DFly-without-D-cut and AR only, not the broader adaptive-depth literature.
- **"Deterministic-draft and target-only verification protocol" caveat on distribution-preservation claim (stated)**: the exact output-distribution-preservation guarantee for D-cut is stated to hold "under the deterministic-draft and target-only verification protocol used in our deployment experiments" — implying the exactness guarantee may not hold unconditionally under other (e.g., stochastic sampling) serving configurations; this qualifier limits how broadly the "lossless" claim generalizes.
- **Reliance on self-reported/target-generated training data (inferred risk)**: training drafters on responses generated by the frozen target model itself (rather than diverse independent references) could overfit acceptance-length metrics to the target model's own idiosyncrasies rather than reflecting robustness to genuinely novel real-world prompts/distributions; the paper presents this as a strength (reduces teacher-data mismatch) without discussing potential downsides such as reduced robustness to distribution shift at serving time.
- **Ablation scale caveat (inferred)**: the MTP loss ablation (Table 1) is explicitly run on "a small-scale MoE target model," not the full Hy3-A21B used in headline results, so it's not fully verified that the same loss ranking (e2e TV + LK cold start best) holds at full target scale, though the paper does carry the chosen recipe forward without re-ablating at scale in the visible text.
