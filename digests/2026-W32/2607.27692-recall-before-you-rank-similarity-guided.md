# Recall Before You Rank: Similarity-Guided Top-$K$ Reuse for Efficient Long-Context Attention

**Authors:** Wenshuai Yao, Wenyong Zhou, Hanyong Shao, Yizhe Chen, Zhiyuan Ning, Yuannuo Feng, Ru Huang, Kechao Tang

**arXiv:** [2607.27692](https://arxiv.org/abs/2607.27692)

**Categories:** cs.CL, cs.LG

**Submitted:** 2026-07-30

**Relevance:** 9/10 — matched: LLM inference efficiency and long-context serving

---

## TL;DR
ReTopK speeds up Top-K sparse attention for long-context LLM decoding by reusing *which KV indices* were selected for past similar queries instead of rescoring the entire KV cache at every step. It maintains a small per-head cache of (query, selected-support) pairs, recalls supports from similar past queries, and reranks only that compact candidate set with exact current-query scores — falling back to full exact search when similarity is low. At 128K context with K=512, it matches Exact Top-K quality within 0.50% perplexity while running attention 3.07× faster.

## First-principles breakdown

**The problem.** In autoregressive LLM decoding, each new token's query must be compared against every key in the growing KV cache to compute attention. Top-K sparse attention tries to cut cost by only doing the expensive Softmax/weighted-sum step over the K highest-scoring keys instead of all of them. But there's a catch: to know *which* K keys are the highest-scoring, you still have to compute the query-key dot product score against *every* key in the cache and then do a global Top-K sort. That "selection" step itself is O(context length) — so as context grows to 64K–128K tokens, this selection step (not the final weighted sum) becomes the dominant cost (the paper shows it's 80-95%+ of latency at long contexts, Figure 1). Sparse attention sparsified the aggregation but not the search for what to aggregate.

**Why prior fixes fall short.** Two families of prior work exist:
1. *KV-cache eviction/streaming* (StreamingLLM, H2O): permanently discard old tokens, keeping only a fixed window/heavy-hitters. Cheap, but if a discarded token turns out to matter later, it's gone — bad for tasks needing distant retrieval (their NIAH scores collapse to ~3%).
2. *Query-aware approximate selection* (Quest, SparQ, Loki, TokenSelect): use cheaper proxies (compressed keys, low-rank projections, page-level bounds) to guess which keys matter for the current query, without touching the full cache. These still scale their search cost with context length, or in TokenSelect's case, only reuse for extremely similar consecutive queries with poor hit rates.

**The core observation that motivates ReTopK.** The authors measure, empirically, that queries which are cosine-similar to each other tend to select overlapping Top-K supports (sets of important key indices) — correlation ~0.70-0.73 between query similarity and support overlap. Crucially, even a single similar historical query's support only partially overlaps the true Top-K set, but *unioning* the supports from several (R) similar historical queries recovers most of the true Top-K "attention mass" (coverage rises from 60% with R=1 to 95% with R=32). This means: instead of computing scores against the whole KV cache to find the right K keys, you can look up what worked for similar past queries and only rescore that much smaller candidate pool.

**The mechanism, step by step.** For each attention head, ReTopK keeps a bounded FIFO cache of size C storing (normalized query vector, selected support indices) pairs from past decoding steps. At each new decoding step:
1. Compute cosine similarity between the current query and the C cached queries (cheap: O(C·d), not O(L·d)).
2. Retrieve the R most similar cached queries and take the union of their stored Top-K supports.
3. Add a small "recent window" of the last W tokens (so brand-new tokens that haven't yet appeared in any cached support are still eligible).
4. This union forms a compact candidate set of size M ≪ context length (bounded by R·K+W).
5. Compute *exact* current-query scores only for these M candidates (not the full cache), then take the exact Top-K within that candidate set. This reranking step means ReTopK never reuses stale scores/weights/outputs — only which indices are worth rescoring.
6. Do the standard Softmax-weighted value aggregation over this final K-index set — the actual output computation is fully exact given the (approximated) support set.

**Reliability safeguards.** Because reuse could drift or fail for atypical queries, two guardrails exist: (a) *similarity fallback* — if the best cached-query similarity falls below threshold τ, skip reuse entirely and do a full Exact Top-K step for that token; (b) *periodic refresh* — every Tr steps, force an exact step regardless, to prevent the cache from drifting away from ground truth over long generations. Both exact and reuse steps update the cache with their resulting support, keeping it current.

**Complexity.** Exact Top-K costs O(L·d) for scoring plus a sort over L. ReTopK's reuse path costs O(C·d) for cache matching + O(M·d) for candidate scoring, where M is bounded and independent of context length L — this is the whole point: selector cost stops growing with context.

## Key insights

- **Novel framing**: identifying that the *selection* step (not the final sparse aggregation) is the actual long-context bottleneck in Top-K attention, and that this cost is separable from — and can be attacked independently of — the aggregation cost. This is a reasonably clear-eyed diagnosis backed by their own latency breakdown (Figure 1).
- **Reuse without eviction**: unlike StreamingLLM/H2O-style methods, ReTopK keeps the *entire* KV cache available for retrieval — it only shortcuts the search, not the underlying data. This lets it retain access to far-away tokens that eviction methods lose, which is reflected in dramatically better NIAH long-range retrieval scores versus StreamingLLM (85-96% vs 2.5-3.8%).
- **What reuses vs. what stays exact matters**: the method reuses only *index selections* (which keys to look at), not scores, weights, or outputs — final attention computation is always exact over whatever candidate set is chosen. This bounds the quality degradation to a "support selection" approximation rather than compounding approximation errors through the whole attention computation.
- **Evidence supports the core efficiency/quality tradeoff claim**: at 128K/K=512, 3.07× speedup for 0.50% PPL increase, and results transfer with no retuning across three different model families/sizes (Qwen2.5-7B, Llama-3.1-8B, Qwen2.5-14B) with 82.5-89.6% reuse rate. The ablations (Table 3, Figure 7) show each component (similarity-guided retrieval vs. naive recency, multi-query union vs. single, fallback, recent-window) contributes measurably — this is solid support, not just a headline number.
- **Speedup increases with context length** (1.29× at 16K to 3.07× at 128K, and up to 3.73× at 5M in end-to-end tests) — this is the expected and desired scaling behavior since selector cost becomes context-independent while Exact Top-K's grows linearly; the trend is corroborated across multiple experiments (Table 1, Figure 9, Table 5), which is more convincing than a single number.

## Caveats — stated and inferred

- **Single GPU / single hardware setup** — all latency numbers are measured on NVIDIA L20 GPUs with the authors' own fused kernel implementation; no comparison of how baseline implementations were kernel-optimized (or not) relative to ReTopK's custom fused kernels. *(inferred — raises the question of whether speedup partly reflects implementation engineering effort rather than algorithmic advantage over equally-optimized baselines)*
- **Loki baseline handicapped**: the paper itself states Loki's rank=64 is "substantially below the 12.5–25% context-proportional budgets used in its paper," meaning its very poor scores (PPL of 61-199, near-zero NIAH) reflect a deliberately constrained configuration rather than the method's best-case performance. *(stated)*
- **Narrow benchmark/task selection**: LongBench evaluation uses only 3 of many available subsets (2WikiMQA, HotpotQA, MultiFieldQA), and PG19/NIAH are used for the other core metrics. No broader instruction-following, coding, or reasoning benchmarks are reported. *(inferred — the paper doesn't discuss whether results generalize beyond these QA/retrieval/LM-perplexity tasks)*
- **Model scale ceiling**: largest model tested is 14B parameters; no evaluation on larger (30B+/70B+) models where head/query dynamics might differ. *(inferred)*
- **Long-horizon stability tested only to 8K continuation**: the "long-horizon stability" experiment (Figure 8) evaluates drift only up to 8K tokens of continuation after a 64K prefill — not clear whether error accumulation stays bounded over much longer generation runs (e.g., 100K+ tokens of output), which matters for genuinely long agentic/generation workloads. *(inferred)*
- **Hyperparameters tuned on one model then "transferred"**: cross-model generalization reuses hyperparameters (C, W, R, τ, Tr) selected via ablation on Qwen2.5-7B; while described as a strength, it also means no evidence is given for whether per-model tuning could produce even better trade-offs, so the reported cross-model numbers may understate model-specific headroom or, conversely, could look worse with different tuning. *(inferred)*
- **No comparison against training-based or learned selection methods at parity** (e.g., SeerAttention, RetrievalAttention, Squeezed Attention, Kascade, IndexCache, PRR are cited in Related Work but not empirically compared in Table 1) — the empirical comparison set is limited to StreamingLLM, Quest, SparQ, Loki, TokenSelect. *(inferred — several directly relevant recent methods mentioned in related work are absent from experiments)*
- **Fallback/refresh overhead not fully decomposed for worst-case query distributions**: the method's efficiency depends on the reuse rate (82-90% in experiments); the paper doesn't address what happens for workloads with unusually low query self-similarity (e.g., highly diverse/randomized queries) beyond noting head-dependent variability (Figure 3). *(inferred, though the paper does acknowledge head-dependent reuse quality — stated)*
- **PPL/NIAH/LongBench as proxies for downstream utility**: no end-task or human-eval style evaluation (e.g., actual generation quality, downstream agent performance) is reported — all evaluation is intrinsic (perplexity) or benchmark QA accuracy. *(inferred)*
