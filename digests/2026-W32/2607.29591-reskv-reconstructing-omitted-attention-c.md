# ResKV: Reconstructing Omitted Attention Contributions for Fixed-Budget KV Cache Compression

**Authors:** Yuhang Zhan, Lisi Chen, Shuo Shang

**arXiv:** [2607.29591](https://arxiv.org/abs/2607.29591)

**Categories:** cs.CL

**Submitted:** 2026-07-31

**Relevance:** 9/10 — matched: LLM inference efficiency and long-context serving

---

## TL;DR
ResKV splits a fixed KV-cache budget into an exact "main cache" (top-scoring tokens) plus a compact "residual cache" that reconstructs the aggregate attention mass of the tokens that would otherwise be evicted, by treating that omitted contribution as residual numerator/denominator statistics inside the same softmax rather than deleting it or blending it into retained tokens. A construction-time validation proxy decides how much of the budget each layer/head should give to residuals, and a decode-time gate scales down residual influence when the main cache already produces a sharp attention peak. Across LongBench and RULER on two 7-8B backbones, adding ResKV to existing eviction baselines (SnapKV, AdaKV) improves accuracy in nearly all tested configurations at the same KV budget, with roughly stable memory/throughput overhead.

## First-principles breakdown

**The underlying problem.** Transformer decoding needs a KV cache — stored keys/values for every past token — so it doesn't recompute attention over the whole sequence at each new step. As context grows, this cache becomes the dominant memory/bandwidth cost, so systems compress it by keeping only a subset of tokens' KV pairs (a "budget" `b` out of `s` total tokens).

**Why prior compression fails, mathematically.** Attention output is a weighted average: `o = softmax(qK^T/√d) V`, which can be written as a fraction — a numerator (sum of `exp(logit)·value` over all tokens) divided by a denominator (sum of `exp(logit)` over all tokens), i.e. `o = N/Z`. 
- *Eviction* methods (H2O, SnapKV, AdaKV, TOVA, etc.) just pick a subset `M` of tokens to keep and throw away the rest (`E`). This literally deletes `E`'s contribution from both the numerator and denominator sums, then renormalizes over only `M`. Even if each dropped token individually has tiny attention weight, their *combined* mass can be large and important — especially for tasks needing evidence spread across many tokens (retrieval, aggregation).
- *Merging* methods (CaM, KVMerger, KeepKV) try to preserve that lost mass by folding evicted tokens' information into the retained ones. The problem: this corrupts the retained tokens — a key/value that's supposed to be an exact memory of one specific token now gets contaminated by unrelated merged content, hurting precise retrieval.

**The paper's core idea.** Instead of choosing "delete" or "merge," represent the omitted contribution *explicitly and separately* as its own small set of cache entries — a "residual." Formally, the residual is exactly the piece missing from eviction: `R(M;q) = (N_E(q), Z_E(q))` — the sums over the evicted set `E`. If you could re-add these sums to the main cache's numerator/denominator, you'd recover exact full attention. The catch: these sums depend on the future query `q` (via `exp(⟨q,k_p⟩)`), so they can't be precomputed and cached exactly — you don't know `q` at compression time.

**The mechanism, step by step:**
1. *Split the budget*: `b = m + r`. `m` slots go to an exact main cache `M` (selected via any existing importance-scoring method, e.g. SnapKV scores, plus a protected recent window). `r` slots go to a residual cache.
2. *Build residual entries*: Cluster the evicted tokens `E` into `r` groups (via a few Lloyd/k-means iterations in key space, since queries aren't known yet — nearby keys tend to produce similar attention logits). Each group stores one averaged key, one averaged value, and a count `c_j` of how many tokens it represents. This is a query-agnostic summary: at decode time, a group's contribution to attention is approximated as `count × exp(similarity of query to averaged key) × averaged value`, i.e. the count injects back the "mass" that would have come from many individual tokens.
3. *Shared-softmax decode*: Crucially, these residual entries aren't tacked on as a correction after the fact — they're added as extra terms directly into the same softmax normalization used by the main cache tokens (both numerator and denominator sums), so they behave like "fuzzy" attendable tokens rather than a side patch. When `r=0` this exactly reduces to plain eviction.
4. *Construction-time validation proxy*: Since the right split between exact tokens and residual slots is unknown in advance, ResKV tries a small grid of candidate `r` values after prefill, using held-out ("validation") queries carved out of the prompt itself to measure how well each candidate residual-augmented output matches full uncompressed attention. It only turns on residuals for a given layer/KV-head if they beat pure-eviction by a margin; otherwise it falls back to `r=0`. This makes the residual/main split adaptive per layer and per attention head.
5. *Decode-time dynamic gate*: At each decode step, a scalar gate down-weights residual logits when the main cache already shows a sharp (confident, peaked) attention distribution — because adding "average" residual mass there would just dilute a correct sharp retrieval — and allows more residual influence when main-cache attention is diffuse (spread thin, suggesting relevant info might be missing/omitted).

## Key insights

- **Genuinely new framing**: recasting "what eviction throws away" as literal residual terms in the softmax numerator/denominator, rather than as an ad hoc score-based heuristic. This is a clean mathematical decomposition (well-grounded, shown in the paper's derivation) rather than a new heuristic scoring rule — arguably the paper's main conceptual contribution.
- **Method is a plug-in, not a competitor**: ResKV wraps around existing eviction methods (SnapKV, AdaKV) rather than replacing their token-selection logic — it adds a residual channel on top, using the same importance scores. This means the claimed gains are incremental improvements to established baselines under the same total memory budget, not a new standalone SOTA method compared head-to-head against everything.
- **Adaptive components matter (per ablation)**: removing the validation proxy or the dynamic gate causes measurable score drops (e.g. -4 to -7 points on some tasks), and replacing shared softmax with separate normalization also hurts — supporting the claim that all three pieces (split, shared-softmax combination, adaptive gating) contribute, not just the residual idea alone.
- **Evidence supports broad improvement, especially at tight budgets and in "query-agnostic" (realistic, prefix-cache) settings**: the paper reports gains concentrated on tasks needing distributed evidence (retrieval, aggregation, code) and larger gains under tighter compression (10-20% retained) and when the cache is built without knowing the future query — plausibly because that's exactly where hard eviction loses the most aggregate mass.
- **Efficiency claim (memory/throughput near-parity with the baseline)** is supported by a specific figure comparing peak memory and decode throughput against SnapKV and the uncompressed full cache, showing the residual branch adds only moderate throughput cost, not by a comprehensive systems benchmark.

## Caveats — stated and inferred

- **Limited model/benchmark scope** (stated): the authors explicitly note evaluation is restricted to two instruction-tuned GQA backbones (LLaMA-3.1-8B, Qwen-2.5-7B) and two benchmarks (LongBench, RULER); they call for broader model/architecture/serving-workload coverage as future work.
- **No residual updates during generation** (stated): the residual cache is built once after prefill and not refreshed during long decoding/generation, so its benefit may degrade over very long generation runs — acknowledged as a limitation.
- **Residual summary richness is basic** (stated): only mean key/value/count summaries are used; the authors say richer summaries or specialized kernels could improve approximation/efficiency further, implying the current implementation is a first cut, not fully optimized.
- **Single seed, single hardware config** (inferred): experiments are run once with a fixed seed (42) on one A100 GPU; no variance/error bars are reported across runs, so the reported point-improvements' statistical robustness is unverified.
- **Baselines are moderately dated / narrow set** (inferred): comparisons are against H2O, SnapKV, TOVA, AdaKV, and CaM; more recent merging/reconstruction methods explicitly discussed in related work (KVMerger, KeepKV, SemantiCache, KVSculpt, RESA) are cited but not empirically compared against in the main results shown here (only CaM appears in one small task-level table), so the paper's "improves over representative baselines" claim rests on a subset of recent competing methods.
- **Reported RULER/LongBench "improves 63/64 or all 32 configs" is an average-level claim** (inferred as a framing caveat): the paper counts configurations where the ResKV-augmented variant beats its own baseline pairing, not a comparison against the strongest method in each row from a different baseline family — so "broad improvement" concerns each baseline in isolation with residual added, not an overall leaderboard win against all methods simultaneously.
- **No latency/throughput numbers under batching or multi-GPU/production serving conditions** (inferred): efficiency analysis (Figure 3 a/b) is limited to a single GPU and describes peak memory and decode throughput trends only qualitatively ("moderate cost," "overlaps with baseline") without exact numeric overhead percentages in the text provided.
- **Construction-time validation proxy adds prefill-time compute overhead** (inferred): trying multiple candidate residual budgets per layer/head via a grid search and computing validation loss against full attention is extra work at cache-construction time; the paper does not report this overhead's cost, only decode-time throughput.
- **Query-agnostic setting still uses in-prompt validation queries** (inferred nuance): the "query-agnostic" construction still relies on held-out queries drawn from the observation window itself (fit/validation split) to calibrate the proxy — not truly zero information about future query distribution — which is a reasonable design but the paper doesn't discuss how sensitive results are to how representative these internal validation queries are of actual downstream queries.
