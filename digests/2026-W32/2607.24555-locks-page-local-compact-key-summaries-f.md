# LOCKS: Page-Local Compact Key Summaries for Efficient Long-Context Decoding

**Authors:** Junsung Hwang

**arXiv:** [2607.24555](https://arxiv.org/abs/2607.24555)

**Categories:** cs.LG, cs.AI

**Submitted:** 2026-07-27

**Relevance:** 9/10 — matched: LLM inference efficiency and long-context serving

---

## TL;DR
LOCKS is a training-free plugin for vLLM that gives each 16-token page of a KV cache its own tiny spectral (eigenbasis) summary, letting the decoder rank which pages to attend to without ever reading the full cache. Because attention keys are locally low-rank within a page but globally high-rank across a sequence, a page-local rank-8 summary (~1/10th the page's bytes) tracks an "attend everything" oracle far more faithfully than shared/global summaries used by prior methods. This buys near-FullKV quality at aggressive sparsity (~2% of tokens attended) and 2x lower decode latency at 1M-token context.

## First-principles breakdown

**The problem.** When an LLM generates text with a huge context (say 100K+ tokens), each new token requires "attention" over every previously cached key/value pair. Serving systems store this KV cache in fixed-size chunks called "pages" (this is "PagedAttention," the vLLM mechanism). At long context, reading the *entire* KV cache at every single decode step becomes the bottleneck — not the model weights, not compute, but the sheer bandwidth of reading gigabytes of cached keys/values per token generated.

**Why sparsity helps, and what's exact vs. approximate.** Empirically (and provably here, via an exact mathematical identity credited to prior work), only a handful of "pages" carry almost all of the attention probability mass for any given query. If you could magically know which pages matter, you could skip reading the rest and only suffer error proportional to the *value* difference between kept and dropped tokens. The catch: computing the *exact* attention mass per page requires reading every key anyway — which defeats the purpose. So you need a cheap, resident "summary" of each page that lets you *estimate* which pages matter without reading the real keys.

**Why prior summaries fail.** Existing approaches store per-page summaries at the wrong "scope":
- *Envelopes* (e.g., Quest) store just min/max per dimension — coarse, so they preserve gross attention mass share but lose track of specific "carrier" pages that hold the actual answer (important for niche retrieval tasks).
- *Block moments* (e.g., COBS) store a mean and a covariance-like spread — this is exact only if the page's keys were Gaussian-distributed, but real "carrier" tokens are peaky/high-dynamic-range, which moments handle poorly.
- *Shared/global bases* (Loki, ShadowKV) fit **one** low-rank projection across an entire sequence or the whole cache. The paper proves (Proposition 1) this is structurally blind: any content variation orthogonal to the fixed shared projection is literally invisible to the scoring function, no matter how much you scale it up. This isn't a fixable-by-more-rank problem — it's a scope problem.

**LOCKS's mechanism.** Instead of sharing structure across pages, LOCKS fits a *separate*, tiny eigendecomposition to each page's own keys:
1. When a page (16 tokens) is finalized, center its keys around their mean, compute the small Gram matrix of deviations, and eigendecompose it (fast — the matrix is only 16x16).
2. Keep the top r=8 eigenvectors ("basis") and each token's coefficients in this basis, quantized to int4 (basis) and int8 (coefficients/centroid) — about a tenth of the page's original KV bytes.
3. At decode time, for each candidate page, reconstruct approximate per-token attention logits from just this compact summary (query dotted with reconstructed keys), then reduce them with log-sum-exp to estimate the page's total attention mass — this recovers the same "exact mass" quantity that would otherwise require reading real keys.
4. Rank pages by this estimated mass and attend only the top-k (a fixed per-head token budget, e.g. 2048 tokens), plus always-kept sink/recent pages.
5. Since models use grouped-query attention (multiple query heads sharing one KV head), LOCKS averages each query's page-mass share across the group ("share-average") to produce one shared selection table for the whole group — proven to maximize group-average coverage among such shared rules.

The whole thing is implemented as a fixed-shape kernel (rank, page size, budget are all constants), so it can run inside CUDA graphs — important for actually getting the latency win in a real server rather than just in theory.

**The theoretical chain.** The paper is explicit about a causal chain it claims to validate end-to-end: page-local spectral concentration (keys within a page really do cluster in a low-dim subspace) → this makes per-token logits reconstructed accurately → which makes the log-sum-exp mass ranking accurate → which makes "carrier" pages (containing the actual needed info) survive selection → which makes downstream task quality hold → which translates into real serving speedups. Theorem 1 formally bounds attention-output error as a function of reconstruction error, but only for the *unquantized* version of the summary; the actually-shipped int4/int8 version is only validated empirically, not bounded.

## Key insights

- **Genuinely new**: the "locality thesis" itself — showing structurally (Prop. 1) and empirically that page-scope representations are qualitatively different from (not just quantitatively better than) sequence- or cache-scope shared bases for this task, and that increasing the shared basis's rank/bytes to match LOCKS's budget still doesn't close the gap (Table D.15). This reframes the KV-selection design space around "what scope stores structure" rather than "how big is the summary."
- **Genuinely new**: a training-free, exact-LSE-target reconstruction from a page-local basis, versus prior work that either trains a surrogate (HiLS) or uses coarser handcrafted statistics (envelopes, moments).
- **Supported by evidence**: quality tracking the "read-every-key" oracle down to very small budgets on RULER and long-document QA, and notably large margins over baseline selectors specifically on long-form reasoning tasks (AIME26, MATH-500) where the working set the model must retain is roughly fixed-size rather than a small fraction of context — this is where baselines "collapse" per the paper's own figures.
- **Supported by evidence**: measured 2x per-token decode latency reduction at 1M context and up to 9.8x fewer bytes read per step, plus scaling benefits under batching, on real H200 hardware inside vLLM (not just simulated).
- **Claimed but more limited**: "matches FullKV aggregate quality at 100K+ context" — true for the specific InfiniteBench aggregate reported (Table 1), but this is an average across task categories; per-task variation exists (see caveats).
- The optimality claims (mass-ranking is minimax-optimal, the local basis is residual-optimal) are explicitly scoped by the authors to specific rule classes (deterministic value-blind selectors; orthogonal rank-r per-page linear reconstructions) — not universal optimality claims, and the paper is careful to say so itself.

## Caveats — stated and inferred

- **Quantized summary is unbounded, only measured** (stated): Theorem 1's formal retention/error guarantee applies to the unquantized (bf16) basis. The actually-deployed int4/int8 summary's error is "measured rather than bounded," described as "roughly double the unquantized error at matched percentiles, and heavy-tailed at the extremes." This means the shipped product's worst-case behavior has no formal guarantee.
- **Fixed, small page size** (stated): page size is fixed at 16 tokens; the authors call this a limitation and don't explore sensitivity broadly beyond the ablation grid.
- **No offloading/tiering** (stated): LOCKS reduces read bandwidth but keeps the *full* KV cache resident in memory — it does not address memory capacity, which the authors explicitly flag as future work.
- **Limited record counts for "microscope" analysis** (stated): the fine-grained page-level fidelity measurements (App. B) use "a small number of records per model, characterizing the estimator in depth rather than establishing coverage across tasks and models."
- **Author-affiliated/self-reported experiments, single-author paper** (inferred): the paper has one listed author (Junsung Hwang) and is very recent (July 2026, arXiv). No independent replication is referenced; claims should be weighed accordingly.
- **Cherry-pickable framing of "about a point" and "2%"** (inferred): headline efficiency/quality numbers ("within about a point," "attending about 2% of tokens," "2.0x at 1M tokens") are drawn from specific operating points (e.g., the shipped 2048-token budget at 100K+ context); the fuller tables show gaps that vary by task and budget (e.g., Table 1 shows LOCKS trailing the exact-LSE oracle and sometimes underperforming at b=512 on LongQA vs. b=2048), so the single-number headline elides this variation.
- **Comparison baselines' "native budget semantics" differ** (stated in App. C.1, referenced in main text): the x-axis "per-head budget" in figures is a "common nominal budget," but "native budget semantics and measured traffic and residency differ across methods" — meaning the plotted comparisons might not be perfectly apples-to-apples across selectors without consulting the audit in the appendix.
- **Hardware/software specificity** (inferred): all efficiency numbers are measured on a single H200 NVL node with a specific pinned software stack (vLLM 0.24, CUDA 13.0, PyTorch 2.11); generalization to other accelerators/stacks is not addressed in the paper.
- **Batched decode speedup has an OOM ceiling** (stated via Table 2): at high context and high batch size combinations, both the dense baseline and LOCKS run out of memory (marked OOM), meaning the reported "grows with batch size" trend is only demonstrated up to the point memory allows, not further.
- **Coverage vs. correctness distinction** (inferred from Lemma 1 discussion): the paper is explicit that retained "mass" is not the same as retaining the specific "carrier" token that decides an answer — average-case mass metrics can look good while missing the one token that matters. This is a real methodological strength the authors highlight, but it also means any metric not specifically checking carrier-recall (only some benchmarks do, per Fig. 1b) could still mask failures on other tasks not analyzed this way.
- **"Nominally matches or exceeds" FullKV on AIME26** (stated, but worth flagging): the paper's own wording ("nominally") suggests this specific result may be within noise/variance rather than a robust win, especially given math benchmarks are typically high-variance across seeds and the paper doesn't report variance for this specific claim in the excerpt provided.
