# Replay Pruning and Few-Bit Integer Inference for Hardware-Efficient Speed-Sign Recognition

**Authors:** Se Un Park, Kyungkeon Chung, Huigeol Kim, Junyoung Park

**arXiv:** [2610.22811](https://arxiv.org/abs/2610.22811)

**Categories:** cs.CV, cs.AR, cs.LG

**Submitted:** 2026-10-16

**Relevance:** 6/10 — matched: Onboard object detection from a moving UAV

---

## TL;DR
This paper compresses a two-stage automotive speed-sign recognizer for SoC deployment: a pruning method called "channel replay" cuts a YOLOv5n detector's parameters by 60.3% at no accuracy loss by applying channel-deletion decisions (found via iterative pruning) back onto the original trained weights rather than keeping the iteratively-pruned weights themselves. A tiny 18k-parameter CNN classifier ("reader") is quantized to 4-bit weights/8-bit activations (W4A8) and verified bit-exact against an executable integer reference model, and the whole pipeline (detector + reader, all integer arithmetic) runs at 94 fps on a Jetson AGX Orin, recognizing 95.2% of signs at 90% precision using only public training data.

## First-principles breakdown

**The problem.** A camera SoC in a car needs to find speed-limit signs in a video frame and read the number off them, within tight memory/compute/energy budgets. Doing this in one shot with a single detector-classifier network is wasteful because the task naturally splits into (a) cheap, coarse localization of "is there a sign here" over a whole frame, and (b) fine-grained classification of a small cropped patch into one of 15 number classes. The paper's "two-stage recognizer" exploits this: a YOLO-style detector finds candidate sign boxes (treating all signs as one class), crops and resizes a square region around each box to 48×48, then a separate small classifier ("the reader") decides the actual speed value.

**Why standard YOLO ops are a problem for hardware.** YOLOv5n/v8n use SiLU activations (x·sigmoid(x)) and sigmoid in the detection head. Both need lookup tables or polynomial approximations to implement in low-precision/integer hardware — expensive on an accelerator with limited arithmetic. The authors replace SiLU with ReLU (max(0,x)) and sigmoid with "hard sigmoid" (a clipped linear function: min(max(x/6+1/2,0),1)). Both replacements are piecewise-linear, meaning they can be computed with only comparisons/adds/shifts — no transcendental functions. This "operator conversion" costs a small accuracy hit (1.2 mAP50 points on public data) but is a precondition for running efficiently on the DLA (a fixed-function low-power accelerator) — the original SiLU network runs 2.8x slower there.

**Structured pruning background.** Pruning removes whole channels (not just individual weights) from a trained network so that the remaining computation is still dense and regular (this matters for actual speedup on accelerators, vs. unstructured sparsity which often doesn't speed up hardware). "Taylor importance" ranks channels by how much removing them would change the loss (first-order Taylor approximation). A "dependency graph" tracks which channels in different layers must be removed together (e.g., due to skip connections) so the network stays structurally valid. Prior work found two competing claims: (1) pruning is "just a hyperparameter search for a good smaller architecture," and training that smaller architecture from scratch is just as good (so the pruning process itself is just an expensive architecture-search); (2) which weights you start finetuning from after pruning matters a lot (so starting from the parent's trained weights vs. random weights matters, like the "lottery ticket"/"weight rewinding" line of work).

**The paper's core method — "channel replay."** Rather than just iteratively pruning and fine-tuning the network as you go (which is standard iterative pruning), or pruning once and fine-tuning ("one-shot"), or training the pruned architecture from scratch, the authors:
1. Run standard iterative pruning (6 steps, Taylor importance, dependency-graph-aware, with KD recovery between steps) purely to *decide which channels to remove* — they record this cascade of deletions but throw away the resulting weights.
2. "Replay" those exact same deletions onto the original, fully task-trained parent network (not an earlier checkpoint, as in weight-rewinding — the final trained weights of the surviving channels).
3. Do one continuous knowledge-distillation (KD) recovery pass (174 epochs) from the full parent as teacher.

This separates two variables that are normally entangled in standard pruning: (a) which channels to remove (a search/architecture problem) and (b) which weights to start recovery from (an optimization problem). The paper's "per-step replay" variant changes how channels are *selected*: at each step, instead of ranking channels on the partially-pruned/retrained iterative model, it re-applies deletions-so-far to the original parent, retrains, and ranks the next channels from there — so channel importance is never estimated on weights that have already been retrained away from the original task optimum.

**Quantization background.** Quantization reduces numeric precision of weights/activations from 32-bit floats to few-bit integers to shrink memory and let hardware use cheap integer ALUs instead of floating-point units. "Symmetric per-channel" weight quantization uses one scale factor per output channel (reduces error vs. a single global scale). Post-training quantization (PTQ) just picks scale ranges after training (here via minimizing mean-squared quantization error over calibration data); quantization-aware training (QAT) simulates quantization during training (with a "straight-through estimator" to let gradients flow through the non-differentiable rounding) so the network adapts to the precision loss. The paper separately varies weight bits (W) and activation bits (A) and finds accuracy degrades non-uniformly — activations tolerate fewer bits better than weights at the low end, and below ~3-4 bits weights need QAT to recover.

**Integer-only pipeline.** Beyond the network itself, the authors also make every post-processing step (box score thresholding, IoU computation in NMS, box decoding) integer/division-free — e.g., applying the score threshold to the pre-sigmoid logit instead of computing a sigmoid, and cross-multiplying instead of dividing for IoU. They also had to replace YOLOv8's "distribution-focal" box head (which decodes each box side as a softmax-weighted average over 16 bins — needs exponentials and division) with a direct regression head, since naively taking the most-likely bin instead destroys accuracy (boxes snap to grid cells, duplicate detections survive NMS).

**Verification via an executable reference model.** To make sure the deployed integer math actually behaves as designed (not just "close enough" in simulation), they wrote a standalone Python model that computes with INT32 accumulators and streams the image row-by-row using 3-row line buffers (mimicking how a real streaming hardware circuit beside the image sensor would need to operate with no full-frame memory), and checked it reproduces identical class predictions to the real deployed runtime on all 9,850 test crops.

**Hardware deployment measurement.** The authors benchmark on a real Jetson AGX Orin across FP16, two different ways TensorRT implements INT8 (explicit: quantize/dequantize nodes inserted in the computation graph; implicit: using precomputed calibration ranges without graph nodes), and the DLA (a separate fixed-function low-power accelerator chip beside the GPU). This matters because, counterintuitively, lower bit-width or fewer FLOPs doesn't automatically mean faster or lower energy — actual measured latency depends heavily on how the inference engine is structured.

## Key insights

- **Claimed and supported:** Channel replay outperforms standard iterative pruning, one-shot pruning, and training-from-scratch baselines in matched 5-seed comparisons on YOLOv5n validation mAP50-95, and outperforms all compared methods (including the unpruned parent) on YOLOv8n. This is a real, controlled comparison (same parent, teacher, data, recovery budget) with paired statistical tests, which is methodologically more rigorous than many pruning papers.
- **Claimed and supported with nuance:** The paper explicitly disentangles two confounded variables in pruning literature — "what weights you recover from" vs. "which channels you select" — via the replay/per-step-replay/one-shot/scratch 4-way comparison. This is a genuine conceptual contribution, not just an engineering trick, though the end-to-end (detector+reader) differences between replay, per-step replay, iterative, and one-shot are *not* statistically significant on YOLOv5n (only the YOLOv8n shows a significant end-to-end gap vs iterative pruning).
- **Claimed and supported:** W4A8 reader matches FP32 accuracy at 12.1 KB (58% of W8A8 memory), and the bit-exact integer reference model reproduces INT8 predictions on all 9,850 test crops (not just "high correlation" — exact match), which is a meaningfully strong verification claim for a hardware-deployment paper.
- **Claimed and supported, and non-obvious:** INT8 is only faster than FP16 in TensorRT's "implicit" quantization formulation, not the "explicit" one — a concrete, actionable, non-intuitive empirical finding about deployment tooling that operation-count-based intuition would miss. Similarly, the DLA is fastest for the small YOLOv5n but *slower* than the GPU's implicit-INT8 engine for the larger YOLOv8n — accelerator choice isn't one-size-fits-all.
- **Honest about a negative/mixed result:** Replay's difference from one-shot pruning is not statistically significant in several comparisons (p=0.28, p=0.18), so the paper doesn't oversell replay as strictly dominant — it's presented as "best or tied-best," which is a more defensible claim than the abstract's framing might suggest at first glance.

## Caveats — stated and inferred

- **Single dataset domain, single country (stated):** "All tests use Korean speed signs." Generalization to other countries' sign designs/fonts is untested.
- **Close-up/large-sign performance is poor and inconsistent (stated):** On close-up signs the converted YOLOv5n detects "poorly and inconsistently" (AP50 86.6 vs 97.3 for unconverted network), and compressed models show very high seed-to-seed variance (9–33 points) in this regime — a real robustness gap the authors flag rather than hide.
- **Energy/latency measurements limited to one board, one setting (stated):** Device measurements use "one board in its 30W mode," only "one seed for the DLA and implicit-INT8 accuracies of the YOLOv8n," and energy measurement excludes memory rail, carrier board, and AC-input supply losses — so energy comparisons are narrower than they might appear and partly single-sample (not averaged over seeds) for YOLOv8n.
- **End-to-end pruning-method differences often not significant (inferred from data, softly acknowledged in text):** On YOLOv5n, "no pair among replay, per-step replay, iterative pruning, and one-shot pruning is separated at p<0.05 in mAP50 or Recognized." The strong claims of replay's superiority hold at the detector-only validation-mAP level, but the practically relevant end-to-end metric shows much weaker separation — a reader should weight the abstract's "outperforms" claims accordingly.
- **Merged single-network baseline may be a weak/unfair comparison (inferred):** The "merged recognizer" (single YOLOv8n doing both localization and classification) scores drastically lower (38.8/7.7 mAP50/Recognized) than the two-stage approach, but the authors themselves note this may be partly an artifact of running at lower input resolution (performance jumps to 73.2/64.4 at 1280px) rather than a fundamentally weaker architecture — so this comparison, used to justify the two-stage design, is somewhat confounded and the authors flag it themselves (stated).
- **No ablation isolating ReLU/hard-sigmoid conversion from pruning gains beyond mAP cost reporting (inferred):** The conversion's accuracy cost (1.2 mAP50 points on public, 0.5 on held-out camera) is reported, but there's no deeper ablation on whether other activation choices might recover more accuracy while keeping hardware-friendliness — not addressed in the paper.
- **Minimum-speed sign classes effectively untrained (stated):** "The public sets hold no Korean minimum-speed signs, so the reader's minimum-limit classes are untrained," and this is listed as future work ("train the minimum-speed classes"), meaning current minimum-speed recognition relies on a workaround (reading by number) rather than a trained class.
- **No RTL/real circuit implementation yet (stated):** The "integer reference model" demonstrates bit-exact feasibility in software, but actual hardware circuit implementation of the streaming reader is explicitly future work ("implement the reader in RTL"), so hardware-efficiency claims for the reader are validated at the algorithmic/simulation level, not in silicon — this is effectively a simulation-only evaluation for the streaming hardware architecture itself (inferred/stated combination).
- **Baselines for pruning are reasonably current but not exhaustive (inferred):** Comparisons are against iterative pruning, one-shot pruning, and from-scratch training — all using the same Taylor-importance/dependency-graph framework as the proposed method. No comparison to other pruning criteria (e.g., magnitude-based, lottery-ticket-style rewinding at intermediate checkpoints) is reported, so the generality of channel replay's advantage across different pruning criteria is not addressed in the paper.
