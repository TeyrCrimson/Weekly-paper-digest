# SkyAgent: Revisable Target Memory for Continuous Aerial Search

**Authors:** Kaibo Yang, Xingyu Wu, Enze Zhu, Yajie Chai, Xuyang Li, Jiahui Cui, Xiaoxuan Liu, Lei Wang, Zhan Chen

**arXiv:** [2610.23293](https://arxiv.org/abs/2610.23293)

**Categories:** cs.RO

**Submitted:** 2026-10-16

**Relevance:** 7/10 — matched: Onboard object detection from a moving UAV

---

## TL;DR
SkyAgent tackles "false candidate persistence" (FCP) in continuous aerial search — the failure where a drone keeps chasing a target hypothesis that later evidence has already disproven. Its fix, Revisable Target Memory (RTM), tags every candidate with a lifecycle state (Tentative/Confirmed/Rejected) and binds every planned waypoint to the candidate that spawned it, so rejecting a candidate instantly cancels its pending goals. Across three aerial-navigation benchmarks and 35 matched real DJI flights, RTM raises success rate by ~3–6 points while cutting FCP-driven wasted travel substantially, with a low false-rejection rate.

## First-principles breakdown

**The problem.** A drone searching for a target (e.g., "find the red truck") builds up belief about candidate objects from a stream of images taken from different positions and angles. A single glance is often ambiguous (a facade might look like the target from one angle), so systems accumulate evidence over time into persistent "candidate" records rather than trusting any one frame. The issue: once a candidate is written into memory and a waypoint is queued to go inspect/approach it, most existing systems never actually *retract* that candidate even after a later, clearly contradicting view comes in (e.g., a side angle reveals it's just a reflection). The stale candidate sits in the planner's active set and keeps triggering detours, revisits, or "confirmation" actions — wasting flight time and distance. The authors name this **false candidate persistence (FCP)**, and distinguish two levels: *State-FCP* (the candidate remains in the planner's active set after it's been disproven) and *Behavior-FCP* (the drone actually takes an action — approach/revisit/confirm — toward it). This is not a one-off perception error; it's a multi-step trajectory failure caused by memory that only ever appends, never revises.

**Why prior approaches fall short.** The paper groups existing work into two camps: (1) memory-based methods (asynchronous maps, octrees, filtered writes) that focus on *storing* more observations, and (2) verification-based methods that check or reconsider the *next* single action before executing it. Neither camp handles what happens to *already-queued* actions/waypoints once a candidate is proven wrong — they look forward (build confidence before acting) but don't look backward (retract commitments after disproof). So a candidate can be individually "reconsidered" for the next step while three other waypoints already in the queue, sourced from the same now-disproven candidate, are untouched and still get executed.

**The mechanism — Revisable Target Memory (RTM).** RTM has two parts:

1. **Candidate Evidence Memory.** Each incoming observation is matched to an existing persistent candidate (or spawns a new one) using a weighted similarity score combining spatial proximity, visual-feature similarity, and temporal recency. Crucially, observations are grouped into "independent viewpoint groups" (based on bearing/range/altitude/time deltas) so that just hovering and capturing many near-identical frames of a false target doesn't artificially inflate its confidence — each group contributes one bounded, quality-weighted vote, not N votes. A frozen pretrained model converts each observation into signed evidence (+1 support, -1 contradict), which updates a bounded running belief score per candidate.

2. **Revise-and-Suppress.** The belief score, combined with the *current* lifecycle state (not just the raw score), drives state transitions via a hysteresis-based rule: a candidate becomes Confirmed if belief crosses a high threshold, Rejected if it drops below a low threshold, and a Rejected candidate can only return to Tentative (not immediately Confirmed) if enough new *independent* positive viewpoint groups accumulate after rejection — guarding against both premature permanent rejection (e.g., from temporary occlusion) and against trivial score flicker reactivating a false target. The critical interface: **every waypoint is tagged at creation time with the candidate ID that generated it.** The instant a candidate transitions to Rejected, every pending/unexecuted waypoint carrying that ID is cancelled before the next planning cycle — this is the mechanism that actually stops the drone from flying toward a disproven target, which simple "re-score and replan the next action" approaches don't do. The underlying flight stack (search policy, event triggers, inspection skills, safety controller) is unchanged; RTM only governs which candidates the planner is allowed to see and act on.

## Key insights

- **Genuinely new framing**: naming and formally measuring FCP as a distinct, trajectory-level failure (vs. single-frame detection error), with explicit State-FCP/Behavior-FCP/Waste/false-rejection-rate/recovery metrics. This gives a vocabulary and measurement protocol that prior memory/verification papers lacked.
- **Genuinely new mechanism**: the waypoint-to-candidate binding + cancellation-on-rejection is the specific novel contribution, not just "add a rejected state." The ablations support this directly — their "verify current action" baseline (effectively what prior verification-based methods do) and "revision state only" (state change without goal cancellation) both leave meaningfully higher BFCPR/Waste than Full RTM, isolating that the *propagation of rejection into the goal queue* is what drives the improvement, not merely having a better belief/state model.
- **Evidence supports**: consistent SR gains (2.90–6.31 pts) and large relative BFCPR/Waste reductions across three simulated benchmarks (CityAVOS, UAV-ON, OpenUAV) and a real-flight DJI test with 35 matched scenarios per method — this is a reasonably broad evaluation for a systems paper and includes a physical deployment check, which is above average rigor for this kind of work.
- **Claimed vs. supported**: the paper explicitly does NOT claim Equation 6's evidence accumulation is a calibrated Bayesian posterior — it's described as "an interpretable evidence accumulator," a fair and self-limiting claim. The paper also appropriately caveats that cross-view association (candidate tracking) remains the dominant residual bottleneck — the oracle-association ablation shows a further jump to 42.11% SR / 8.82% BFCPR, meaning a decent chunk of remaining error is a tracking problem, not a revision-logic problem, and RTM's reported gains are therefore a partial fix bounded by underlying perception/association quality.

## Caveats — stated and inferred

- **Reliance on reliable cross-view association** (stated): RTM assumes candidates are correctly tracked across views; merging or splitting candidate identities would distort the FCP counts and corrupt the mechanism. The gap between Full RTM and "Full + oracle association" (40.26% vs 42.11% SR, 15.27% vs 8.82% BFCPR) shows association errors are a real, non-trivial remaining source of failure.
- **Confound between route changes and revision mechanism** (stated): because RTM changes trajectories, which then changes what the drone subsequently observes, closed-loop results measure whole-system behavior, not revision in isolation; the authors say "common-trajectory replay is needed to isolate revision" — i.e., they acknowledge they have not isolated the mechanism's effect from its downstream exploration side-effects.
- **Threshold recalibration needed for new sensors** (stated): thresholds (τ_pos, τ_neg, τ_react, etc.) are calibrated on CityAVOS-specific held-out episodes; the authors note cameras/altitudes outside this calibration may need retuning, implying generalization beyond the tested settings is unverified.
- **Scope limited to static targets, no safety guarantee** (stated): the method and evaluation only cover physically static objects, and the authors explicitly say the real flights "do not establish a general safety guarantee."
- **Frozen evidence/match model may carry systematic bias** (stated): the signed-evidence model h_φ is a frozen, separately calibrated component; the authors flag that it "may retain systematic biases" that RTM's lifecycle logic cannot correct for.
- **Baseline comparability concerns** (inferred): in Table 1, many external competitor numbers (SR, Eff.) are "reported by the cited papers" under possibly different perception front ends, while SkyAgent's own Dist. numbers come from the authors' own reproduction — this is a stated caveat in the table note but it's a meaningful comparability red flag: the headline SR gains are partly comparisons against numbers generated by different pipelines, not a fully controlled ablation against identical perception stacks (the clean comparison is really Append-only SkyAgent vs. SkyAgent+RTM, which is internally controlled).
- **Small real-world sample size** (inferred): the physical validation uses 35 matched scenarios per method (140 trials total across 4 methods) — informative as a sanity check but a modest N for strong generalization claims about "physical deployment conditions," especially with percentage metrics like FRR computed over such a small base.
- **No discussion of computational/latency overhead of RTM's added bookkeeping** (inferred/missing): the paper reports "revision latency" in steps/seconds for the mechanism but doesn't address broader compute/memory cost of maintaining per-candidate evidence stores, viewpoint grouping, and association search at scale — not addressed in the paper.
- **Hyperparameter sensitivity not explored** (inferred): the lifecycle depends on several hand-set thresholds and hysteresis margins (τ_pos, τ_neg, δ_hyst, τ_react, n_react) calibrated on disjoint episodes, but no sensitivity analysis or robustness check across different threshold settings is presented — not addressed in the paper.
