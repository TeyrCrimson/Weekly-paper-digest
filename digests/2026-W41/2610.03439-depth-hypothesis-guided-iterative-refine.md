# Depth Hypothesis Guided Iterative Refinement for Event-Image Monocular Depth Estimation

**Authors:** Daikun Liu, Teng Wang, Changyin Sun

**arXiv:** [2610.03439](https://arxiv.org/abs/2610.03439)

**Categories:** cs.CV

**Submitted:** 2026-10-02

**Relevance:** 6/10 — matched: Metric and temporally-consistent monocular depth

---

## TL;DR
HypoDepth reframes event-image monocular depth estimation as an iterative "depth search" rather than direct regression: it discretizes depth into a learned hypothesis volume, builds a RAFT-style 3D cost volume between this volume and fused image/event features, and refines depth residually across resolutions via a GRU. It reports state-of-the-art accuracy on DSEC and MVSEC with strong zero-shot transfer, and a "tiny" variant that runs in real time on resource-limited hardware.

## First-principles breakdown

**The problem.** Monocular depth estimation (MDE) infers a per-pixel distance map from a single viewpoint — inherently ill-posed since one 2D image is consistent with infinitely many 3D scenes. Standard image-based MDE networks fail under motion blur or poor lighting. Event cameras (sensors that asynchronously report per-pixel brightness changes with microsecond latency and high dynamic range) can fill in those gaps, since they keep working during fast motion or in low light. But event cameras only report *change*, so they're blind in static regions — hence the push to fuse events with conventional images.

**Why prior fusion methods plateau.** Existing event+image MDE methods (RAMNet, UniCT, SRFNet, PCDepth) focus almost entirely on *how to merge the two modalities' features* (RNNs, self-attention, iterative feature fusion). But after fusion, they still ask the network to directly regress a continuous depth value per pixel in one shot (or via feature-level iteration) — a highly nonlinear mapping that's hard to learn reliably, regardless of how good the fused features are.

**The paper's reframing: regression → search.** The key idea, borrowed conceptually from optical flow (RAFT) and stereo matching, is: instead of asking the network "what is the depth," ask it "which of these candidate depths is most consistent with the evidence, and how do I nudge toward it." RAFT does this for optical flow by building a 4D cost volume (over all pixel-pair correspondences between two frames) and iteratively refining a flow estimate with GRU updates. HypoDepth adapts this to the single-image depth case, where there's no second viewpoint to correlate against — so it invents one:

1. **Depth Hypothesis Volume (DHV):** For each pixel, uniformly sample D candidate depth values within a scene-appropriate range `[d_min, d_max]` (converted to normalized log-depth for numerical stability). Embed these discrete depth candidates into a feature space via a learned projection — producing a small set of "virtual depth feature vectors" that don't depend on image content.

2. **3D cost volume:** Run bidirectional cross-attention between the DHV embeddings and the real contextual (image+event fused) features, so each side becomes aware of the other, then take the dot-product similarity between every pixel's context feature and every one of the D depth-hypothesis embeddings. This produces an H×W×D "cost volume" — essentially a per-pixel score for "how well does this pixel's observed appearance match depth hypothesis i." This substitutes for RAFT's cross-frame correspondence volume, using depth hypotheses instead of a second image.

3. **Correlation lookup (local search):** Rather than reasoning over the whole D-dimensional cost volume every iteration, it takes the previous iteration's estimated depth, finds the closest DHV candidate index, and looks up a small window (`radius r`) around that index — a local search, like RAFT's spatial neighborhood lookup but along the depth axis. This is pooled at multiple scales (different D's per resolution) so both coarse/global and fine/local depth cues are captured cheaply (since D ≪ H×W, this stays lightweight).

4. **GRU-based residual update:** The local correlation features, combined with the fused context features, feed a convolutional GRU that predicts a depth *residual* to add to the previous estimate. This is repeated for several iterations per resolution level, then the whole process is repeated coarse-to-fine across 1/16 → 1/8 → 1/4 resolution, each stage refining what the previous stage produced (and convex upsampling, also from RAFT, projects estimates back to full resolution).

**Supporting architecture.** A Swin-Transformer backbone (separate, non-weight-shared encoders for image and event-voxel-grid inputs) extracts multi-resolution features. Fusion ("EIFusion") uses cross-attention at coarse resolutions (global semantic alignment) and convolution at fine resolution (cheaper, local detail fusion) — a resolution-adaptive design rather than one fusion mechanism everywhere. Events are converted into a multi-bin voxel grid (a common image-like representation of asynchronous event streams) so they can be processed by standard CNN/Transformer encoders. Training uses a scale-invariant log loss (from Eigen et al.) with iteration-weighted supervision, consistent with RAFT-derived training recipes.

**Why discretization helps despite seeming like a step backward.** Continuous residual regression tends to accumulate drift over iterations when the starting point is noisy. Constraining updates to be "find the nearest of D plausible candidates, then do local correlation search around it" bounds the search space and acts as a regularizer — the ablation ("w/o DHV," replacing the discrete volume with sampling around the raw continuous previous estimate) empirically supports this, showing worse accuracy without discretization.

## Key insights

- **Genuinely new framing (claimed and evidenced):** applying a RAFT-style discrete cost-volume/iterative-refinement scheme to single-image (not stereo/multi-view) depth by synthesizing a "virtual correspondence" axis (the DHV) rather than relying on a second camera view. The ablations (`W/o DHV`, `W/o multi-scale in lookup`, varying D, varying radius) each show consistent degradation when removed, lending some support to the mechanism's necessity rather than just being an architecture change that works for unrelated reasons.
- **Modularity / portability:** plugging the same iterative-refinement decoder onto an existing method's fused features (PCDepth-Ours) yields further gains over both HypoDepth-alone and PCDepth-alone, suggesting the refinement mechanism is complementary to (not just competitive with) feature-fusion-centric approaches. This is reasonably good evidence the gains come from the depth-search mechanism specifically, not merely from a better backbone/fusion module.
- **Efficiency claim is substantiated by direct comparison:** the lightweight 3D cost volume (depth dimension D ≪ H×W) keeps compute low enough to run iterative refinement at multiple resolutions, and the "tiny" variant lands favorably on the accuracy/inference-time/Param Pareto frontier (Fig. 6) versus faster-but-less-accurate baselines (E2Depth, DepthAnyEvent) and more accurate-but-slower ones (PCDepth).
- **Zero-shot generalization:** pretraining once on synthetic EventScape and transferring to DSEC/MVSEC without fine-tuning beats reproduced baselines (EReFormer-C, PCDepth) under identical protocol — a reasonably controlled generalization test since all compared methods share the same pretraining-then-transfer setup.
- Distinguishing claim vs. evidence: the paper claims the DHV "mitigates the impact of prediction noise" and "enables stable residual optimization" — this is argued conceptually and supported indirectly via the ablation, but no direct quantitative noise-robustness experiment (e.g., deliberately injecting noisy priors and measuring convergence) is shown.

## Caveats — stated and inferred

- **Known failure mode under weak parallax / low texture (stated):** the paper explicitly shows a failure case (Fig. 10) where non-forward camera motion yields weak parallax and events provide limited structure, and textureless regions (roads, facades) produce ambiguous cost volumes — refinement degrades to relying on priors rather than real evidence.
- **Fusion strategy admitted to be suboptimal (stated):** the authors note that PCDepth-Ours outperforming Ours-B on DSEC indicates "our multimodal fusion strategy still has space for improvement," i.e., EIFusion is not state-of-the-art for fusion itself — the gains are mainly from the refinement mechanism.
- **Only two real-world datasets, both driving/outdoor scenes (inferred):** DSEC and MVSEC are both automotive/outdoor benchmarks; no indoor, handheld, or non-driving scenario is evaluated, so generalization to other domains (e.g., robotics manipulation, indoor SLAM) is untested.
- **Baseline reproduction choices could favor the proposed method (inferred):** several comparison numbers come from the authors' own reimplementation (PCDepth "reimplemented from scratch," EReFormer-C "retrained... following the original paper's setting" but modified from EReFormer's original recurrent design). While reasonable for fair comparison, self-reimplemented baselines are a known source of potential bias and aren't independently verifiable from the text.
- **Test-set construction is non-standard for DSEC (stated indirectly):** because DSEC's official test-set ground truth isn't public, the authors create their own train/test split and apply a center crop "to reduce misalignment artifacts" — this diverges from a universally standard benchmark protocol, making direct comparison to numbers reported elsewhere in the literature (outside this paper's own baselines) less reliable.
- **No explicit runtime/robustness analysis on long/noisy event streams or sensor failure (inferred):** the ablation on event-slice duration (20/50/100 ms) is the closest proxy, and shows accuracy does degrade with longer windows (motion artifacts), but no test of degraded/noisy event data (hot pixels, low event rate scenes beyond what's naturally in DSEC/MVSEC) is reported.
- **Efficiency comparisons depend on hardware/implementation details (inferred):** inference-time comparisons (Fig. 6, Tab. 1) are run on a single RTX 4090 for all methods, which is reasonable for a controlled comparison, but FLOPs/Param/time differences across very different architectures (Transformer vs CNN vs recurrent) can still be sensitive to implementation-level optimization that isn't discussed.
- **Ablations use a "scaled-down" model, not the full base model (stated):** Table 4's ablations are run on a reduced-capacity version of the architecture trained for fewer iterations (40k vs 60k) with smaller batch size — results may not perfectly transfer to conclusions about the full Ours-B/PCDepth-Ours models used in the headline comparisons.
- **Depth range (d_min, d_max) is assumed known/prior-derived (inferred):** the DHV requires a prior minimum/maximum depth range; the paper states this is "derived from prior estimates" but doesn't fully detail how this prior is obtained at inference time for genuinely unknown scenes, which could be a practical deployment constraint not addressed in the paper.
