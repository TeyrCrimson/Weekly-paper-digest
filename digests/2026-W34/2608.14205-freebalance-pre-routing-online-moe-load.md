# FreeBalance: Pre-Routing Online Moe Load Balancing via Residual Workload Prediction

**Authors:** Pengfei Chen, Yize Wu, Shouxu Kuang, Ke Gao, Ling Li

**arXiv:** [2608.14205](https://arxiv.org/abs/2608.14205)

**Categories:** cs.AI, cs.LG

**Submitted:** 2026-08-14

**Relevance:** 8/10 — matched: LLM inference efficiency and long-context serving

---

## TL;DR
FreeBalance is an online load-balancing system for Mixture-of-Experts (MoE) inference that predicts next-layer expert workload *before* the router runs, by reusing the router on the previous layer's residual hidden state, so expert-weight migration can be hidden behind the preceding attention computation instead of stalling the critical path. It also uses a cost model to cap how many expert swaps it schedules so migration never outlasts the available overlap window. On Qwen3-30B-A3B and Moonlight-16B-A3B across LongBench, it cuts max-to-mean rank load imbalance by up to 32.8% and end-to-end prefill latency by up to 13.1%, while provably not changing model outputs.

## First-principles breakdown

**The setting: MoE inference with expert parallelism.** In a Mixture-of-Experts layer, a small router network looks at each token's hidden state and picks the top-k "experts" (small feed-forward sub-networks) out of a much larger pool to process that token — this keeps compute cost low while allowing huge total parameter counts. To serve these models across multiple GPUs, each GPU ("rank") is assigned a subset of experts (expert parallelism, EP). Tokens get shipped (via an all-to-all communication step) to whichever GPU holds the expert they were routed to, processed, and shipped back.

**The problem: load imbalance stalls everything.** Routing is data-dependent — some experts get picked far more often than others, and which experts are "hot" changes across layers and across task types (the paper shows only 4.1% overlap in which experts are hot between two different task workloads). If a GPU happens to hold several currently-popular experts, it becomes a bottleneck: because the all-to-all and expert computation are synchronized operations, every GPU must wait for the slowest (most-loaded) one before the layer can finish. This "straggler" effect wastes idle capacity on lightly-loaded GPUs and directly adds latency.

**Why prior fixes are insufficient.**
- *Offline placement* (e.g., DeepSeek's EPLB) assigns experts to GPUs ahead of time based on historical routing statistics. This works when load patterns are stable but fails in multi-task serving where the workload composition shifts request to request — a static mapping can't adapt.
- *Reactive online balancing* waits until the router actually produces its routing decision for the current layer, then decides how to redistribute experts and moves expert weights between GPUs. The problem: this migration happens *after* routing and *before* the expert computation can proceed, so it sits directly on the critical path — every millisecond spent moving weights is a millisecond added to inference latency.

**The core idea: predict the routing distribution before it's computed, so migration overlaps with earlier computation.** The authors' insight is that a transformer's hidden state changes only a little from one layer to the next (because of residual connections: `h_ℓ = h_{ℓ-1} + Attention + MoE`). So the hidden state entering layer ℓ-1's output, `h_{ℓ-1}`, is already a decent proxy for what layer ℓ's router will see. Concretely, FreeBalance feeds `h_{ℓ-1}` into layer ℓ's own (frozen, unmodified) router to get an *early* set of routing logits — before layer ℓ's attention has even run. This gives an estimated per-expert workload for layer ℓ. Because this estimate is available before attention, there's now a window (the duration of attention computation) during which expert weights can be migrated between GPUs without adding to the critical path — the migration runs concurrently with attention rather than sequentially after routing.

Crucially, this predicted workload is used *only* to decide physical expert placement (which GPU holds which expert weights). The actual token-to-expert routing decision is still made later by the real router acting on the real hidden state `H_ℓ`; nothing about model outputs changes. This is the "lossless" property — it's a systems optimization, not an approximation of the model's behavior.

**Step-by-step pipeline per MoE layer:**
1. **Residual workload prediction:** Run the layer's router on `h_{ℓ-1}` (available before attention) to get predicted per-expert token counts.
2. **Budgeted expert-swap planning:** Using the predicted loads, greedily pick pairwise expert swaps between the most-overloaded and most-underloaded ranks that reduce a load-imbalance objective (weighted combination of max load and variance across ranks). Swaps are pairwise (rank-for-rank) so every GPU keeps the same number of experts and memory footprint, simplifying bookkeeping and rollback. A cost model estimates transfer time per swap (bandwidth, latency, transferred weight size) and caps the total planned swaps to fit inside the profiled attention-duration window minus a safety margin — so the plan is guaranteed (approximately) to finish before it's needed. Every rank independently computes the same deterministic plan from the same aggregated load statistics, avoiding a broadcast step.
3. **Weight transfer:** Execute the selected swaps concurrently with attention computation of the current layer.
4. **Lossless MoE computation:** The real router runs on the real hidden state, and MoE computation proceeds against the now-updated (rebalanced) expert placement.

## Key insights

- **Genuinely new mechanism:** reusing the *same* router, applied one layer early to the residual stream, as a zero-extra-parameter, zero-training workload predictor. This is elegant because it needs no auxiliary model, no training data, and no checkpoint changes — it just exploits an already-observed property of residual networks (adjacent-layer hidden-state similarity).
- **Evidence supports the prediction is decent but not exact:** hidden-state cosine similarity between `h_{ℓ-1}` and `H_ℓ` ranges 0.71–0.93 (moderate to high, varies notably by model), but router *logit* cosine similarity is consistently very high (0.99+), and top-k hit rate (how often the early prediction actually matches the final routing choice) is only 0.74–0.85. This is an important nuance: the prediction is good enough to guide *placement* decisions (which are somewhat tolerant of error, since a mismatch just means a slightly suboptimal but still valid swap) but is explicitly not accurate enough to replace the real router — which the design correctly avoids relying on.
- **The overlap argument is validated, not just asserted:** the paper separately reports measured overlap time (12.55–36.80ms depending on sequence length) versus actual migration cost (3-4ms/layer), and shows non-monotonic returns to swap count (Figure 4) — an adaptive budget beats any fixed swap count across all tested sequence lengths. This supports the claim that the cost model is doing real work, not just an unused safety feature.
- **Claimed vs. supported:** the abstract's headline numbers (32.8% imbalance reduction, 13.1% latency reduction) are supported by the LongBench table across 19 subsets + 1 mixed-task benchmark on two models, which is a reasonably broad evaluation for this kind of systems paper. The "lossless" claim (no change to model outputs) is architecturally justified by the design (real router still decides final assignments) rather than being an empirically measured property of output quality (no accuracy/perplexity comparison is reported).

## Caveats — stated and inferred

- **Load-balance gains don't translate linearly to latency gains** — stated: the paper explicitly notes "other kernels remain on the critical path," meaning the 32.8% imbalance reduction only yields 13.1% latency reduction, and the reader should not extrapolate one from the other.
- **Only two models evaluated** — inferred: Qwen3-30B-A3B and Moonlight-16B-A3B are both fairly moderate-scale MoE models with linear routers; there's no evaluation on larger or more heterogeneous MoE architectures (e.g., DeepSeek-V3 scale, or non-linear/gated routers), so generalization to those settings is unverified.
- **Single hardware configuration** — inferred: all experiments run on one node type (8×A800 with NVLink, EP=8). No results are shown for different topologies (e.g., inter-node EP, different interconnect bandwidths), even though the cost model explicitly depends on calibrated bandwidth/latency parameters that would differ across such setups.
- **Layer-level imbalance improvement is not universal** — stated: only 95% of layers where migration occurs show a measured improvement in max-to-mean ratio; the remaining 5% don't improve, attributed to "runtime variation or interactions among multiple swaps whose isolated benefits are not perfectly additive" — an acknowledged but not deeply investigated gap in the greedy planner's optimality.
- **Prediction quality varies notably across models** — inferred/partially stated: hidden-state cosine similarity is much lower for Qwen3-30B (0.71–0.73) than for Moonlight-16B (0.92–0.93), suggesting the residual-similarity assumption the whole method rests on is model-dependent and could degrade further on architectures with less smooth residual streams (e.g., deeper models, models with normalization schemes that change residual magnitude behavior) — the paper doesn't test or discuss this sensitivity explicitly.
- **No comparison of predicted vs. actual accuracy trade-off with a "perfect information" oracle** — inferred: the paper doesn't report what imbalance reduction or latency gain would be achievable if the true post-routing distribution were used without migration overhead (i.e., an upper bound), which would help contextualize how much headroom is left versus how much is inherent to the overlap-budget constraint.
- **No evaluation of decoding (only prefill)** — inferred: all reported experiments are prefill latency; the paper doesn't address whether/how the technique applies during autoregressive decoding, where batch sizes and attention costs (and thus the available overlap window) look very different.
- **No output-quality/correctness experiment despite "lossless" framing** — inferred: while the design is such that final routing decisions are unaffected (architecturally sound reasoning), the paper presents no empirical check (e.g., comparing generated outputs or logits with/without FreeBalance) to directly confirm no observable drift, e.g., from numerical/timing side effects.
- **Migration budget calibration and safety margin (δ) sensitivity not explored** — inferred: the budget formula depends on a safety margin δ "for prediction error and stream interference," but no ablation shows how performance changes with different δ values, so it's unclear how tightly tuned this parameter needs to be per deployment.
- **Baseline comparison scope** — inferred: the main baselines are "Vanilla" (fixed placement) and EPLB (offline/history-driven); no comparison is made against more recent reactive online balancers mentioned in Related Work (UltraEP, MoonEP), even though those are argued to be the closest competing approach conceptually.
