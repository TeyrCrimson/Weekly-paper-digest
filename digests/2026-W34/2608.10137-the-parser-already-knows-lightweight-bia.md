# The Parser Already Knows: Lightweight Bias Correction in Constrained Decoding

**Authors:** Işıl Özgü, Yaoxuan Wu, Guy Van den Broeck, Miryung Kim

**arXiv:** [2608.10137](https://arxiv.org/abs/2608.10137)

**Categories:** cs.CL, cs.LG

**Submitted:** 2026-08-10

**Relevance:** 9/10 — matched: Pre-inference input sanitization for generation stability

---

## TL;DR
Grammar Constrained Decoding (GCD) forces LLM outputs to be syntactically valid by masking invalid tokens at each decoding step, but this masking distorts the model's true probability distribution, often locking generation into degenerate completions. SHIM fixes this by training a small offline correction model (logistic regression or a tiny MLP) that reads the parser/lexer state already computed by the masking tool plus the candidate next token, and uses it to rescale the masked logits back toward the model's original distribution. Across bit-vector (SyGuS/BV4) and text-to-SQL (Spider) grammars, SHIM cuts KL divergence from the target distribution by up to 113× vs. plain masking and 235× vs. online sampling, while adding negligible inference latency.

## First-principles breakdown

**The problem: constrained decoding breaks the model's probabilities.**
When you want an LLM to only produce text that obeys a formal grammar (e.g., valid SQL, valid bit-vector expressions), the standard trick is Grammar Constrained Decoding (GCD): at every generation step, you compute which next tokens would keep the output a valid prefix of the grammar, and you zero out (mask) the probability of every other token, then renormalize. This guarantees the final output is syntactically valid.

The catch: masking only checks "is this token valid *given what's been generated so far*" (local/past validity). It has no way to know whether choosing this token will *later* trap the model in a corner where all remaining continuations are low-probability or awkward for the LM. The paper's toy example: a grammar accepts either the string "00000" or any 5-bit string starting with "1". If the LM's honest per-token belief is 50/50 between starting with "0" or "1", the correct grammar-conditioned probability of "00000" should be 1/17 (since it's one of 17 equally likely valid strings), but masking greedily commits to a 50% chance of "0" as the first token, and once "0" is chosen the grammar forces the rest — so masking assigns "00000" a probability of 1/2, wildly overestimating it relative to the model's true intent. This distortion compounds over the sequence and can push the model toward "valid but suboptimal" outputs.

**Why prior fixes are unsatisfying.**
- *Rejection sampling*: keep sampling freely until you get a valid string. No guarantee within budget, computationally wasteful.
- *Masking (GCD)*: fast and always valid, but distorted (as above).
- *Online sampling* (e.g., ASAp): iteratively reweights the distribution during generation to correct for future-invalidity, restoring fidelity — but requires expensive resampling at every step, blowing up latency (their benchmark shows it running many times slower than masking).
- *Tractable probabilistic augmentation* (e.g., HMM-based methods like GeLaTo/Ctrl-G): pair the LLM with a separate exactly-computable model (like a distilled HMM) that can be combined with the LLM's distribution without runtime sampling — but distilling an entire secondary model of the LLM's output distribution is hard and introduces its own approximation error.

So existing approaches trade off between output fidelity, speed, and modeling difficulty. Nothing gets all three.

**The core insight: the parser already contains the missing information.**
GCD tools like Syncode use an *incremental parser* — a parser that consumes the sequence token-by-token (rather than all at once at the end) and maintains internal state about how far it has progressed through the grammar. This is standard compiler-construction machinery (lexer + parser, as in a typical compilers course): a *lexer* turns a character stream into tokens ("lexemes") by matching against patterns, and a *parser* tracks which grammar rule/position it's currently in given the tokens seen.

Crucially, this state already implicitly encodes a lot about what's grammatically permissible next, even before the parser itself formally advances. The paper illustrates this with the lexer state: while parsing the operator "bvand" character-by-character, after seeing "bv" the lexer knows the only remaining candidate lexemes are {bvand, bvlshr, bvor} — information not yet visible to the parser (which only advances once the whole token "bvand" is consumed). So there are two complementary state sources:
- **Parser state**: captures structure across already-completed lexemes/tokens, but "stalls" (doesn't update) mid-lexeme.
- **Lexer state**: captures fine-grained within-lexeme progress but is blind to grammar structure beyond the current lexeme.

Additionally, the **candidate next token itself** is informative, analogous to how LR(1) parsers use a single lookahead token to resolve ambiguous parsing decisions (shift/reduce conflicts) — the token about to be emitted often already discriminates between future grammatical paths.

**The mechanism: a learned correction factor γ.**
Mathematically, the paper derives (via Bayes' rule) that the "ideal" fix to the masked distribution q_α is to multiply each valid token's probability by a correction factor γ(x_i, x_<i) ≈ p(α | x_i, x_<i) — i.e., the probability that choosing this token still allows a grammar-satisfying continuation in the future. This quantity is intractable to compute exactly (it would require knowing the full future). So instead of computing it exactly, SHIM *learns* an approximation of γ offline, using a small classifier whose inputs are: (parser state, lexer state, candidate next token), and whose training label is whether the sequence that resulted was ultimately grammatically valid, using training data generated by running the base LLM (unconstrained) and observing which sequences the incremental parser marks as valid/invalid at each step.

At inference: mask invalid tokens as usual (guaranteeing hard grammar compliance), then apply the learned γ (via its log added to the logits) to the remaining valid tokens' logits, nudging the surviving probability mass back toward what the LM would have generated unconstrained. Because parser/lexer state is *already computed* as a byproduct of masking (Syncode already needs it to decide the mask), extracting it for γ's input costs almost nothing extra. Crucially, this doesn't touch the LLM's weights at all — it's a pluggable post-hoc correction layer sitting on top of any existing GCD masking tool (they build on Syncode/Lark, but say the idea generalizes to XGrammar, Outlines, etc.).

They train three variants of increasing lightness: an MLP (2 hidden layers, all three features), a logistic regression on the same full feature set (LR_FULL), and a logistic regression using only the candidate next token (LR_NT, no parser/lexer access at all).

## Key insights

- **Genuinely new framing**: masking's failure mode is characterized precisely as a mismatch between "past-conformance-only" masking (q_α) and the true grammar-conditioned distribution p(·|α), formalized via Bayes' rule into a decomposable correction factor γ = p(α | x_i, x_<i). This gives a principled target for what needs to be learned, rather than an ad hoc heuristic.
- **The main technical claim**: parser and lexer state that GCD tools already compute for masking is *sufficient* signal to approximate γ well, avoiding the need to learn a whole new surrogate model of the LLM's distribution (unlike HMM-distillation approaches) or to do expensive online resampling (unlike ASAp-style methods). This is supported reasonably well by the KL-divergence results: MLP/LR_FULL beat Syncode on most of the 14 BV4 grammars and beat ASAp on essentially all of them, at comparable or better latency than plain masking.
- **Secondary, more surprising claim**: even the next-token-only variant (LR_NT, with zero access to parser/lexer state) matches or beats both baselines in aggregate, supporting an analogy to LR(1) parsing's lookahead-token trick. However, the paper's own SQL experiments show this is "conditional rather than universal" — LR_NT does badly when grammatical validity depends on longer-range structure (e.g., disambiguating near-duplicate SQL column names, or JOIN table membership), where the discarded parser/lexer state actually mattered. This is a good example of the paper being honest that its own headline simplification doesn't always hold.
- **Practical framing**: SHIM is positioned as a drop-in correction layer compatible with any existing masking-based GCD tool, not a replacement — it requires no LLM fine-tuning and claims to generalize (though only Syncode was actually tested).

## Caveats — stated and inferred

- **Small, narrow benchmark set (stated implicitly / inferred)**: The main quantitative results are on 14 BV4 SyGuS bit-vector grammars (small closed vocabulary of essentially "0/1"-like bitvector expressions) and only 4 hand-picked Spider text-to-SQL query rows. Four SQL examples is a very small sample to support claims of "generalization to a real-world domain." **(inferred)**
- **Single base LLM**: All experiments use only Mistral-7B-Instruct-v0.2; no results are shown for other model families or sizes, so it's unclear whether the correction generalizes across architectures/scales. **(inferred)**
- **ASAp baseline artificially capped**: The paper states ASAp's resampling cost grows with each sample and running it to convergence "was computationally infeasible at our evaluation scale," so they cap it at 100 samples per grammar — meaning the comparison against ASAp may not reflect ASAp's best achievable fidelity, only a resource-limited version. **(stated)**
- **Grammar was modified for one baseline comparison**: For the `cre_theme_park` SQL row, they explicitly simplified ASAp's grammar/vocabulary just to get a timing result to terminate, and consequently omit the KL score for that row entirely because "this changes the target distribution." This is a partial, acknowledged apples-to-oranges comparison. **(stated)**
- **KL divergence estimated from finite samples, with an acknowledged bias**: The paper notes "an empirical KL estimate is optimistically biased when computed from few target samples," and shows (Figure 5) that ASAp's apparent early competitiveness partly reflects under-sampling rather than true closeness to the target — implying the headline Table 1 KL numbers themselves may also carry some finite-sample bias despite the authors checking for it. **(stated, but self-mitigated only partially)**
- **Mixed/non-uniform results, not uniformly dominant**: MLP loses to Syncode on 3 of 14 BV4 grammars; LR_FULL loses on 2; LR_NT beats Syncode on "exactly half" the grammars and performs badly on one SQL row (`entertainment_awards`, where it is called out as "substantially worse than every full-feature variant"). The abstract's framing ("consistently outperforming") somewhat overstates what Table 1 actually shows, which is *mostly but not uniformly* better. **(inferred — abstract vs. table tension)**
- **No comparison against tractable probabilistic augmentation baselines (GeLaTo/Ctrl-G/P-GCD)**: These are discussed at length in Related Work as a third paradigm SHIM is positioned against, but no empirical comparison is run against them — only against Syncode (masking) and ASAp (online sampling). The claimed advantage over this third family is argued conceptually, not measured. **(inferred)**
- **Training data / offline cost not analyzed**: The method requires generating 1000 sequences per grammar via the vanilla LLM plus running the incremental parser over them to build training data, and cross-validating architecture choices on 5000 examples. The paper doesn't report how this training cost scales with grammar complexity or vocabulary size, nor how much labeled data is needed for the corrector to work well on a new grammar — relevant for the "cheap to retarget to new grammars" claim in Related Work. **(inferred)**
- **No ablation isolating parser state's marginal contribution alone (without lexer state)**: They ablate down to next-token-only (LR_NT) and up to full-feature (MLP/LR_FULL), but there's no reported experiment measuring parser-state-only vs. lexer-state-only contributions, despite the paper's narrative giving both features distinct conceptual roles. **(inferred)**
- **Latency measured only in seconds per full sequence on unspecified hardware**: No GPU/CPU specs, batch size, or sequence length details are given for the timing comparisons (Tables 1–2), making it hard to judge how the "negligible overhead" claim would hold up at production scale or under batched inference. **(inferred — not addressed in the paper)**
