# MCUFlowNet: Hardware-Aware Neural Architecture Search for Optical Flow on Microcontrollers

**Authors:** Enmin Lin, Jona Beysens

**arXiv:** [2611.08147](https://arxiv.org/abs/2611.08147)

**Categories:** cs.CV, cs.AR

**Submitted:** 2026-11-05

**Relevance:** 6/10 — matched: Onboard object detection from a moving UAV

---

## TL;DR
PACE-NAS is a hardware-aware neural architecture search framework that first fixes peak SRAM usage by restructuring a network's memory-bottleneck layer, then searches only architectural choices that cannot increase that peak, freeing the search to optimize purely for latency and accuracy. Applied to EdgeFlowNet on an Arm Cortex-M55/Ethos-U55 MCU, the resulting MCUFlowNet-S runs 1.76× faster than a retrained EdgeFlowNet baseline at only 1.6% worse endpoint error (EPE), and improves simulated drone obstacle-avoidance success from 41.8% to 51.5%. The same recipe also speeds up PIDNet-S for semantic segmentation by 1.17× at similar accuracy, suggesting the approach generalizes beyond optical flow.

## First-principles breakdown

**The problem.** Small drones need dense optical flow (per-pixel motion between consecutive camera frames) to avoid obstacles. Running this on-device on a microcontroller (MCU) is attractive because MCUs are light and low-power, but MCUs with neural accelerators (like the Ethos-U55 used here) have very limited on-chip SRAM. All the intermediate data a network produces while running ("activations"/"tensor arena") must fit in this SRAM — if it doesn't, the model simply cannot be deployed. This caps how big an input image the network can process, which in turn limits accuracy. Existing good optical flow networks (RAFT, NeuFlow, FastFlowNet) target GPUs and use expensive operations (cost volumes, iterative refinement, warping) that don't fit MCU accelerators at all — the authors tried deploying them and none worked. EdgeFlowNet is a decent lightweight candidate (built from plain convolutions the accelerator supports well) but was designed for Google's Edge TPU, not MCUs, and its output head — the part producing full-resolution flow — turns out to be the layer that drives peak memory use.

**Why naive NAS (architecture search) doesn't trivially solve this.** Normally, hardware-aware NAS (e.g., MCUNet) treats peak SRAM as a constraint baked into every candidate architecture's evaluation — you search a space and reject/penalize anything that busts the memory budget. This is workable for classification nets but gets complicated for dense prediction tasks like optical flow, and entangles two different concerns (memory feasibility and speed/accuracy trade-off) into one search objective.

**This paper's mechanism — "macro-to-micro" decoupling (PACE-NAS):**
1. **P — Platform Profiling:** Run the target network through Arm's Vela compiler (which estimates per-layer SRAM and latency on the Ethos-U55) to find exactly which layer causes the peak SRAM. For EdgeFlowNet at 160×208 input, profiling shows the peak (1430 KiB, almost the entire 1434 KiB budget) occurs at the full-resolution output head, because it must simultaneously hold its upsampled input and its output.
2. **A — Architectural Restructuring:** Fix that one bottleneck, once, for the whole architecture. Concretely: replace all 11 transposed convolutions (a learned-upsampling operation) with a cheaper "bilinear resize + regular convolution" combo. Why this helps: Vela can "cascade" (stream, stripe-by-stripe without ever fully materializing) compatible layers like regular convolutions, but not transposed convolutions. Swapping removes the uncascadable operation, cutting peak SRAM by 18% and latency by 15%, while leaving accuracy roughly unchanged. This also moves the peak elsewhere (to final flow upsampling) and frees up spare SRAM in early (low-resolution) stages. The authors use that freed SRAM to add two lightweight attention modules — Efficient Channel Attention (ECA, reweights channels based on global context at the lowest-resolution feature map) and a "global broadcast gate" (uses that global context to modulate the decoder feature feeding all flow-prediction heads) — giving the network image-wide context it otherwise lacks (plain convolutions only see local windows), improving accuracy without raising the peak.
3. **C — Configuration Space & Supernet Training:** Now define a search space of architecture variants (which convolution kernel types at specific stages, how many residual blocks at each resolution) that are carefully chosen so that none of them can touch tensor sizes and thus none can exceed the already-fixed peak. This is the key trick: because every candidate is memory-safe by construction, the search doesn't need to track or penalize memory at all — it only needs to trade off latency vs. accuracy. They train one "supernet" containing all candidate sub-networks simultaneously via weight-sharing (Single Path One-Shot style: each training step samples one candidate path and updates only its weights), with "FairNAS" balanced sampling (make sure each option gets fair training exposure) and distillation from a frozen pretrained EdgeFlowNet teacher (so all shared paths are pulled toward consistent features rather than diverging).
4. **E — Evolutionary Pareto Search:** Score ~800 of the 23,328 possible sub-networks by (a) their accuracy using the shared supernet weights (no retraining needed — fast proxy) and (b) Vela-estimated latency. Run NSGA-II (a standard multi-objective evolutionary algorithm) to find the Pareto front (best accuracy-for-latency trade-offs). Pick two points off this front — fastest (MCUFlowNet-S) and one matching the baseline's latency (MCUFlowNet-L) — and retrain those from scratch for the real deployment numbers.

This is analogous to deciding a building's structural footprint and load limits once (civil engineering), then letting interior designers freely rearrange furniture within those limits without re-checking structural safety each time — the "memory constraint" cost in the search becomes free.

## Key insights

- **Genuinely new idea:** decoupling the "stay within memory" problem from the "be fast and accurate" problem by solving the first once via targeted profiling + restructuring, then restricting the search space so memory is automatically satisfied. This removes memory as a search constraint entirely (claimed and demonstrated: all 800 evaluated subnets share identical peak SRAM, confirming the restructuring argument holds in practice, not just in theory).
- **Vela compiler's cascading behavior (streaming compatible layers to avoid materializing full intermediate tensors) as the root cause of the memory bottleneck** is a specific, device/compiler-level diagnosis — valuable for engineers targeting Ethos-U55/similar accelerators, not just a generic "make the network smaller" fix.
- **First application of hardware-aware NAS to dense optical flow for MCU-class accelerators** — claimed novelty; plausible given related work survey shows prior flow NAS (FlowNAS) targets GPU-scale models and prior MCU NAS (MCUNet/MCUNetV2) targets classification/detection.
- **Evidence supports:** real deployed, measured speedups (1.76× for MCUFlowNet-S, matching latency for MCUFlowNet-L) with accuracy costs quantified on standard benchmarks (Sintel EPE) and an end-task benchmark (simulated obstacle avoidance), plus a second domain (segmentation/PIDNet-S) showing the framework isn't single-use.
- **Interesting secondary finding:** in the obstacle-avoidance task, latency matters more than raw EPE accuracy for real-world success — a model with worse EPE but much lower latency outperforms more accurate-but-slower models, and the ablation (slowing MCUFlowNet-S to match baseline latency) isolates that most of the gain is from latency, not architecture quality per se. This is a useful, somewhat counter-intuitive practical insight for the robotics/edge-AI community.
- **Latency estimates from Vela are empirically validated** against real board measurements (within 2.1%), which supports using the compiler's static estimate as a fast NAS proxy instead of running every candidate on real hardware.

## Caveats — stated and inferred

- **Single hardware target (stated/inferred):** All results are on one specific board (Grove Vision AI V2, Cortex-M55 + Ethos-U55). The paper doesn't claim or test generalization to other MCU/accelerator combinations; the compiler-specific "cascading" behavior that drives the key restructuring trick may not transfer to other compilers/accelerators. (inferred)
- **Obstacle avoidance evaluation is simulation-only (stated):** The flight tests use AvoidBench simulation, not real drone flights; real-world sensor noise, wind, vibration, and compute-in-the-loop effects are untested. (inferred from methodology — simulation is explicitly named, but no real-flight validation is mentioned or caveated by authors)
- **Narrow comparison baseline for "faster/no worse" claims (inferred):** The primary comparison is against a *retrained* EdgeFlowNet (not even the original public weights, which perform worse), and no other MCU-targeted dense flow network is compared at deployment (cost-volume/warping models reportedly "could not be deployed" at all on the MCU) — so there's no apples-to-apples competing method on the same hardware, only an internal before/after comparison.
- **Search space is fairly constrained and hand-designed (inferred):** Channel counts, connections, upsamplers, ECA, and gate are all fixed by the architects, not searched; only kernel choice (3×3 vs 5×5) and residual-block depth are searched. This is a deliberate design choice to keep memory fixed, but it means the "NAS" explores a much smaller space (23,328 combos) than typical NAS papers, and the accuracy gains attributable to search per se (versus the macro restructuring) are modest — Table I shows EPE differences from the architectural restructuring/attention modules are already within about one standard deviation across seeds in places.
- **Supernet proxy accuracy (EPE with inherited weights) used for Pareto search, not independently validated against fully-retrained accuracy for all 800 candidates (inferred):** Only two final subnets are retrained from scratch and verified; it's not shown how well the supernet-inherited EPE ranking correlates with true post-retraining EPE across the broader Pareto set, so cherry-picking two "winners" that happen to retrain well cannot be ruled out.
- **Small-scale quantization calibration (inferred):** INT8 post-training quantization uses only 64 (optical flow) or 256 (segmentation) calibration images — not addressed whether this is sufficient for robustness across broader scene distributions.
- **Evaluation resolution/crop choices (inferred):** EPE is computed on a central crop of Sintel Final at a specific resolution with deployed models' outputs resized/rescaled; the effect of this resizing+rescaling pipeline on reported EPE versus native-resolution evaluation is not discussed.
- **Training cost claims (17 GPU-hours vs 33 for one training run) are estimates (stated as "estimated H200 GPU-hours")**, not measured wall-clock, and exclude the cost of the two full retrains of selected subnets plus three-seed ablation runs, so total framework cost including human-in-the-loop model selection is likely higher than the headline "half the cost" framing suggests. (inferred)
- **Generalization claim to segmentation is based on a single additional architecture (PIDNet-S) and dataset (Cityscapes)** — modest 1.17× speedup at similar mIoU is a reasonable but limited data point for a "generalizes beyond optical flow" claim. (inferred)
