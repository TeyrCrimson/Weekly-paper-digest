# Pallas: A Proactive KV Cache Migration Framework for LLM Inference in AI-RAN

**Authors:** Tianhang Ding, Jianchun Liu, Hongli Xu

**arXiv:** [2608.16477](https://arxiv.org/abs/2608.16477)

**Categories:** cs.LG

**Submitted:** 2026-08-17

**Relevance:** 10/10 — matched: LLM inference efficiency and long-context serving

---

## TL;DR
Pallas is a proactive KV-cache migration framework for LLM serving in AI-RAN that prepares an inference session's KV cache at the predicted target base station *before* cellular handover happens, by having the target prefill a stable token prefix while the source streams newly-generated KV blocks for the evolving suffix. This overlap-with-inference approach cuts service interruption time (SIT) by 2.28–89.68x versus prior target-side recovery methods and reduces inter-token latency (ITL) by 16–50% versus simply forwarding tokens through a relay, across three LLMs and 100–500 Mbps inter-gNB links. The core idea is treating handover as a *deadline* for state preparation rather than a *trigger* for it.

## First-principles breakdown

**The setup.** AI-RAN colocates GPU inference servers with cellular base stations (gNBs) so LLM serving happens physically close to the user, cutting network latency. But mobile users move between cells ("handover"), and when they do, their network connection switches to a new (target) gNB while the LLM's per-request state — the KV cache — is still sitting on the old (source) gNB's GPU.

**Why the KV cache is the hard part.** During autoregressive decoding, a transformer caches the key/value tensors for every previously generated token so it doesn't have to reprocess the whole context each step. This cache grows linearly with tokens generated (the paper computes ~256 KiB/token for Qwen3-32B, reaching ~1 GiB at 4K tokens) and it keeps growing throughout the session — it's not a static, one-time object you can snapshot and forget.

**Why prior approaches fail:**
- *Detour (source-side retention)*: keep running inference at the source and just relay tokens to the UE through the target gNB after handover. This avoids ever moving the KV cache, but adds permanent extra network hops to every subsequent token, degrading ITL for the rest of the session (P90 ITL up to 130ms+, violating the 100ms SLO with meaningful probability).
- *Full-Copy*: transfer the entire KV cache to the target after handover. Simple but slow — transfer time scales with cache size and is bandwidth-bound (29s at 4K tokens over 300Mbps), and the user gets zero new tokens until it's done.
- *Recomputation*: instead of transferring cache, send just the token IDs and have the target re-run prefill to rebuild the cache locally. Avoids the transfer but the recompute time still scales with context length and blocks the user on the critical path.
- *ctHO* (closest prior work): split the sequence into a prefix (rebuilt via target prefill) and suffix (transferred from source), and jointly optimize this split, balancing the two operations. Better than either alone, but crucially **both operations start only after handover** — so the slower of the two still directly adds to interruption time.

All four share the same structural flaw: they treat handover as the moment recovery *begins*, so recovery latency is fully exposed as service interruption.

**Pallas's mechanism.** The insight is that upcoming handovers are often predictable in advance (from mobility/radio trajectory prediction), so preparation can start *before* the user actually switches, running in parallel with the still-ongoing source-side inference:
1. At a "preparation trigger" time (chosen by a scheduler, see below), Pallas freezes a block-aligned split point in the token sequence: everything before it is a stable "historical prefix," everything generated after is an "evolving suffix."
2. The target gNB receives just the prefix's token IDs and reconstructs its KV cache locally via ordinary prefill — this is compute-bound work done ahead of time.
3. Meanwhile the source keeps decoding and delivering tokens to the user *uninterrupted*, and asynchronously streams newly-completed KV blocks for the suffix to the target as they're produced (not one big transfer — a rolling stream).
4. At the actual handover moment, the source sends a final token snapshot plus any not-yet-streamed KV blocks; the target assembles prefix + suffix into a complete, up-to-date cache and resumes decoding locally. Only whatever prefix-reconstruction or suffix-streaming work is *still incomplete* at that instant contributes to SIT — ideally that's near zero.

**The scheduling problem: picking the "prefetching window."** How far ahead of predicted handover should preparation start? Too early: the prefix split point is earlier, meaning a bigger, more expensive suffix to stream (and the target sits holding partially-stale state longer — "early-preparation exposure"). Too late: prefix reconstruction or suffix sync won't finish in time and the leftover work spills onto the SIT-critical path. Pallas formalizes this as minimizing a weighted objective J = α·SIT + (1-α)·early-exposure over candidate window lengths, using estimates of target prefill throughput, source decode throughput, and inter-gNB goodput (smoothed via exponential moving average to avoid noise). An online scheduler re-evaluates this every control cycle, using mobility prediction (predicted target gNB + handover time) plus live telemetry, and can defer, trigger, or (if a new target is predicted) cancel and replan.

**Practical engineering details:** built on vLLM 0.8.5, KV-cache splits align to PagedAttention block boundaries (16-token blocks) so only complete blocks are ever transferred; blocks are streamed via gRPC; a migration epoch number prevents stale/cancelled preparation from contaminating an active request; chunked prefill is used so target-side prefill doesn't starve co-located decoding requests (handling GPU contention when multiple migrations/inference share a target).

## Key insights

- **Genuinely new**: reframing handover from "recovery trigger" to "preparation deadline" — i.e., doing state migration *proactively and in parallel* with ongoing inference rather than reactively after the disruptive event. This is the paper's central claimed contribution and is architecturally distinct from ctHO, which optimizes the same prefix/suffix split but still executes it entirely post-handover.
- **The prefix/suffix decomposition itself isn't new** (ctHO already does prefix-prefill + suffix-transfer combination) — Pallas's novelty is timing (moving it before handover) plus the online window-selection scheduler that adapts the trigger point to changing conditions and mobility-prediction updates.
- **Evidence supports**: large, consistent SIT reductions (orders of magnitude vs Full-Copy, several-fold vs Recomputation/ctHO) across three model sizes, three fixed goodput levels, replayed real-world bandwidth traces, and repeated-handover trajectory simulations — this is a fairly comprehensive sweep for a systems paper. ITL improvement over Detour is also well substantiated and intuitively expected (locality restored, forwarding hops removed).
- **Ablation supports the two-mechanism design**: removing either historical-prefix recomputation or incremental streaming substantially hurts SIT (down 97.9%/33.3% respectively when combined vs either alone), so both pieces are doing real work, not just one dominating.
- **Bounded staleness is a real but modest guarantee**: the paper proves an upper bound on wasted preparation (T_waste) when mobility predictions are wrong, and shows empirically the actual waste stays below this bound — a reasonable engineering safety net rather than a strong constant-factor optimality claim.
- **Contention handling is evaluated but underspecified as a mechanism**: Pallas adapts *when* to trigger migration based on measured contention, but explicitly does not perform joint GPU/bandwidth allocation across concurrent migrating users — that's deferred to "future work" / underlying runtimes, so the reported gains under concurrency (Section 6.4) reflect only this partial mitigation.

## Caveats — stated and inferred

- **Requires accurate mobility/handover prediction** (stated, and partially inferred as a real dependency): the entire proactive advantage collapses if predicted handover time/target is wrong or too close to the actual event; the paper's own robustness test shows SIT degrades sharply once available prediction lead time (T_avail) drops below ~1s for larger contexts/models. `stated`
- **Target-prediction errors are non-trivial in the tested setting**: with a 50m cell grid, 37.3% of handovers had an incorrect target prediction and only 51.9% had ≥2s of T_avail; even at 150m cells, 11.2% mispredicted. This is real data the authors report, but it means a meaningful fraction of handovers in their own simulated trajectories don't get Pallas's full benefit and fall back to reactive recovery. `stated`
- **No joint multi-user resource allocation**: the scheduler reacts to observed contention but doesn't optimize GPU/bandwidth allocation across concurrently migrating or inferencing users — explicitly called out as future work and a scope limitation. `stated`
- **Evaluation topology is synthetic/simplified**: trajectories from nuScenes are translated/rotated onto artificial square-grid cell topologies (50/100/150m), not real cellular deployment geometries or real handover traces; goodput is either fixed, drawn from a truncated normal distribution, or replayed from a single WiGig testbed dataset (SNOB-5G) — not diverse real inter-gNB backhaul measurements. `inferred`
- **Single-vendor GPU/cluster setup**: all experiments run on RTX A6000 GPUs across at most two physical servers connected by 1-Gbps Ethernet or single-host — much smaller/more homogeneous than a real multi-vendor RAN deployment with heterogeneous accelerators. `inferred`
- **Baselines may be somewhat idealized re-implementations**: Detour, Full-Copy, Recomputation, and ctHO are described as being compared "under identical workloads, network conditions, and handover events," but it's not stated whether these are the original systems or the authors' own re-implementations on top of their vLLM prototype — if the latter, baseline tuning quality is uncertain. `inferred`
- **α=0.8 weighting for the SIT-vs-early-exposure objective is fixed by the authors with no sensitivity analysis reported** beyond stating the choice; how robust results are to this hyperparameter across workloads is not addressed. `inferred`
- **Fallback policy (when predicted target is infeasible, e.g., lacks VRAM or model) is only briefly described conceptually** and not evaluated quantitatively — its performance under real admission failures is not addressed in the paper.
- **Tail latency under contention still degrades**: at higher concurrency (K=4 handover-handover contention) or resident-load 3 (handover-inference), worst-user SIT and P99 ITL both rise noticeably, showing the proactive approach's benefits shrink under heavier load — the authors report this transparently but it tempers the headline average-case numbers. `stated`
- **Real-world deployment costs (VRAM overhead of holding prepared-but-unused state, GPU cycles "wasted" on mispredicted targets) are quantified only via the analytical T_waste bound, not measured in absolute GPU-hour or dollar terms** — not addressed in the paper.
