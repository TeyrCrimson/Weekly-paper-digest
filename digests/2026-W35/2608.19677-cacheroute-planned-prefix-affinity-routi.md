# CacheRoute: Planned Prefix-Affinity Routing for Large-Scale LLM Serving

**Authors:** Huang Cheng

**arXiv:** [2608.19677](https://arxiv.org/abs/2608.19677)

**Categories:** cs.DC, cs.LG

**Submitted:** 2026-08-20

**Relevance:** 9/10 — matched: LLM inference efficiency and long-context serving

---

## TL;DR
CacheRoute is a periodic, rate-aware routing planner for LLM serving that admits high-rate "keys" (e.g., business/tenant IDs) into a stable warm-cache set, sizes their destination assignments to cap expected load, and places them via longest-processing-time-first scheduling — combining prefix-cache affinity with load balancing instead of forcing a tradeoff. On Llama-3.3-70B fp8 across 60 H100 GPUs it sustains 2.3x the QPS of the strongest of five baselines at a fixed p99 SLO and raises served KV-cache hit rate from 64% to 93%. The paper also reports two 32B workloads where affinity *hurts* throughput, leading the authors to recommend a mandatory shadow-replay gate rather than deploying affinity based on workload statistics alone.

## First-principles breakdown

**The underlying problem: prefix caching in LLM serving.** When an LLM server processes a prompt, it computes "KV cache" (key/value attention states) for every token, an expensive step called prefill. If a new request shares a prefix with a previous request handled by the same server (e.g., a repeated system prompt or conversation history), the server can reuse the cached KV states and skip prefill for that shared portion — a large latency/compute win. But this only works if the repeat request is routed to the *same* server that still holds that KV cache in memory (caches are per-server and finite, so old entries eventually get evicted).

**Why naive load balancing fails.** A standard load balancer (e.g., "power-of-two choices," which picks the less-loaded of two random servers per request) spreads a given tenant's/business's requests across many servers to balance queue lengths. But this means a repeat request from the same business rarely lands back on the server holding its cached prefix — the expected time before returning to any one server scales with (number of servers)/(that business's request rate). More servers can paradoxically make caching *worse* because revisit times grow, even though aggregate cache capacity grows too.

**Why naive "stickiness" (pure affinity) also fails.** The opposite fix is to pin each business's traffic to one server via consistent hashing, guaranteeing cache locality. But request rates across businesses are highly skewed (the paper measures a Gini coefficient of 0.756 — a small fraction of keys generate a disproportionate share of traffic). Pinning a very active business to one server can overload that server's queue, and that overloaded server's tail latency becomes the bottleneck for the whole fleet (fleet-wide p99 is set by the worst queue, not the average).

**CacheRoute's mechanism — resolving this by planning, not reacting.** Rather than making a per-request decision reactively (as prior "cache-aware" routers like Preble or DualMap do — checking current cache/load state and possibly spilling to a cold server once a destination fills, which forfeits the warm prefix), CacheRoute precomputes a *routing table* periodically (every "control interval") using measured per-key request rates:
1. **Load sizing**: for each business key with rate λ_b, compute k_b = max(1, ⌈λ_b/q_cap⌉) — the number of destination servers needed so that no single destination's expected load from this key exceeds a calibrated capacity threshold q_cap. In their primary workload, every key's rate is low enough that k_b = 1 (single-destination affinity) — replication across multiple destinations is only exercised in synthetic "whale" stress tests.
2. **Warm-set admission**: sort keys by rate, and admit the highest-rate keys into a fixed cache-slot budget (C = R×W slots across R destinations with W slots each) until the budget is used up. Lower-rate keys are not given guaranteed affinity.
3. **Placement via LPT (longest-processing-time-first) scheduling**: a classic bin-packing heuristic — process jobs (here, key-to-destination assignments) in decreasing size order, always assigning the next job to the currently least-loaded valid destination. This balances aggregate expected load across servers while respecting each key's k_b destination constraint.
4. **Dispatch**: during the control interval, admitted keys' requests go to the least-loaded member of their fixed assigned set; everything else (unadmitted, low-rate/cold-tail traffic) falls back to ordinary power-of-two-choices load balancing.

The table is deliberately *fixed* for the whole interval rather than updated per-request — this trades some staleness for cache stability (avoiding "cap thrashing" where requests get reassigned mid-stream and lose their warm cache). The actual KV cache itself is untouched — CacheRoute doesn't reserve or migrate cache blocks, it just steers traffic; the underlying engine's native eviction still governs what's actually cached.

**Why this is expected to beat both extremes.** Instead of spreading everyone (losing locality) or pinning everyone (creating hot spots), CacheRoute gives guaranteed-affinity treatment only to keys whose rate justifies it, sized to avoid overload, and balances the resulting assignment load like a bin-packing problem. The 8B ablation (Table 4) explicitly separates the two effects: adding affinity alone raises KV hit rate but also raises load imbalance (3.46x) without improving capacity; adding LPT placement on top brings imbalance down to 1.24x and only then does throughput capacity actually increase — showing both pieces are necessary, neither alone suffices.

## Key insights

- **Genuinely new contribution**: not the scheduling primitives themselves (top-rate admission and LPT are explicitly acknowledged as "established techniques," not novel) — the contribution is the *routing design* that combines them for prefix-affinity serving, plus large-scale empirical characterization of when this helps versus hurts.
- **Strong, well-supported result**: the 70B/60-H100 headline (2.3x capacity, 93.2% vs 64.1% KV hit) is backed by five paired seeds with confidence intervals and a second independently-collected workload distribution showing a smaller but still positive effect (1.6x at a wider active set) — reasonably convincing given the paired, multi-seed design.
- **The mechanism decomposition (affinity vs. placement) is a genuine, well-evidenced insight**: affinity alone can *increase* load imbalance and not help throughput at all — only the combination with balanced placement unlocks the gain. This is a nontrivial, non-obvious finding rather than an assumed synergy.
- **The negative results are arguably the paper's most valuable contribution**: two 32B workloads where affinity provides only marginal KV-hit improvement (8–12 percentage points) and this is not enough to offset residual load skew, causing CacheRoute to *underperform* flat load balancing (0.5–0.67x capacity). This directly motivates their practical recommendation — mandatory shadow-replay testing before enabling affinity, rather than trusting an analytic model — which they also empirically justify by showing an analytic residency-prediction model failed badly (14.3 pp median error, 44.7 pp at p90).
- **Claimed vs. supported precision**: the paper is unusually careful to flag which results are "right-censored" (hit the test ceiling, so true capacity is unknown), which are single-seed/low-seed (wide, noisy confidence intervals), and which are "supporting mechanism evidence" vs. core claims (see their own "claim-to-evidence map" in the appendix) — this self-labeling is a good-faith signal but also means several headline-adjacent numbers (e.g., 8B knees capped at 500 QPS) are less solid than the flagship 2.3x figure.

## Caveats — stated and inferred

- **Two negative workloads where the method actively hurts performance** (32B aggregate A: 0.50–0.67x flat baseline capacity) — `stated`, and notably the authors did not paper over this; it's foregrounded as a core finding.
- **Equal-slot admission assumes uniform prefix sizes**; no byte-aware/heterogeneous-prefix admission was built or tested — `stated`.
- **Analytic residency/occupancy prediction model failed** (14.3pp median, 44.7pp p90 error vs. measured hit rate) — `stated`; the authors use this to justify requiring shadow replay rather than trusting statistics-only deployment.
- **No churn-aware replanner implemented**; stale tables lose up to 3.0 points KV hit / 858ms p99 in worst-case drift transitions, and fresh-plan installs cause a transient 13.6-point hit-rate drop during rewarming — `stated`.
- **Baselines are reimplementations, not original codebases** ("Preble, DualMap, and CHWBL are common-harness reimplementations... do not reproduce the published systems end to end") — `stated`; this means absolute comparisons to these systems' published results should not be trusted, though the authors are transparent about it.
- **Workload is semi-synthetic, not live production traffic** — a synthetic stream constructed to mimic statistics (per-key rates, inter-arrival gaps, popularity) derived from de-identified telemetry, not actual replayed requests — `stated`. This is essentially a simulation-of-realistic-statistics evaluation; real production dynamics (e.g., true timestamp ordering, content-dependent effects) are not captured. The paper itself notes "they do not preserve exact per-key timestamps."
- **Small sample sizes for several sub-studies**: secondary-distribution, 8B, and negative-32B studies use only 3 paired seeds with explicitly "wide" Student-t confidence intervals that the authors themselves say "warrant interpreting small differences as noise" — `stated`.
- **Right-censoring in the 8B results**: several capacity numbers hit the 500 QPS sweep ceiling and are reported as lower bounds, not true capacities, inflating apparent parity/wins in some cells — `stated`.
- **An earlier anomalous high-failure-rate result at top-K256 did not reproduce** in a later confirmation run — `stated`; while transparently reported, this suggests some result instability/flakiness in the experimental harness that isn't fully explained.
- **Single-author paper from an industry lab (Meta) using internal, de-identified telemetry-derived workloads** — the semi-synthetic aggregates cannot be independently verified or reproduced by outside readers since raw data isn't shared — `inferred`.
- **No comparison against a churn-aware or hybrid reactive+planned baseline** (e.g., a system that updates the table more frequently or blends reactive spillover with planning) — the paper only compares against static reactive baselines and its own planned approach — `inferred`.
- **Generalization beyond the tested key type (business/tenant ID) is asserted but not empirically tested** — the paper suggests tenant, document collection, or agent keys "could" substitute, but no experiments verify this — `inferred` (paper itself flags this as future/untested, bordering on `stated`).
- **The fp16 cache-pressure run showed no policy meeting the SLO at all**, so it contributes no capacity multiplier and is excluded from headline claims — `stated`, but worth flagging as a scenario where the method's practical benefit is unproven under higher memory pressure.
