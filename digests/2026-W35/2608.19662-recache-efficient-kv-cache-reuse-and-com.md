# ReCache: Efficient KV Cache Reuse and Compression for Tool-Augmented LLM Agents

**Authors:** Yichu Fang, Sitong Wei, Haozhe Hu, Xiaoyu Shen

**arXiv:** [2608.19662](https://arxiv.org/abs/2608.19662)

**Categories:** cs.CL

**Submitted:** 2026-08-20

**Relevance:** 10/10 — matched: LLM inference efficiency and long-context serving

---

## TL;DR
ReCache lets LLM agents cache the KV states of tool/skill schemas ("resources") independently of what else is in the prompt or in what order, by cutting cross-resource attention and resetting each resource's internal positions — recovering 82.3% vs. 82.4% dense Inv-F1 with a 3.655× TTFT speedup. Layered on top, contribution-guided pruning of layers/KV-head-groups plus field-aware token pruning (keep resource/argument names, argument descriptions, and the final "suffix" token) cuts KV memory 92.43% and speeds attention 1.423×, retaining ~97.5% of dense accuracy in-distribution and ~92% on unseen resources.

## First-principles breakdown

**The problem.** Agentic LLMs are given a system prompt plus a set of "resources" — tool or skill schemas (name, arguments, descriptions) — retrieved per-request from a larger pool. The same resource (e.g., a `weather.search` schema) shows up across many requests, but in different combinations and different orders alongside other resources. Standard "prefix caching" (reusing KV cache for a request that shares an identical prefix with a previous one) only works when the *exact same token sequence in the exact same position* recurs. Since resource sets and orderings vary per request, prefix caching essentially never fires here — the model re-encodes the same schema text from scratch every time, wasting prefill compute.

**Why naive fixes don't work well.** You could try to reuse each resource's KV cache independently, but two things break that: (1) in standard causal self-attention, a resource's KV vectors are computed while attending to whatever tokens happen to precede it — so its representation is entangled with neighboring resources; (2) positional encodings (RoPE etc.) bake in a resource's absolute position in the sequence, so the same resource text produces different KV values depending on where it sits. Prior work (EPIC, CacheBlend, KVLink) tries to patch this via selective recomputation or positional correction, which still costs compute and only approximates full re-encoding.

**Mechanism 1 — Resource-wise attention.** The key empirical observation (Figure 1) is that models attend much more heavily *within* a resource than *across* resources, echoing findings that positional/global-context information isn't always load-bearing. So ReCache modifies the attention mask during cache construction: tokens inside resource R_i attend only to the shared system prefix and to other tokens within R_i — not to other resources. It also resets each resource's positional indices to start at 0 (i.e., "local" positions), rather than using its absolute offset in the full prompt. Consequence: a resource's KV block becomes a pure function of the resource's own text (plus the shared prefix) — independent of what other resources are present or in what order. This turns an O(D_R²) cross-resource attention cost into O(ΣD_i²), and lets each resource's KV cache be pre-computed once and reused across arbitrary combinations/orderings. Because this differs from how the model was originally trained (full dense attention over the whole prompt), they do lightweight fine-tuning to adapt the model to this new attention/position pattern.

**Mechanism 2 — Structural pruning (layer/head-group routing).** Not all transformer layers or KV-head-groups (under grouped-query attention) contribute equally to using resource information for the final invocation decision. Rather than just measuring attention mass (which the authors show misleads), they measure *causal contribution*: starting from a config where the conversation tokens can't see any resource state (Ω=∅), they add one layer's (or one head-group's) resource visibility at a time and measure how much it reduces prediction loss on the invocation tokens ("leave-one-in" analysis). Layers/groups get a positive contribution weight if they help; the top-K layers and top-K head-groups (by weight) are retained as the only "routes" (layer × head-group pairs) allowed to see resource KV states. Everywhere else, conversation tokens use a pruned mask that hides all resource tokens. This shrinks how many of the model's internal pathways need to process/store resource KV data, without touching accuracy much, because contribution is concentrated in a small subset of layers/heads (e.g., ~20 of 36 layers capture 97.7% of contribution in the 4B model).

**Mechanism 3 — Semantic (field-level) pruning.** Even within an activated route, a resource's full token sequence (name, description, arguments, etc.) is processed. The authors note that invocation failures are dominated by wrong names/arguments, and that the *last* token of a resource (a natural "suffix" position) empirically absorbs the most attention from later conversation tokens — i.e. it acts as a summary anchor for everything before it, similar to how a sentence-embedding model uses a final token's hidden state. So ReCache keeps only: resource name tokens, argument name tokens, argument description tokens, and the final suffix token — discarding boilerplate/description fluff elsewhere. This differs from generic compressors (Gist tokens, Beacon chunk-summaries) that compress everything into learned summary vectors and lose exact identifier/argument strings that tool calls need to reproduce verbatim.

**Putting it together (Figure 2):** each resource is (a) encoded with resource-wise attention into an independent, reusable KV block; (b) exposed only along a small set of contribution-selected layer–head-group routes; (c) truncated to just its invocation-critical fields plus its suffix token. The three stages compose: (a) enables reuse across requests, (b) reduces which parts of the network must access resource KV, and (c) reduces how many tokens must be stored/processed once accessed.

**Evaluation setup.** They build a benchmark from 7 public tool/skill datasets (ToolACE, APIGEN, ToolMind, ToolRet, Toucan, SkillRouter, WildToolBench), applying "diversity-first" sampling (to avoid the model just memorizing frequently-repeated resource names/subsets) and filtering invalid/hallucinated traces, yielding an in-distribution (IND, resources seen in training) and out-of-distribution (OOD, resources unseen in training) test split. Metrics: Inv-F1 (exact match on resource name + all arguments), resource-ID F1/precision/recall, hallucination rate, plus efficiency metrics (TTFT, TPOT, attention latency, allocated KV memory). Backbones: Qwen3-4B (primary, fully fine-tuned) and Qwen3-1.7B (auxiliary, to study scale sensitivity).

## Key insights

- **Genuinely new mechanism:** resource-wise attention + local position reset as a way to make KV blocks *composition-invariant* — reusable regardless of order/combination of retrieved resources — is the core novel idea, distinguishing it from prior position-correction approaches (EPIC, CacheBlend, KVLink) that still require recomputation or positional patching.
- **Contribution-based (leave-one-in loss reduction) route selection beats attention-mass-based selection**, especially on OOD/unseen resources (e.g., Ω20,3 beats attention-based SA20,3 by 3–5 points Inv-F1 and cuts OOD hallucination from 5.1%→0.5%). This is evidence-backed via direct ablation comparison (Table 3/4), not just claimed.
- **Field-aware semantic pruning (keep name/args/desc + suffix token) clearly outperforms generic text-compression baselines** (Gist collapses catastrophically to 39.2%/9.7% Inv-F1 IND/OOD; Beacon does better but still trails). This supports the claim that structured schema compression needs domain-specific field awareness, not generic summarization.
- **Efficiency claims are well supported for the measured setup**: resource-wise attention alone gives 3.655× TTFT speedup at ~0.1–0.2 point effectiveness cost; full ReCache gives 92.43% KV memory reduction and 1.423× attention speedup, and scaling curves (Figure 4) show ReCache keeps near-constant latency/memory as resource-context length grows to 10k+ tokens, versus Dense's latency/memory blowing up.
- **Trade-off is explicit and quantified, not hidden**: full ReCache retains 97.5% of Dense Inv-F1 IND but only 91.8% OOD (Inv-F1 drops from 82.4→80.3 IND, 66.3→60.8 OOD), so the compression cost is real and larger for unseen resources — the paper reports this rather than obscuring it.
- **Structural budgets are scale-dependent**, not a fixed universal recipe: the smaller Qwen3-1.7B needs far more KV-head-groups retained (7/8) to match performance than the 4B model (3/8), suggesting the "sparsity budget" must be re-derived per model rather than assumed transferable.

## Caveats — stated and inferred

- **Stated**: Evaluation is limited to two backbones (Qwen3-4B primary, Qwen3-1.7B auxiliary); larger models weren't tested due to compute budget for full fine-tuning. Generalization of structural budgets to larger/other architectures is left open.
- **Stated**: The method requires *trainable* models (lightweight fine-tuning to adapt to the new attention/position pattern) — applying it to frozen/off-the-shelf models is explicitly left to future work. This is a real deployment constraint: you can't just bolt ReCache onto an existing served model without retraining it.
- **Stated**: ReCache assumes "relatively stable system instructions and resource schemas" reused across queries/retrieval combinations; it's not designed for highly dynamic environments where retrieval order or cross-resource dependencies matter semantically.
- **Stated (limitations section)**: explicitly says extending to larger models/architectures and to frozen-model settings remain future work — i.e., the authors flag that current results may not transfer beyond the tested regime.
- **Inferred — narrow backbone family**: All experiments use only Qwen3 variants from the same model family; no cross-architecture validation (e.g., Llama, Mistral) is shown, so it's unclear whether the observed within-resource attention concentration (Figure 1, the empirical basis for the whole method) generalizes beyond Qwen3.
- **Inferred — accuracy cost concentrated on OOD/unseen resources**: the OOD Inv-F1 drop (66.3→60.8, ~8% relative) and the fact that alternative methods degrade far more on OOD (e.g., SPEED hallucination jumps to 13.4% OOD) suggests the harder generalization case is where the method's own gains are also more fragile — worth watching if deployed with fast-evolving tool catalogs.
- **Inferred — benchmark is self-constructed**: the 7-dataset merged benchmark, diversity-first sampling, and train/test split were all built by the authors specifically for this paper (not a pre-existing standard benchmark), which raises some risk of the construction being tuned toward showcasing the method's strengths; no external/held-out benchmark from another group is used to cross-check.
- **Inferred — efficiency baselines are recent but not exhaustively covered**: comparisons include SPEED, DuoAttention-style ideas, Gist, Beacon — reasonably current methods — but there's no comparison against, e.g., production KV-cache-sharing systems (vLLM prefix caching variants, SGLang RadixAttention) under realistic multi-tenant serving loads, so real-world serving gains (beyond the reported micro-benchmarks) are not directly demonstrated.
- **Inferred — "not addressed in the paper"**: no discussion of how resource updates/versioning (schema changes over time) invalidate cached blocks, nor of memory/storage costs for maintaining a growing library of cached resource blocks across a large tool catalog at scale.
