# TreeWY: Speculative Verification for Gated DeltaNet Hybrids

**Authors:** Sneha Murthy Ghantasala

**arXiv:** [2608.20961](https://arxiv.org/abs/2608.20961)

**Categories:** cs.AI, cs.CL, cs.DC, cs.LG, cs.PF

**Submitted:** 2026-08-21

**Relevance:** 9/10 — matched: LLM inference efficiency and long-context serving

---

## TL;DR
Speculative decoding on GDN-hybrid models (Qwen3.5) normally requires snapshotting the full recurrent state at every draft token, which explodes memory and kills wide draft trees; TreeWY instead applies a tree-structured WY/UT transform to the gated delta rule so a whole draft tree verifies in one triangular solve and only the accepted state is reconstructed on commit. This cuts speculative-decoding memory 2–3x, giving up to 1.49x throughput and ~40x lower TTFT when memory is the bottleneck (costing a few percent when it isn't), and makes wider/higher-acceptance trees affordable (though not yet a throughput win).

## First-principles breakdown

**The setup: hybrid models and why they're memory-cheap normally.** Modern LLMs increasingly mix ordinary softmax-attention layers with "linear-attention" layers like Gated DeltaNet (GDN). A softmax layer needs a KV cache — one key/value vector stored per past token, so memory grows linearly with context length. A GDN layer instead compresses the entire prefix into one fixed-size matrix `S` (like an RNN hidden state) that gets updated token by token via the "gated delta rule": each new token's key/value nudges `S` by (a) decaying it slightly (`α_t`, a forgetting factor) and (b) erasing-and-rewriting whatever `S` currently predicts for this token's key, replacing it with the true value (the "delta"/correction term, weighted by `β_t`). This keeps memory flat regardless of context length — great for normal decoding.

**Why speculative decoding breaks this.** Speculative decoding speeds up generation by having a cheap "drafter" propose several future tokens at once, then having the real (target) model verify all of them in a single parallel forward pass, accepting the longest correct prefix and discarding (rolling back) the rest. For softmax layers, rollback is trivial: just drop the KV entries for rejected tokens (like moving a pointer back). But for GDN layers, the single verification pass advances the recurrent state `S` all the way through every draft token *before* you know which ones get accepted. Since `S` is a lossy, compressed summary (not a list of entries), you can't "un-mix" it after the fact. The existing fix ("full-state snapshotting," used by vLLM/SGLang today) is to save a *complete copy* of `S` after every single draft token, so you can just restore the right snapshot once you know what was accepted. For a draft of k tokens this means storing k+1 full state copies — and if the draft is a *tree* (multiple candidate continuations branching at each step, to raise acceptance rates), snapshots for different branches can't be shared, so memory scales with tree size and wide trees become infeasible.

**The core trick: WY/UT transform.** The paper's insight is algebraic: expand the recurrence and notice that the update to `S` at each step can be rewritten as a "pseudo-value" `ṽ_t` (the actual value minus what the state already would have predicted, scaled by `β_t`) added via decayed attention. If you know all the `ṽ_t` values across the draft up front, you don't need to have walked the recurrence step by step — every node's output and the final state become just weighted sums over ancestors. Laying the draft tree out in DFS pre-order (so every ancestor node has a smaller index than its descendants) turns the whole computation into one triangular linear system: `(I + diag(β)G) Ṽ = R`, where `G` is a strictly lower-triangular matrix encoding decayed key-similarity between ancestor/descendant pairs. Because it's triangular, this solves in one forward substitution — no need to materialize per-node states at all. This generalizes a known technique (DeltaNet's chain-only WY transform) from chains to arbitrary trees, and specifically extends prior tree work (STree) which only handled Mamba2's simpler *scalar* decay — GDN's transition is a scalar decay *times* a non-commuting rank-1 correction, which is the harder case this paper solves.

**Commit step.** Once verification decides which node was actually accepted, you reconstruct *only that one* state by summing the pseudo-values along its ancestor path — an O(N·d_v) object 128x smaller than a full per-node state cache (at their d_k=d_v=128 config). So instead of storing N+1 full states, you store one small pseudo-value matrix and reconstruct exactly one real state on commit.

**Engineering reality check.** A draft *chain* (branching factor 1) fits into a single fused, CUDA-graph-capturable kernel — cheap and fast. A real *tree* needs a non-causal ancestor mask that can't be replayed from a CUDA graph, forcing vLLM to fall back to slower "piecewise" execution for the whole model, not just the masked part. So today, wide trees are memory-*affordable* under TreeWY but not yet a *speed* win, because the verification kernel itself costs more than the extra acceptance buys.

## Key insights

- **Genuinely new**: a closed-form, tree-structured WY transform of the gated delta rule specifically (not just Mamba2's scalar-decay case), letting an entire draft tree verify with one triangular solve and requiring storage of only one small pseudo-value matrix rather than per-node state snapshots. The derivation is claimed to depend only on the gated-delta-rule math, not on other architectural specifics — plausible from the derivation shown, though only tested on one model family.
- **Evidence supports**: on real serving benchmarks (not just microbenchmarks) with two model scales (35B-A3B, 397B-A17B), TreeWY delivers 2–3x peak KV/state memory reduction at matched acceptance length, translating to up to 1.49x throughput and up to ~40x lower p99 TTFT specifically in memory-bound regimes, with acceptance length statistically indistinguishable from the baseline (mean |Δ| = 0.039). This is well-instrumented — Fig. 3 explicitly decomposes results by whether the baseline was memory-bound, showing the win is conditional, not a uniform speedup.
- **Weaker/partial claim**: the tree-width benefit ("wider trees become affordable") is demonstrated only as memory-flat scaling and rising acceptance length with width — the authors explicitly state this is *not yet* a throughput win, since the tree-verify kernel isn't graph-capturable yet.
- **Honest framing of prior/concurrent work**: the paper carefully positions itself relative to ReplaySSM (same triangular system, different question of *when* to materialize state — TreeWY loses a real throughput comparison to it on chains, 0.97-0.99x-ish vs ReplaySSM's 1.12-1.20x own-baseline gain) and Bole (closest concurrent, untested head-to-head since no public code). This is a system/kernel contribution layered on a fairly narrow, but real, algebraic novelty — not a new model architecture or training method.

## Caveats — stated and inferred

- **Single model family evaluated** (stated): both benchmarked models are Qwen3.5 hybrids (35B and 397B); the authors explicitly list "extending to a second model family" as future work. Generality of the "cuts across architectural detail" claim is unverified beyond GDN itself.
- **Not upstreamed / unofficial fork** (stated): implemented as a fork of vLLM's main branch, "not yet upstreamed as of this writing" — production readiness/maintenance burden unaddressed.
- **Tree mode not yet a throughput win** (stated): wider trees are memory-affordable but require falling back to slower piecewise (non-CUDA-graph) execution, so the paper explicitly reports tree results "as enabled and correct, not as a speedup."
- **Loses to a closest concurrent baseline on chains** (stated, in Appendix D): ReplaySSM achieves higher throughput gains (1.12–1.20x vs TreeWY's 0.99–1.08x) on the same chain workload; the authors attribute this to scheduling/deferred-write differences but explicitly flag this as "an attribution, not a validated claim" since they haven't prototyped the deferred-write path themselves.
- **No head-to-head against the most architecturally similar concurrent work** (stated): "Bole" is described as the closest concurrent method but no comparison was run because its paper has no linked code implementation.
- **Cross-build normalization caveat** (stated): the ReplaySSM comparison runs on different vLLM builds, each normalized to its own baseline rather than a shared one — introduces potential confounds despite the authors checking that baseline throughputs agree within 1%.
- **Correctness is approximate, not exact** (stated): bf16 production kernel matches a reference only to bf16 tolerance; token streams are "not bit-identical" to baseline — correctness is instead validated via matched acceptance length, an indirect proxy rather than exact output equivalence.
- **Greedy decoding only** (inferred): all evaluation explicitly states "greedy drafting and verification" — no results given for sampling-based (temperature/top-p) decoding, which is the more common production setting and could behave differently under the acceptance-length-matching correctness check.
- **Prefix caching disabled throughout** (stated): "All evaluations here run with prefix caching disabled" — a common production optimization is excluded, so real-world gains under prefix caching are untested.
- **Single hardware target** (inferred): all benchmarks run on B200 GPUs with specific TP configurations (TP1/TP8); no evidence given for other accelerators or parallelism strategies.
- **Fixed draft depth** (inferred): the concurrency/memory sweep (Table 1, main results) uses a fixed depth-3 MTP draft chain; deeper drafts, which would stress the snapshot problem even more, aren't swept in the primary throughput results (only width is separately swept, at depth 3 as well).
- **Compute budget modest, single-run figures** (inferred): ~85 GPU-hours total across all reported sweeps; no repeated trials or variance/error bars reported for throughput/TTFT numbers, so noise in these serving benchmarks isn't quantified.
