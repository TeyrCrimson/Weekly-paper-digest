# Beyond Binary Priorities: Multi-Tier SLA Scheduling for Large Language Model Serving

**Authors:** Anders Vestrum, Arya Raeesi, Hanna Roed

**arXiv:** [2608.16336](https://arxiv.org/abs/2608.16336)

**Categories:** cs.AR, cs.DC, cs.LG

**Submitted:** 2026-08-17

**Relevance:** 9/10 — matched: LLM inference efficiency and long-context serving

---

## TL;DR
This paper extends Llumnix's binary (high/normal) priority scheduler for LLM serving into a configurable K-tier system with exponentially decaying per-tier "headroom," implemented inside the Vidur simulator. Sweeping K from 1–10 across three synthetic priority distributions, the authors find K=4 tiers gives the best cost-latency tradeoff, with up to 8.3x prefill mean speedup and 3.1x P99 speedup over an INFaaS baseline. All results are simulation-only (Vidur, not real GPUs), and the paper's own baseline comparison in Section 5.2 shows aggregate latency differentiation is largely invisible at the tested load, undercutting some of the headline claims.

## First-principles breakdown

**The underlying problem: scheduling LLM inference requests across GPU replicas.** LLM inference has two phases: *prefill* (processing the input prompt in one compute-bound parallel pass) and *decode* (generating output tokens one at a time, autoregressively, bounded by memory bandwidth). A request's total runtime and memory (KV-cache) footprint aren't known in advance because output length is unpredictable. This makes classic scheduling hard: you can't just estimate job size and use standard queueing theory.

**Why per-replica schedulers aren't enough.** Systems like vLLM, Orca, and Sarathi-Serve improved *single-GPU-replica* efficiency: Orca introduced "continuous batching" (making batching decisions every generation step instead of per-request, avoiding head-of-line blocking), vLLM added PagedAttention (block-based virtual memory for the KV-cache, cutting memory waste), and Sarathi-Serve added chunked prefill (splitting long prompts into pieces interleaved with ongoing decode work, so a big new request doesn't stall everyone else's token generation). But none of these systems can move a request that's already been assigned to an overloaded replica — dispatch is "one-shot." If a cluster has multiple replicas and load becomes imbalanced or memory gets fragmented, per-replica schedulers can't rebalance.

**Llumnix's contribution (prior work, not this paper): live migration and the "freeness" metric.** Llumnix sits above multiple replicas as a global scheduler. It defines a *freeness* score per replica — essentially spare KV-cache capacity accounting for both real usage and a "virtual usage" that includes reserved headroom for high-priority requests. If freeness is negative, the replica is effectively overloaded, triggering migration: a request's KV-cache blocks are copied piece-by-piece to a less-loaded replica while the request keeps running on the old one, with only a brief handoff pause. This single mechanism drives four functions: load balancing, defragmentation, priority isolation, and auto-scaling. But Llumnix only supports two priority classes.

**This paper's mechanism: generalizing headroom to K tiers.** The key equation is a headroom budget per tier: Hp = M · h_max · e^(−λp), where M is a replica's KV block capacity, h_max=0.20 reserves 20% of capacity for tier 0, and λ controls how fast headroom decays for lower tiers (so background/low-priority tiers get ~0 reserved headroom). Crucially, the *entire* budget Hp is charged to a replica's virtual usage as soon as *any* request of that tier is present — not per request — so even one critical request can make a replica look "full" to the scheduler and discourage dumping more normal-priority work there. Dispatch is done in strict priority order (tier 0 first, FCFS within a tier), and the scheduler tracks two separate freeness values: "full freeness" (includes headroom, used for dispatch/migration) and "normal-priority freeness" (excludes headroom, used only for auto-scaling), so that priority isolation doesn't get mistaken for genuine capacity shortage and trigger unnecessary scale-out.

**Evaluation approach.** Rather than building this in a real GPU cluster, they implement it as a new scheduling policy inside Vidur, a discrete-event simulator (from Microsoft Research) that predicts latency/throughput/memory from profiled real-GPU operator runtimes without needing physical hardware. They also reimplement INFaaS (a cost-based global router with no migration, used as a baseline) and Llumnix's Llumlet (per-replica logic) inside Vidur. They test three synthetic priority distributions — uniform (equal traffic per tier), Gaussian (weighted toward middle tiers), enterprise (10% critical, ~70% mid, 5-20% background) — sweeping K from 1 to 10 and request volumes of 10K/15K.

## Key insights

- **Claimed and evidence-supported:** Extending Llumnix's binary priority model to K arbitrary tiers with exponential headroom decay is a reasonably natural generalization, and the paper does show (Section 5.1, Figures 5/8/9) that tiers get differentiated latency (tier 0 much faster TTFT than lower tiers) at K=3 and K=5 under all three distributions — this is the core mechanism working as intended.
- **Claimed: K=4 is the sweet spot.** This is consistently observed across all three distributions and both request scales in their speedup tables (Table 2–4) — a genuine, reproducible-within-their-setup empirical pattern, though it's an optimum over a narrow, self-defined design space (only headroom fraction/decay and priority count are varied).
- **Claimed: large speedups over INFaaS (8.3x prefill mean, 3.1x P99, 46–68% cost/latency improvement) exceeding original Llumnix's reported numbers.** The authors attribute this to migration-driven load balancing outperforming INFaaS's slower reactive cost model. This is plausible but is a comparison against their own reimplementation of INFaaS, not the original, and is explicitly flagged by the authors as not directly comparable to the original paper's hardware results (Section 6.4).
- **Useful nuance surfaced by the authors themselves:** aggregate (pooled-across-tiers) P50/P90/P99 latency is a misleading metric for priority-scheduler effectiveness, because gains for high tiers and losses for low tiers cancel out in the aggregate. The paper's own Figure 6 scheduler-comparison experiment runs below saturation (QPS=10) specifically so it does *not* show per-tier differentiation — it only shows "baseline parity" (no aggregate regression), which is a much weaker and different claim than "priority scheduling works well," and the paper is honest about this distinction (Section 6.2, Section 5.2 discussion).
- **Priority-granularity tradeoff concept:** more tiers = better differentiation but more cumulative headroom "tax" on virtual usage, reducing effective batching capacity — a reasonable qualitative mechanism explanation for why very high K underperforms K=4, though it's more asserted than rigorously isolated via ablation.

## Caveats — stated and inferred

- **Simulation-only, no hardware validation** (stated): All results come from Vidur, which "simulates GPU computation without capturing all hardware effects such as PCIe bandwidth for KV migration and CUDA kernel launch overhead" (Section 6.4/6.5). Migration costs specifically depend on real interconnect bandwidth, which isn't modeled.
- **Not the original Llumnix/INFaaS implementations** (stated): "we implemented our own versions of Llumnix and INFaaS adapted to Vidur's architecture, which may differ in subtle ways from the original implementations," and the workload traces from the original paper were unavailable — so comparisons to Llumnix's original reported numbers are explicitly acknowledged as not apples-to-apples (Section 6.4).
- **Synthetic priority distributions and synthetic request-length distribution** (stated/inferred): the three priority distributions (uniform, Gaussian, enterprise) and the token-length table (Table 1) are self-constructed rather than drawn from real production traces; "enterprise" traffic mix percentages appear to be assumptions rather than measured (inferred, since no citation/dataset is given for these specific percentages).
- **The central scheduler-comparison figure doesn't actually demonstrate the claimed benefit at the tested load** (stated by authors): Section 5.2 explicitly says the QPS=10 benchmark "is deliberately... not designed to demonstrate per-tier latency differentiation" and that headroom "rarely binds" at that load — meaning the flagship cross-scheduler comparison (Figure 6) mainly shows no-regression, not the priority mechanism's value. This is a significant limitation of the evidence presented, honestly flagged but easy to miss given how the abstract frames results.
- **Missing per-tier breakdowns at high/production load** (stated): the authors identify as future work that "demonstrating the expected per-tier latency split... would require both higher utilization and reporting per-tier breakdowns separately" — meaning the paper's most policy-relevant scenario (heavy load) is not actually shown with per-tier granularity.
- **Static/non-adaptive headroom schedule** (stated): headroom decay (h_max, λ) is fixed a priori and not tuned adaptively to observed SLO violations; the authors list "adaptive headroom allocation" as future work.
- **No starvation protection / fixed tier assignment** (stated): low-priority requests can be starved indefinitely since tier assignment is fixed at arrival with no MLFQ-style promotion; listed explicitly as a limitation.
- **Limited/no ablation on headroom hyperparameters** (inferred): h_max=0.20 and the decay λ are fixed constants across all experiments; there's no reported sweep of h_max or λ independent of K, so it's unclear how sensitive the "K=4 is optimal" conclusion is to this specific headroom schedule choice rather than being fairly attributable to K alone.
- **Single-metric "optimum" claim across a fairly coarse grid** (inferred): K=4 being "consistently optimal" is drawn from only three K values compared per table (3, 4, 5) in the main speedup tables, even though the introduction and Figure 6 discuss sweeping K from 1–10 — the fine-grained sweep (K=1–10) is only shown for the weaker aggregate-parity metric, not for the cost/speedup metrics that support the "K=4 is optimal" headline claim.
- **Author affiliation / venue check not addressed in the paper**: no venue or peer-review status is stated in the provided text beyond an arXiv identifier.
