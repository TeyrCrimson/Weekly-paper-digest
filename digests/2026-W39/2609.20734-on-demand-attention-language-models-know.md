# On-Demand Attention: Language Models Know When to Recall

**Authors:** Haibo Feng, Ruiqi Liang, Hanyang Peng, Shiqi Yu

**arXiv:** [2609.20734](https://arxiv.org/abs/2609.20734)

**Categories:** cs.CL

**Submitted:** 2026-09-17

**Relevance:** 10/10 — matched: LLM inference efficiency and long-context serving

---

## TL;DR
On-Demand Attention (ODA) trains a small "recall head" that reads a frozen LLM's own hidden states to decide, at each decoding step, whether the current token actually needs full (global) attention or can be handled with cheap local attention alone. The pretrained weights stay untouched, the full KV cache is always kept around for later use, and a GPU-side conditional-execution implementation in vLLM turns the resulting reduction in "global reads" into real decoding speedups (up to ~2x at 128K context) with near-full-attention quality on RULER/LongBench.

## First-principles breakdown

**The problem.** In a transformer, generating each new token normally involves "full attention": the model compares the current query against every previous token's key/value pair in the KV cache. As the context grows to tens or hundreds of thousands of tokens, this per-step cost grows linearly per step and quadratically over a full generation (O(n) per step accumulating to O(n²) over n steps), making long-context decoding expensive. A cheaper alternative is "local attention" (as in StreamingLLM): only attend to a few initial tokens plus a recent sliding window, which is O(1) per step. The problem is local attention silently throws away information that might matter for the current prediction — but it's used uniformly, without regard to whether the current step actually needs distant context.

**Why prior approaches fall short.** Existing "dynamic" methods (e.g., AHA, L2A, Switch Attention, LoGo) bake the local/global decision into new training that jointly learns language modeling and attention allocation, or require continued pretraining/architecture changes. The authors instead ask: does a pretrained, frozen model already "know" — in its existing hidden states — whether it would benefit from a global (full) attention read at this step, before that read is even computed? If so, you could bolt on a tiny decision module without touching or retraining the backbone.

**Their mechanism, step by step.**
1. Define "access gain" g_t: run both Local and Full attention from the same history at a step, and measure how much Full reduces the negative log-likelihood of the actual next token compared to Local (Eq. 4). Positive gain = Full genuinely helps at this step; negative/zero = Local is fine.
2. Collect training data: for many steps, compute this paired gain using a frozen backbone (teacher supervision), then subtract a fixed "cost" penalty λ per Full call (so recall must earn its computational cost) and apply a signed-log squashing transform to get a regression target y_t.
3. Train a lightweight "recall head" R_ψ — a small feedforward network (~28M params, tiny relative to the backbone) — to predict a scalar score q_t from three things already available after a Local step: (a) the hidden state carried from the previous step, (b) the embedding of the current input token, (c) the current step's Local hidden state. This is trained with Huber regression against y_t. Crucially, only this head is trained; the LLM's weights are frozen.
4. At inference: every step first computes Local (cheap). The recall head scores q_t from the inputs above. If q_t exceeds a threshold θ (default 0), the step is *recomputed* using Full attention from the same pre-step history (the extra compute cost), and that result is used instead; otherwise the cheap Local result is kept. Either way, the current token's key/value is appended to the complete, ever-growing KV cache — so even after many skipped (Local-only) steps, older information remains available for future recall.
5. Efficiency: since Local is O(1)/step and Full is O(n)/step, and only a fraction ρ of steps trigger Full, total compute is roughly (1−ρ)·F_Full − (F_Local + F_head), which favors ODA more as context length n grows (fixed ρ). They implement this branching as GPU-side conditional execution inside vLLM (rather than naive Python branching) to avoid synchronization overhead eating the savings, using CUDA graphs.

## Key insights

- **Claimed and supported**: A frozen model's decoding states already carry information predictive of whether global attention would help *before* that global computation is done — demonstrated via readout/AUROC experiments (Section 3.4) and offline ranking experiments (Fig. 2b, 4) using a frozen backbone, not just anecdote.
- **Claimed and supported**: The recall head recovers most of the Full-vs-Local performance gap while cutting global calls substantially (e.g., 98.8% of the gap recovered on RULER16K with only 41.6% Full calls on Qwen3-1.7B), and this generalizes across model families/scales (Qwen3-1.7B/8B, hybrid Qwen3.5-2B, Gemma-4-12B-it), each with its own separately trained head — genuinely useful because it needs no backbone retraining.
- **Claimed and supported**: Timing matters, not just call frequency — a random-routing control (Random) at the *same* Full-call rate scores far worse (32.79 vs. ODA's 88.96 on a 5-task subset), showing the learned policy is doing real work, not just spending a budget.
- **Claimed and supported, with nuance**: The recall signal is distinct from simple uncertainty/entropy of the Local prediction — it beats entropy-based ranking on AUROC within the Local-incorrect subset, and it also correctly predicts benefit at positions where both branches already get the top-1 token right (i.e., it's about probability-mass improvement, not just correctness flips).
- **Practical engineering contribution**: real vLLM decoding speedups (1.98x at 128K/12.5% Full-call rate) are demonstrated, not just FLOPs estimates — though speedups reverse at short contexts (15.8% slower at 4K), correctly flagged by the authors as a context-length-dependent tradeoff.
- Ablations (Table 2) show input composition matters a lot to the *learned policy's operating point* (which streams the head sees changes Full-call rate/quality substantially), but the paper is explicit these are not budget-matched comparisons, so they show sensitivity, not a clean "which input matters most" ranking.

## Caveats — stated and inferred

- **stated**: A "complete anonymous implementation release remains pending" — code/checkpoints not yet available for independent verification.
- **stated**: Complete GPU-hours and total training cost (including frozen-backbone feature/label computation) are "not yet available" — the reported 28.3M-parameter head size understates true training cost, and the authors explicitly say they do not claim a measured total-training-cost advantage over other methods.
- **stated**: Several results in Table 1 are marked with dashes ("measurements not yet available") — e.g., LongBench v1 for Qwen3-8B/Qwen3.5-2B/Gemma are incomplete, so cross-model comparisons are partial.
- **stated**: The AUROC advantage of the recall head over simple Local-entropy is only established on the Local-incorrect subset with a resolved confidence interval; across *all* positions the AUROC difference is "unresolved" (interval likely crosses zero), so the discrimination advantage is narrower than the headline framing suggests.
- **stated**: An independent Qwen3.5 pilot (Appendix B.6) explicitly "does not establish the same failure-subset discrimination advantage" seen for Qwen3 — i.e., a key claimed insight fails to replicate on a second model in their own appendix.
- **stated**: Efficiency measurements (FLOPs and vLLM throughput) use "a fixed continuation and prescribed recall schedule" (artificially set Full-call rates of 0/12.5/25/50/100%) rather than the actual learned policy's dynamic behavior — i.e., quality evaluations and speed evaluations were never jointly measured on the same run. The paper states "joint task quality and speed for the same learned policy... have not been measured."
- **stated**: Speed gains reverse at short context (4K tokens, 15.8% slower than native Full) — the method has a real regime where it hurts, not just a uniform win.
- **stated**: Recall predicts relative benefit, not Local errors — the paper itself cautions against interpreting the head as an error-correction/confidence mechanism, since it can invoke Full even when Local's top-1 answer is already correct (or vice versa fail to invoke it when Local is wrong).
- **stated**: Multiple appendix caveats about non-equivalence of comparisons: e.g., the input-ablation heads (Table 2/9) are "natural zero-threshold results, not budget-matched comparisons"; supervision-objective comparisons (Table 13) are at different "natural operating points," not matched access frequency. This weakens the strength of several internal ablations as clean causal evidence.
- **stated**: Longer training does not monotonically improve the quality–access tradeoff (the H+E+L head's Full-call rate swings from 76%→50%→71% over more updates with scores staying flat/noisy) — instability in what's being learned is acknowledged but not resolved.
- **inferred**: Backbones tested are moderate scale (1.7B–12B); no evidence given for very large (70B+) production-scale models, so claims about "practical" gains for the largest deployed LLMs are unverified.
- **inferred**: Only two model families (Qwen, Gemma) evaluated; each uses a "separately trained recall head" with no head-transfer test across models — so the method's cost (retraining a head per backbone/checkpoint) isn't amortized or characterized, and generalization to arbitrary new pretrained models is unproven.
- **inferred**: The main quality benchmarks (RULER, LongBench) are synthetic/proxy long-context tasks (needle-in-haystack style, QA); it's not addressed in the paper whether gains hold on real open-ended agentic/reasoning workloads mentioned as motivation in the introduction.
- **inferred**: The λ (Full-call cost penalty) and θ (decision threshold) are manually chosen hyperparameters reported "configuration-specific" in an appendix; no principled or automatic method for setting them per-deployment cost target is discussed, meaning practitioners must retune per use case — a real deployment friction not emphasized in the main text.
- **inferred**: The FLOPs/speedup numbers assume batch size one, single-GPU, a specific A100 setup — multi-request batching, memory pressure, and interaction with other serving optimizations (e.g., continuous batching at scale) are not evaluated, which the paper's own limitations section gestures at ("multi-request batch scaling have not been measured").
