# Learning Context-Free Grammars for Grammar-Constrained Decoding via Declarative Agentic Programming with Guarantees

**Authors:** Kevin Cheang, Geoff Hulette, Rahul Kumar, Felipe R. Monteiro, Federico Mora, Robin Salkeld, Lin Tan, Serdar Tasiran

**arXiv:** [2608.05493](https://arxiv.org/abs/2608.05493)

**Categories:** cs.PL, cs.AI, cs.CL, cs.SE

**Submitted:** 2026-08-06

**Relevance:** 9/10 — matched: Pre-inference input sanitization for generation stability

---

## TL;DR
Autogrammar is an LM-driven agent that automatically infers context-free grammars for esoteric DSLs (e.g., cloud query languages) from execution logs and documentation, so those grammars can drive grammar-constrained decoding (GCD) and stop LMs from emitting syntactically invalid programs. The agent's control logic is formalized as a Kripke structure whose nondeterministic transitions are resolved by an LM, with linear temporal logic (LTL) constraints used to declaratively restrict/optimize its behavior (e.g., a time-bounded variant cuts runtime 3.8x with no significant precision loss). Across three real DSLs, Autogrammar-generated grammars beat a state-of-the-art grammar-induction baseline (Arvada) and LM-prompting baselines by large margins, and plugging them into GCD improves end-to-end task success on 8/10 real tasks, matching a professionally maintained grammar.

## First-principles breakdown

**The underlying problem.** LMs increasingly need to emit strings in domain-specific languages (DSLs) — e.g., a CloudWatch Logs Insights query, a Dynatrace query, a cron expression — as part of calling external APIs. These DSLs are "low-resource": there's little training data for them relative to Python or SQL, so LMs frequently generate syntactically broken programs. The paper backs this up with a concrete finding: scanning 416 AWS Boto3 services, 23% expose a string parameter that must conform to some DSL, and there are at least 59 distinct DSLs in AWS alone.

**Why grammar-constrained decoding (GCD) is the standard fix, and why it's blocked here.** GCD restricts an LM's token-by-token output so every generated string is guaranteed syntactically valid (e.g., by rejecting tokens that can't extend to a valid parse, or by only sampling from strings a parser accepts). This is well-studied (PICARD, Willard & Louf's FSM-based approach, Park et al.'s distribution-preserving algorithm). But every GCD technique needs a formal syntactic specification as input — typically a context-free grammar (CFG). For the "long tail" of proprietary/vendor DSLs, no such grammar exists publicly, and hand-writing one is expensive and error-prone (the paper cites evidence that even writing regexes, a simpler formalism, is hard for engineers). So the real bottleneck isn't decoding — it's obtaining the grammar in the first place.

**Why classic grammar-induction methods don't fit either.** Formal grammar inference (Gold's identification-in-the-limit, Angluin's L*, Clark & Eyraud) and practical systems (GLADE, Arvada) typically assume a "membership oracle" — something you can query with arbitrary candidate strings to ask "is this valid?" For real DSLs behind authenticated, rate-limited, possibly state-mutating cloud APIs, you can't freely probe with garbage inputs. So these active-learning approaches (which generate candidate strings and query an oracle to refine the grammar) are infeasible in this setting.

**What Autogrammar does.** It's a "passive learner": instead of querying a live oracle, it works from data you already have — execution logs (pairs of programs known to have succeeded/failed when actually run) and (optionally) API documentation. It repeatedly proposes a candidate CFG, tests it against the training examples, and refines it (adds/removes training examples, or generates new test strings from documentation to probe weaknesses) until it finds a grammar that accepts all positive examples and rejects all negative ones, or hits a resource limit.

**The Kripke-structure/LTL framing (the paper's methodological contribution).** A Kripke structure is a standard model-checking formalism: a set of states, initial states, a transition relation between states, and labels (atomic propositions) on states — used to reason formally about system behavior over time. The authors model Autogrammar's execution as a Kripke structure: the "state" holds the training data, documentation, and set of candidate grammars discovered so far; the "transition" is a choice among a fixed toolkit of actions (`add_g`: propose a candidate grammar, `eval`: test a grammar against examples, `add_s`/`del_s`: edit training data, `gen_ts`: generate new test strings from docs, `return`: finish). Crucially, at each step the *choice* of which action to take is nondeterministic in the formal model, and this nondeterminism is resolved by querying an LM — the LM picks the action. Linear temporal logic (LTL) — a logic with operators like G ("globally/always"), F ("eventually"), X ("next"), U ("until") — is then used to add *constraints* on top of this: e.g., "never evaluate the same grammar twice without changing the data first" (avoids wasted repeated work), "never repeat test-generation on the same grammar" (avoids unproductive loops that LMs are known to fall into), or "if a time budget is exceeded, return immediately." Practically, these constraints are enforced via rejection sampling: if the LM tries to pick an action that would violate an LTL formula, the system just asks it to choose again. This gives you two provable properties: a *safety* guarantee (the agent's tools never let it touch test/held-out data during learning) and a *progress* guarantee (certain wasteful behaviors are structurally forbidden). The framing lets the authors create four variants of the same agent purely by swapping which LTL formulas are attached — "Unlimited" (few restrictions), "Performance" (adds efficiency/time-bound constraints), "No Documentation" and "No Execution Data" (ablations that remove access to one input type on top of Performance).

**Deployment.** Once a grammar is learned, it's handed to any existing GCD "validator" tool, and a separate "downstream" LM (the one actually trying to solve user tasks) uses that validator as a post-condition/guard when generating DSL programs, retrying up to a fixed number of attempts if the check fails.

## Key insights

- **Reframing agent design as declarative temporal-logic-constrained model checking, not prompt engineering.** The genuinely novel methodological idea is expressing an LM agent's action space as a Kripke structure and using LTL to declaratively add/remove behavioral constraints, rather than hand-coding control flow or relying purely on prompting. The paper shows this is not just conceptually elegant but practically useful: switching from "Unlimited" to "Performance" constraints (just changing a few LTL formulas) cuts execution time 3.8x with no statistically significant precision loss — a concrete, measured payoff from the declarative framing, not just a theoretical nicety.
- **Passive (log+doc-based) grammar learning beats active oracle-based learning here, contrary to the general active-learning literature.** The claimed contribution — near-perfect precision (91–100%) on held-out data via 5-fold cross-validation across three real DSLs — is well supported by direct comparison. Against Arvada (an oracle-based state-of-the-art baseline) it wins by a huge margin (0.999 vs 0.025 precision on CWIL); against two LM-only baselines (grammar generation from docs/examples with no agentic scaffolding) it wins by roughly an order of magnitude on two of three DSLs. This is evidence the *agentic iterative refinement process* itself (not just "give an LM the docs") is doing the work.
- **Execution data matters far more than documentation.** Removing documentation causes little to no significant degradation on 2/3 DSLs; removing execution data causes severe degradation (e.g., CWIL precision collapses from ~0.99 to 0.11). This is a genuinely useful, somewhat counterintuitive practical finding for anyone building similar systems — invest in log collection, not doc scraping.
- **End-to-end payoff, not just intrinsic grammar quality.** Autogrammar-generated grammars plugged into a GCD pipeline significantly improve real task success rate (measured via actual boto3 API call success) on 8/10 tasks versus no constraint, and match/exceed a professionally-maintained grammar on the same benchmark. This is the strongest practical claim, and it's tested end-to-end across 6 different LMs (including non-Claude models: Nova, Qwen, DeepSeek), which is good generalization evidence for the "downstream" half of the pipeline. However, note the grammar-learning experiments (RQ1-4) only used Claude Opus for Autogrammar itself — generalization of the *learning* agent to other backbone LMs is untested.
- **Distinguishing claim from evidence:** the paper explicitly hedges that the Kripke/LTL framework "will generalize beyond learning context-free grammars to other agentic domains... though further empirical study is required to confirm this" — this generalization claim is *not* evidenced, only asserted.

## Caveats — stated and inferred

- **Threats to validity from data/task bias (stated).** Authors explicitly acknowledge that if the log data doesn't exercise the full breadth of a DSL, Autogrammar may only learn a subset of the language, and that the 10 end-to-end tasks may not represent all agent usage.
- **Arvada baseline may be poorly suited to this domain, weakening the comparison's generality (stated, with explanation).** The paper itself explains that CloudWatch is "deliberately permissive" (accepts near-arbitrary text), which specifically breaks Arvada's bubble-and-merge algorithm that relies on negative examples to find structure. The authors admit Arvada "performs exceptionally well" in other settings — meaning the dominant win over Arvada may be partly an artifact of DSL choice rather than a universal result. Also, Arvada was only evaluated on 1 of 3 DSLs (CWIL) because a ground-truth grammar was needed and wasn't available for DQL/DSS.
- **Recall is not optimized for and sometimes low (stated).** The paper explicitly prioritizes precision "because it is compatible with the goals of GCD," but reported recall is often mediocre-to-poor (e.g., CWIL recall as low as 0.176–0.584 across variants). A grammar with low recall could reject many *valid* programs, which matters for real usability but is underexplored relative to precision.
- **Statistically significant recall drop under performance constraints for CWIL (stated).** The "Performance" (time-bounded) variant that the paper otherwise touts as a win explicitly costs recall for at least one DSL, which is a real trade-off, not just a strict improvement.
- **Single-organization, internal data (inferred).** The execution logs (tens of thousands of "internal API calls") appear to be proprietary/internal to the authors' organization (Amazon), and the "professionally maintained grammar" comparison and CloudWatch documentation access likely benefit from insider access not available to external practitioners trying to replicate this on arbitrary third-party DSLs — potentially limiting external validity of the reported ease/quality of grammar learning.
- **Grammar-learning agent evaluated with a single LM backbone (inferred).** RQ1–RQ4 (grammar quality, ablations, baseline comparisons) all use only Claude Opus 4.6 as Autogrammar's underlying LM; only the downstream/deployment evaluation (RQ5) varies the LM. It's unclear whether Autogrammar's strong results depend on using a top-tier model for the learning phase.
- **Small negative-example counts for some DSLs (inferred).** DSS has only 17 negative examples out of 838 total; such scarce negative data could make cross-validation precision/recall estimates noisy or unstable, which is consistent with the notably higher variance (std) reported for DSS in Table 1/2 relative to CWIL/DQL.
- **"Near perfect precision" claim is DSL-dependent (inferred from data, understated in framing).** DSS precision under "Unlimited" is 0.910 ± 0.124 — a wide standard deviation and meaningfully below "near perfect" — yet the abstract and RQ1 summary characterize results broadly as "near perfect precision," which slightly overstates the weakest of the three cases.
- **Cost/compute of the "Unlimited" variant is high (stated numerically, not framed as a limitation).** Average 461 minutes per CWIL grammar run under Unlimited settings is substantial; while Performance-constrained variants fix this, the paper doesn't discuss compute/token cost in dollar terms or compare total LM API cost against the value of a hand-written grammar.
- **Generalization of the Kripke/LTL agent-programming framework beyond grammar learning is asserted, not demonstrated (stated as future work).** The authors explicitly say confirming this "requires further empirical study" — readers should not treat this as validated.
- **No ablation on the specific LTL constraints' individual contribution (inferred).** The paper compares four bundled configurations (Unlimited/Performance/No-Doc/No-Exec) but doesn't isolate which individual LTL formulas (e.g., the anti-repeat-eval constraint vs. the time bound) drive the 3.8x speedup or the safety/progress guarantees — it's a package comparison, not a per-constraint ablation.
