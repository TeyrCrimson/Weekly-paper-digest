# Every Cache Entry Earns Its Place: Global Allocation of Resolution and Coverage for KV Cache Compression

**Authors:** Haolin Tian, Yuzhe Liu, Tonghan Wang

**arXiv:** [2608.07001](https://arxiv.org/abs/2608.07001)

**Categories:** cs.LG

**Submitted:** 2026-08-07

**Relevance:** 9/10 — matched: LLM inference efficiency and long-context serving

---

## TL;DR
GraceKV reframes KV-cache compression as a single global resource-allocation problem: instead of applying fixed per-layer/head eviction or merging rules, it builds a tree of progressively coarser prototypes over each (layer, KV-head, context-slot) unit and lets "add coverage" vs. "split for resolution" operations compete for a shared token budget by marginal utility. It requires no training, runs entirely on GPU, and reportedly wins 24/32 (abstract) or 25/32 (results text) benchmark settings across LongBench/RULER, staying robust up to 128× compression. The core claim is that letting cache budget flow freely across layers/heads/regions—rather than pre-fixing allocation granularity—better balances "see everything roughly" vs. "see the important parts exactly."

## First-principles breakdown

**The problem.** LLMs cache Key/Value vectors for every past token so they don't recompute attention at each decoding step. As context grows, this KV cache grows linearly in memory and must be read at every step, making it a bottleneck for long-context inference (memory footprint + memory-bandwidth/latency).

**Why prior approaches fall short.** Two families exist:
- *Token eviction* (H2O, StreamingLLM, SnapKV, PyramidKV, etc.): keep some tokens exactly, drop the rest entirely. A token is either fully present or fully gone — no partial/approximate representation, so dropped regions vanish from later attention.
- *KV merging* (CaM, KVMerger, AsymKV): average multiple tokens' K/V into fewer "prototype" entries, retaining partial information for more tokens but blurring precision.

Both typically fix the compression rule and/or the per-layer/per-head budget *in advance* (e.g., "each head keeps X% of tokens"), which prevents cache capacity from moving fluidly to wherever it's most needed. So a head/region that turns out to need fine detail can't "borrow" budget from a head/region that could tolerate a coarse summary.

**GraceKV's mechanism, step by step:**
1. **Slot segmentation via curvature.** Treat the sequence of hidden states as a trajectory; measure how much the trajectory "turns" at each token (a curvature score, computed from cosine dissimilarity of before/after windowed means, combined across layers/scales and with token surprisal). High curvature = likely semantic boundary. Dynamic programming then cuts the context into slots at these boundaries (length 16–128 tokens), so merged regions inside a slot are semantically coherent.
2. **Atomic units and prototype trees.** For every (layer, KV-head, slot) triple — the "atomic unit" — build a binary tree. The root is one prototype summarizing the whole slot; leaves are the original per-token K/V entries; internal nodes are prototypes for sub-intervals. A "frontier" (a set of non-overlapping nodes covering the slot) defines the current representation: an empty frontier = the slot is dropped, root only = one coarse summary, deeper frontier = finer resolution, all leaves = exact (no compression).
3. **Two operations compete for budget.** *Add* = introduce a new tree's root (gain: expands *coverage* to a previously-unrepresented slot). *Split* = replace a frontier node with its children (gain: improves *resolution* in an already-covered region). Each operation has a cost in physical cache entries (Add costs 1; Split costs children-count minus 1).
4. **Utility scoring — "value flow."** Each token gets a relevance score by measuring how much attention probes from the question/sequence end actually attend to it (direct relevance), plus a multi-hop propagation step over the attention graph (to catch indirectly relevant "bridge" tokens, e.g., multi-hop QA chains). These token values aggregate bottom-up into node values. Separately, "prototype distortion" measures how much error a coarse prototype introduces versus exact attention output (both attention weights and value aggregates), weighted by how much attention mass that region actually receives (so rarely-attended regions with big local error don't get inflated priority). Node/head sensitivity (how much a KV head's output actually influences the final output via output-projection weights) further scales utility.
5. **Budget flow — global greedy allocation.** All candidate Add/Split operations across all (layer, head, slot) atomic units are placed into one shared priority queue, ranked by utility-per-cost. The system greedily executes the highest-utility legal operation (respecting prerequisite ancestor operations) until the budget is exhausted. This is what makes allocation "global" — a head that needs many fine-grained tokens in one region can take budget away from a head that's fine with one coarse summary elsewhere.
6. **Singleton floor.** Greedy marginal allocation can undervalue a few extremely high-value tokens (non-smooth gains). GraceKV reserves a small budget to preserve some tokens as exact singletons outside this greedy competition.
7. **Output.** Whatever nodes remain in the frontier across all trees are physically materialized as the compressed KV cache (ragged across layers/heads) — this is a real compressed cache, not a masking trick. At compression ratio 1×, it recovers exactly FullKV.

## Key insights

- **Genuinely new framing:** unifying eviction (drop) and merging (coarse prototype) as two ends of one continuum inside a tree, and turning "how much resolution where" into one global combinatorial-optimization/greedy-allocation problem instead of fixed per-layer/head quotas. This is the paper's main claimed contribution and is architecturally distinct from cited baselines (PyramidKV/Ada-KV allocate budgets at layer/head level but still with predefined hierarchy).
- **Evidence supports:** on their benchmarks (LongBench, RULER; Qwen2.5-7B and Llama-3.1-8B), GraceKV is competitive-to-best across a wide range of compression ratios (4×–128×) and shows smoother degradation than baselines that collapse on specific tasks (e.g., H2O/CaM/D2O fail badly on RULER Retrieval; merging-heavy methods lag on Aggregation vs Retrieval trade-offs that GraceKV balances better).
- **Efficiency claim supported by data:** at 30K context, memory drops ~74–92% vs FullKV at 4×/8×/16×, with ~1.7× decode-latency advantage over FullKV at long context, and one-time construction overhead ~2s / ~8% peak memory.
- **Note an internal inconsistency:** the abstract/intro states "24 of 32 settings" and "20 of 24 LongBench settings," while the Main Results section states "21 out of 24" and "25 out of 32." This is a discrepancy in the paper itself, not just a reporting choice by us — worth flagging rather than picking one number as ground truth.
- Ablations (Table 3) indicate Multi-Resolution and Global Allocation contribute the most, giving some support that the paper's central mechanisms (not just incidental engineering) drive the gains — though effect sizes are small in absolute terms (mostly <3 F1/Rouge points).

## Caveats — stated and inferred

- **No global optimality guarantee (stated).** The allocation is a greedy approximation to an NP-hard-flavored combinatorial problem; authors explicitly say it "cannot guarantee global optimality."
- **One-time construction overhead (stated).** ~2s and ~8% peak memory overhead after prefill, not yet optimized with fused/hardware-specific kernels; benefits only amortize with longer generation or cache reuse.
- **Cache not question-portable (stated).** The compressed cache is conditioned on the specific question/probe set used during construction; authors explicitly warn it should not be reused for a different question over the same document without recomputing relevance-dependent stages.
- **Single-run benchmark tables, no variance/error bars reported (inferred).** The paper reports single point-estimate scores across many settings; no confidence intervals, seeds, or repeated-run statistics are shown, so it's unclear how much of the "24/32" or "25/32" win margin is noise, especially given many wins are by <1 point (e.g., RULER retrieval 87.25 vs 87.00 for SnapKV).
- **Discrepant win-count claims within the paper itself (inferred).** Abstract says 24/32 overall and 20/24 LongBench; Main Results text says 25/32 and 21/24. This internal inconsistency isn't addressed and suggests the headline numbers weren't fully reconciled across drafting.
- **Baselines' hyperparameters/tuning not detailed (inferred).** The paper states baselines are evaluated "under a unified framework" with "identical cache budgets," but doesn't describe whether each baseline's own hyperparameters (e.g., window sizes, layer-specific settings) were tuned to match its original paper or left at some default — a common source of unfair baseline comparisons in this literature.
- **All backbones are mid-size open models (inferred).** Main results use Qwen2.5-7B-Instruct and Llama-3.1-8B-Instruct; the paper mentions "further backbones" only in an appendix not included in the provided text, so generalization to larger models or different architectures (e.g., non-GQA, MoE) is not addressed in the given text.
- **Efficiency comparisons are against FullKV mainly, not baselines at matched budget for latency/memory (partially stated).** The paper explicitly notes it "primarily compares FullKV with GraceKV" for the memory/latency figure, and separately notes that under equal physical-entry budgets, compressed methods "generally exhibit similar steady-state memory and decoding costs" — meaning the headline efficiency numbers reflect compression-vs-uncompressed, not GraceKV's efficiency advantage over other compression baselines.
- **Task-dependent sensitivity acknowledged (stated).** Ablation shows single-document QA is far more sensitive to component removal than summarization, meaning gains are uneven across task types — the method's advantage may be concentrated in specific task categories (precise localization/multi-hop) rather than uniformly strong everywhere.
- **Complexity/latency of the allocation algorithm at inference time (inferred).** Given the many hand-tuned constants (λ_stab, λ_s, λ_Z:λ_M=0.25:0.75, r=32, n_min=16, n_max=128, η_seed=0.9, M_seed=64, R_hop=2, etc.), the approach carries substantial hyperparameter surface; while a "Hyperparameter Study" is mentioned, the full sensitivity results are deferred to an appendix not present in the provided text, so robustness to these choices outside the tested defaults is not fully verifiable from what's given.
- **GPU-only, no CPU-offload comparison depth (inferred).** The paper criticizes CPU-offload-based methods (SeKV, SpeCache) for overhead but doesn't run head-to-head efficiency comparisons against them in the provided text — the critique is asserted, not empirically demonstrated here.
