# EdgeXpert: An Edge Device for Memory-Efficient LLM Inference with Mixture-of-Experts and Speculative Decoding

**Authors:** Sangwoo Ha, Hyunwoo Seo, Yurim Jo, Youngjin Moon, Hoi-Jun Yoo

**arXiv:** [2608.05303](https://arxiv.org/abs/2608.05303)

**Categories:** cs.AR, cs.CL, cs.LG

**Submitted:** 2026-08-05

**Relevance:** 9/10 — matched: LLM inference efficiency and long-context serving

---

## TL;DR
EdgeXpert is an ASIC accelerator that fixes a memory-access conflict between two popular LLM speedup techniques — speculative decoding and mixture-of-experts (MoE) — which, when naively combined, actually *increase* memory traffic instead of reducing it. It does this with two software-hardware co-designed mechanisms: prompt-wise expert reuse in the prefill stage and depth-aware expert coalescing (plus compute-based accuracy recovery) in the decode stage. Synthesized in 28nm silicon, it reports up to 56.3% latency reduction and 44.1% energy reduction versus three prior accelerator/pruning baselines, with near-baseline accuracy.

## First-principles breakdown

**The underlying problem: external memory access (EMA) dominates edge LLM inference.**
Running an LLM on a phone/edge chip means loading model weights from external DRAM for every token generated (single-batch, autoregressive). This is a bandwidth/energy problem, not a compute problem — DRAM access costs far more energy than a multiply-add. The paper's Equation (1) frames the cost simply as "total weight parameters loaded per output token." The dominant contributor is the feed-forward network (FFN) layers, and this cost scales linearly with the number of decode steps.

**Two independently useful fixes, and why combining them breaks:**

1. *Mixture-of-Experts (MoE)*: instead of one big FFN, split it into many small "expert" sub-networks; a router picks only a handful (top-k) per token. This cuts both compute and, importantly, the weight bytes that need to be fetched per token (Eq. 2) — fewer active experts = less EMA.
2. *Speculative decoding (SD)*: use a cheap "draft" model to guess several future tokens at once, then verify them all in one pass through the expensive "target" model. If N_A tokens are accepted per verification pass, you amortize one expensive weight-load across N_A tokens (Eq. 3) — effectively fewer "decode stages," so less EMA per output token.

The catch: SD verifies a *batch* of candidate tokens together. When the target model is MoE, each candidate token in that batch may route to a different set of experts. To serve the whole batch, the hardware must load the *union* of every expert any candidate token wants — so more candidate tokens (which SD wants, to raise acceptance length) means more experts touched, which increases EMA (Eq. 4) and directly fights against MoE's memory-saving premise. The paper measures this concretely: attaching EAGLE-3 speculative decoding to Qwen3 activates 52.1 experts per stage, a 6.5× jump, and the "actual" combined system consumes 24.3% *more* energy than plain autoregressive decoding rather than less — the opposite of the intended benefit.

**Fix #1 — Prefill stage: Prompt-wise Expert Reuse.**
Normally, MoE routing is done independently per token: every token in the prompt asks "which experts do I need?" With many prompt tokens processed at once (prefill), this activates a huge, mostly non-overlapping set of experts. EdgeXpert reframes this as a *prompt-level* problem: figure out which tokens matter most, let those establish a small "shared expert set," and force less-important tokens to preferentially reuse that same set rather than pulling in fresh experts.
Mechanism: a lightweight bidirectional encoder (a small pretrained sentence-transformer, MiniLM) produces a CLS-style attention score per token cheaply (negligible overhead relative to the LLM itself). Tokens are bucketed into major/minor/trivial importance groups via a hardware "partitioning network" (threshold comparators + a reordering pipeline, processing 128 tokens/cycle — chosen over a global sort because sorting scales badly with variable prompt length). Major tokens route normally (top-k) and build the shared set E. Minor/trivial tokens keep only their top-1 expert for fidelity, then fill remaining routing slots by preferentially reusing experts already in E (function `reuse_route`), falling back to fresh top-k only if reuse isn't enough. The budget (k, n — how many candidates to consider vs. how many to actually route) is tuned per token class by searching for a Pareto point between MoE output error (MSE) and fraction of experts activated (R_EMA), not by hand-tuning on downstream benchmarks. Result: 55.7% less prefill-stage expert EMA with reportedly minimal accuracy loss, because the encoder's bidirectional context is arguably *better* at estimating importance than using the causal (forward-only) target model's own attention.

**Fix #2 — Decode stage: Depth-aware Expert Coalescing + Computational Calibration.**
In SD, candidate tokens form a tree; tokens at the same "depth" in the tree are competing alternatives — only one will ultimately be accepted after verification, the rest discarded. The paper observes two properties: (a) same-depth tokens are contextually similar and tend to activate overlapping sets of experts/channels (up to 88.4% overlap for 3+ of 8 experts), and (b) they're mutually exclusive at verification time — only one survives. Standard channel-level pruning reduces each token's own *compute* by having it use only its needed channels, but hardware still must fetch the *union* of channels needed across all same-depth tokens to serve them all — so EMA savings don't materialize even though compute shrinks. Since most of those tokens get thrown away anyway, loading their full channel requirements is wasteful. EdgeXpert instead loads only "salient" channels — selected by comparing a per-channel salience score against a threshold (selection ratio s_r, chosen so ≥75% of the eventually-accepted token's needed channels are still covered, based on calibration data). This is a hardware-supported channel budget rather than a full union, cutting EMA further.
The risk: skipping channels can hurt accuracy and shrink acceptance length (fewer tokens get accepted per stage, undoing SD's benefit, and indirectly increasing EMA again since more decode stages are needed). Their fix, "computational calibration," is to let *all* candidate tokens at that depth recompute over *all* the channels that were loaded (not just their individually-pruned subset) — i.e., trade extra on-chip compute (cheap) for not needing extra memory access (expensive) to recover accuracy/acceptance length. A "dual reconfigurable adder tree" hardware unit computes the necessary channel/salience scores efficiently across variable-sized depth groups, cutting coalescing-unit latency 76.7% versus a fixed adder tree.

**Hardware implementation:** an 8-cluster PE array (8K MACs, A8W4 precision, 512KB SRAM, 28nm, 800MHz, 13.1 TOPS peak) with a "top controller" that runs both new units — the Prompt-wise Reuse Unit (PRU) and Depth-aware Coalescing Unit (DCU) — which together occupy only ~14% of chip area and ~9% of power, since they run once per layer/expert rather than repeatedly like the MAC array, and their latency overlaps with ongoing compute.

## Key insights

- **Correctly diagnosing the SD+MoE incompatibility as a memory (not compute) problem** is the paper's central contribution. Prior related work (MoESD, SS-MoE, MoE-Spec) either analyzes the interaction without fixing EMA, targets GPU/CPU-transfer costs rather than edge EMA, or handles only expert-level budgeting without touching intra-expert (channel) EMA. EdgeXpert explicitly claims to be the first to address both prefill-stage expert EMA *and* decode-stage intra-expert EMA (Table I comparison).
- **Reframing prefill routing as prompt-level reuse rather than per-token routing** is a genuine algorithmic idea, distinct from prior MoE cache/routing-locality work ([34],[35]) which the authors argue is infeasible on edge devices anyway due to tiny on-chip cache (can't hold multiple 4MB experts).
- **Turning channel-level sparsity into actual EMA reduction** is the paper's other core claim — the observation that pruning reduces compute but not necessarily EMA (because hardware must still load the union of needed channels) is a subtle and believable point specific to batched/tree-based verification, and the "trade extra compute for zero extra memory access" calibration trick is a sensible way to reconcile accuracy loss with the memory-bound reality of edge hardware.
- Evidence supports moderate, not universal, gains: accuracy loss from coalescing alone is significant (Table IV shows large drops, e.g. GSM8K falling from 62.6% to 16.5% on OLMoE) and calibration is essential to restore it — the ablation table is a real strength, showing each component's individual contribution rather than only the combined system.
- Reported headline numbers (56.3% latency, 44.1% energy reduction) are relative to three baselines the authors themselves selected and reimplemented/projected onto comparable hardware — a genuine improvement given the comparison, but the paper doesn't compare against the most recent competing MoE+SD EMA-aware works (MoESD, SS-MoE, MoE-Spec) quantitatively, only qualitatively (Table I).

## Caveats — stated and inferred

- **Simulation-based hardware evaluation** — the actual chip numbers come from an "instruction-level custom simulator" using post-synthesis per-instruction costs and DRAM energy parameters, not a fabricated/tested chip. (inferred, though implicit in the described methodology — synthesis was done but no tape-out/silicon measurement is mentioned)
- **Baselines are reimplemented/projected, not run on their original hardware** — EdgeMoE's numbers were originally on a Jetson board but are re-mapped onto "dedicated hardware with 4-bit dense INT MAC units" for comparison; SMoLPU is scaled from 200MHz to 800MHz. This normalization is reasonable for apples-to-apples comparison but introduces estimation uncertainty the paper doesn't quantify. (inferred)
- **Missing comparison against most directly relevant recent work** — MoESD, SS-MoE, and MoE-Spec are all MoE+speculative-decoding EMA-aware methods per Table I, but the authors exclude them from quantitative comparison, citing that they target GPUs or use large self-draft models "less suitable for edge devices" — a reasonable but self-selected exclusion that removes the closest competitors from the numeric results. (inferred)
- **GSM8K accuracy degradation under non-thinking mode is explicitly acknowledged** (3–4% drop attributed to fewer intermediate reasoning steps to recover from coalescing's approximation error), and the authors note this is resolved in "thinking mode." This is a real, stated limitation rather than a fully solved problem for shorter-reasoning-trace settings. (stated)
- **Hyperparameters (k_min/tri, n_min/tri, θ1,2, s_r) are calibrated per-model on WikiText-2/MT-Bench data, not tuned per downstream task** — the authors frame this as a strength (avoids overfitting to benchmarks), but it also means there is no ablation showing sensitivity if the calibration set were mismatched with a real deployment's actual usage distribution. (inferred)
- **Single-batch inference only** — all evaluations assume single-batch edge deployment; the paper doesn't address how these mechanisms behave under multi-request or batched serving (not addressed in the paper).
- **The paper is self-reportedly built on and directly extends the authors' own prior work (SMoLPU [3], an ISSCC 2026 paper by overlapping authors)**, which is adopted as both the pruning baseline and a hardware baseline for comparison — a close relationship between the paper and its primary point of comparison. (inferred)
- **Open-source artifact runs in full bf16 precision, not the actual A8W4 quantized configuration used for the reported hardware results** — the authors state the artifact "runs in full precision (bf16)" while the paper's reported results were "simulated with 8-bit inputs and 4-bit weights," meaning the publicly reproducible code does not directly reproduce the paper's headline efficiency numbers. (stated)
- **Area/power overhead of the added control logic (PRU+DCU) is reported as small (~14% area, ~9% power)**, but this is based on the same custom synthesis flow rather than independent verification. (inferred)
