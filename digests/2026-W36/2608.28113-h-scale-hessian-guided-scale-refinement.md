# H-Scale: Hessian-Guided Scale Refinement for NVFP4 Sub-Byte LLM Inference

**Authors:** Hao Yu, Zheng Li, Dayiheng Liu, Jianwei Zhang

**arXiv:** [2608.28113](https://arxiv.org/abs/2608.28113)

**Categories:** cs.CL

**Submitted:** 2026-08-28

**Relevance:** 9/10 — matched: LLM inference efficiency and long-context serving

---

## TL;DR
NVFP4 (NVIDIA Blackwell's 4-bit float format) quantizes weights in tiny 16-value groups, each with its own scale factor — but existing PTQ methods obsess over fixing the quantized weights while picking that per-group scale via naive min-max/RTN. H-Scale instead searches a small window of hardware-valid neighboring scales and picks the one minimizing a diagonal-Hessian-weighted (activation-aware) reconstruction error, at zero inference-time cost. Applied as a drop-in replacement across six NVFP4 baselines (RTN, GPTQ, 4over6, ArcQuant, MR-GPTQ, GPTAQ) on Qwen3 and LLaMA-3.1 models, it generally raises average benchmark scores and narrows the gap to BF16.

## First-principles breakdown

**The problem: quantization compresses weights, but needs a "scale" to do it.** LLM weights are stored in BF16/FP16 (16-bit floats). To speed up inference and cut memory, PTQ converts them to lower precision — here, NVFP4, a 4-bit floating-point format (E2M1: 1 sign bit, 2 exponent bits, 1 mantissa bit) supported natively by Blackwell GPU tensor cores. A 4-bit grid can only represent 16 distinct values in [-6, 6], so to map a group of real-valued weights onto that grid you divide by a "scale" factor first (shrinking the values into the representable range), round to the nearest grid point, then multiply back by the scale at dequantization time. Get the scale wrong and you either clip large weights or waste resolution on a range most weights don't occupy.

**Why NVFP4 makes this harder.** Instead of one scale per whole tensor, NVFP4 uses "micro-blocks" of just 16 weights, each with its own scale (stored as an 8-bit E4M3 float), plus one global 32-bit scale for the whole tensor. This fine granularity is good for isolating outliers, but it means there are now enormous numbers of small scale-selection decisions to get right — a combinatorial space existing methods largely ignore, since they focus on adjusting the *weight values* (e.g., GPTQ's iterative error compensation, SpinQuant's rotations) rather than the *scales*.

**How scales are normally chosen (baseline/RTN):** take the max absolute value in each 16-weight group, derive a scale that fits that range, and round every weight to the nearest FP4 code under that scale. This is "round-to-nearest" (RTN) — simple but naive: a single outlier weight can dictate the scale for all 16 values, wasting grid resolution on the other 15.

**H-Scale's mechanism, step by step:**
1. *Better objective:* Instead of minimizing raw weight error `||W - Ŵ||²` (weight MSE), H-Scale wants to minimize the actual downstream effect: the error in the layer's *output*, `||XW - XŴ||²`, where X is calibration activation data run through the layer. This full objective involves a Hessian-like matrix `G = XᵀX`, which couples all input channels together — solving that exactly per 16-weight group is computationally intractable (combinatorial across channels).
2. *Diagonal approximation:* They keep only the diagonal of G, i.e., per-channel "energy" `h_j`, ignoring cross-channel interactions. This decouples the problem so each group's scale can be chosen independently, weighting reconstruction error by how much each channel actually matters to the output — channels with high activation energy get penalized more for weight-rounding errors.
3. *Discrete search over hardware-valid scales:* Starting from the RTN baseline scale, H-Scale doesn't invent new scale values — it walks along the actual FP8 (E4M3) grid of representable scale values, checking a small window (default: 9 steps down, 6 steps up = 16 candidates) around the initial guess. For each candidate scale, it quantizes the group, computes the Hessian-weighted error, and keeps the best one. This guarantees every chosen scale is something the hardware can actually store/use.
4. *Zero inference overhead:* Because only the *scale value* changes (not the format, not added compute at runtime), the model runs exactly as fast as any other NVFP4 model — all the extra work happens once, offline, during calibration.
5. *Drop-in composability:* Since most NVFP4 pipelines end with "pick a scale via RTN, then quantize," H-Scale just swaps out that final step — it can sit on top of GPTQ (reusing GPTQ's already-computed Hessian diagonal), 4over6, ArcQuant, etc., without touching their other machinery (e.g., GPTQ's column-wise error propagation stays intact).

## Key insights

- **Genuinely new framing:** treating per-group *scale selection* (not weight rounding) as the primary lever for NVFP4 accuracy — this is the paper's core claimed contribution, and it's a reasonable gap given cited related work focuses on weight reconstruction/rotation.
- **Evidence supports the mechanism, not just the claim:** the layer-wise validation (Fig. 1, Qwen3-4B gate_proj) is a genuinely informative ablation — it shows weight-centric scale search achieves the *lowest weight MSE* but only a 12.6% output-error reduction, while H-Scale's Hessian-weighted objective achieves 32.5% output-error reduction (~80% of an oracle "Best Scale" upper bound obtained via gradient-based backprop). This directly substantiates the "weight MSE is a bad proxy for output fidelity" claim rather than just asserting it.
- **Consistent, if modest, empirical gains:** across 4 model/scale settings (Qwen3-30A3-Thinking, Qwen3-30A3-Instruct, Qwen3-4B-Instruct, LLaMA-3.1-8B-Instruct) and 5-6 baselines each, H-Scale improves the *average* score in nearly every baseline×model combination — but gains are frequently ~0.5-1.5 average points, and individual per-benchmark deltas are often negative even when the average rises (explicitly acknowledged in table captions, e.g. "not every individual benchmark improves").
- **Practical, low cost:** offline overhead is small — GPTQ+H-Scale goes from 9.6h→9.9h, 4over6+H-Scale from 0.2h→0.4h on one H200 GPU — and works with a much smaller calibration set (128 vs 4096 samples) per Appendix F, suggesting reasonable robustness.
- **Ablation isolates the Hessian's contribution specifically:** the "scale-only" (uniform weighting, hi=1) variant sometimes *hurts* relative to the raw baseline (Table 5: 4over6 and ArcQuant), while full H-Scale consistently helps — evidence that the Hessian weighting, not just "search more scales," drives the benefit.

## Caveats — stated and inferred

- **Text-only, single format/group-size scope** (stated): "Our study is limited to NVFP4 with g=16 and text-only LLMs. Whether the same scale-contraction strategy transfers to other formats, group sizes, or multimodal models is left open."
- **Diagonal Hessian is an approximation that discards cross-channel correlation** (stated): the authors explicitly note "the approximation drops the cross-channel correlation terms," used purely to make the search tractable — no full-Hessian result is provided at model scale (only per-group examples/oracle at small scale).
- **Run-to-run variance is nontrivial relative to some reported gains** (stated/inferred): Appendix D shows suite-level average standard deviations up to 0.37 points across 3 runs, and the authors themselves state "we do not attach statistical significance to small deltas" — yet several headline gains in Tables 1-4 are in the 0.5-1.0 point range, comparable to or only modestly larger than this noise floor. The paper argues the noise "never exceeds 0.37" so gains are real, but no formal significance test (e.g., p-values) is reported (inferred: this is an assertion, not a statistical proof).
- **Mixed per-benchmark results despite positive averages** (stated): multiple tables explicitly caveat that "not every individual benchmark improves for every method" — a form of the average-metric-can-mask-regressions pattern; e.g., in Table 1, RTN+H-Scale drops LiveBench (75.14→74.72) even as the average rises.
- **No comparison against activation-migration methods (SmoothQuant, AWQ) or Hadamard preprocessing** (stated), justified by citing prior work (Egiazarian et al. 2025) claiming these give "little additional benefit" for NVFP4 — this justification relies on one external paper's finding rather than the current authors' own ablation, so it's a somewhat weak baseline-exclusion argument (inferred).
- **"Best Scale" oracle uses gradient-based backprop unavailable at PTQ time** (stated) — used only as an upper-bound reference, not a deployable comparison, which is reasonable but means the ~80%-of-oracle framing is against a method that isn't a fair real-world baseline.
- **All models are from two families only (Qwen3, LLaMA-3.1)** (inferred): cross-family transfer claim rests on a single non-Qwen model (LLaMA-3.1-8B-Instruct), which is a fairly narrow basis for "generalizes across families."
- **No wall-clock/latency measurement of actual inference speed** beyond asserting "zero overhead" structurally (inferred) — plausible given the format is unchanged, but no end-to-end inference benchmark is shown, only offline calibration runtime (Table 6).
- **Candidate-window ablation (Table 7) only tested on one model (Qwen3-4B)** (inferred) — the choice of U=6, K=16 is validated on a single model's 144 layers, not shown to transfer to other model sizes/families.
