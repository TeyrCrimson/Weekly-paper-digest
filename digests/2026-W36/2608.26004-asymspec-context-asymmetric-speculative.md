# AsymSpec: Context-Asymmetric Speculative Decoding for Agentic LLMs

**Authors:** Sheng Liang, Yongyue Zhang, Nathanael Brian, Hang Lv, Hao Wang, Chen Zhang, Yong Liu

**arXiv:** [2608.26004](https://arxiv.org/abs/2608.26004)

**Categories:** cs.AI, cs.CL

**Submitted:** 2026-08-26

**Relevance:** 9/10 — matched: LLM inference efficiency and long-context serving

---

## TL;DR
AsymSpec is a speculative-decoding variant for agentic LLM pipelines where the small "drafter" model reads the full, uncompressed context while the large "verifier" only sees a cheap compressed view, with the drafter's extra context signal injected into the verifier via a contrastive logit trick and a divergence-aware acceptance rule. Across four agentic capabilities and two end-to-end agent benchmarks it recovers ~90% of full-context accuracy while running at roughly the compressed verifier's compute cost (0.2–0.3× FLOPs) and 1.3–1.7× the throughput of full-context decoding. The core claim is that breaking the "drafter and verifier see the same input" assumption of standard speculative decoding unlocks an accuracy/cost operating point that neither compression nor symmetric speculative decoding can reach alone.

## First-principles breakdown

**The problem.** Agentic LLM systems (RAG, tool use, multi-turn chat, multimodal agents) keep accumulating context — retrieved documents, tool outputs, conversation history. The large "verifier"/target model's forward pass cost grows with context length, so it dominates latency. The standard fix is to *compress* the context (summarize retrieved passages, pass API signatures instead of full docs, use captions instead of images) before feeding it to the big model. This saves latency but throws away information the model needs to reason correctly, hurting accuracy.

**Why speculative decoding doesn't help here.** Speculative decoding (SD) is a well-known lossless acceleration trick: a small, cheap "drafter" model guesses several next tokens, and the large "verifier" model checks all of them in one parallel forward pass, accepting the ones that agree with what it would have generated itself and correcting the rest. This is faster because verifying K tokens in one pass is cheaper than generating them one at a time autoregressively. But standard SD requires the drafter and verifier to see *identical* input. That means SD can only speed up whatever accuracy level the verifier's context already supports — if you feed the verifier compressed input to save cost, SD just accelerates the compressed (lower-accuracy) model. It cannot recover what compression discarded, because the drafter never has access to information the verifier doesn't have.

**The key structural observation.** In practice, almost all of the per-step latency comes from the *verifier's* forward pass, not the drafter's (the drafter is tiny by comparison). So if you could keep the verifier cheap (compressed input) while somehow giving it access to what a full-context model would have said — using only a nearly-free extra forward pass by the small drafter — you'd get both the latency benefit of compression and the accuracy benefit of full context.

**The mechanism (asymmetric context + contrastive fusion).** AsymSpec breaks the "same input" rule: the verifier L always operates on the compressed context; the drafter S is run *twice*, once on the full context and once on the compressed context (both cheap since S is small). At each decoding step:
1. S(full context) produces logits `a` and proposes K candidate tokens.
2. S(compressed context) produces logits `b` at the same positions.
3. L(compressed context) produces logits `t` for verification, as in normal SD.

The difference `δ = a − b` is a "context-gain signal": since both `a` and `b` come from the *same* small model, subtracting cancels out whatever generic biases/preferences that model has regardless of context, leaving (in theory) just the effect of having seen the extra information in the full input. This is philosophically like contrastive decoding, but crucially both terms are from the same model on different context views, rather than from two different-capacity models on the same context (which is what prior "speculative contrastive decoding" (SCD) work did).

**Combining drafts with the verifier (CDA gate).** A token is accepted if the verifier's probability for it exceeds a threshold relative to the drafter's compressed-context probability — like standard SD's rejection sampling, but with an adaptive threshold. The threshold γ_eff shrinks (becomes more lenient) as the Jensen-Shannon divergence between the drafter's full-context and compressed-context distributions grows — i.e., in positions where full context and compressed context disagree a lot (meaning compression likely discarded something important), the gate is more willing to accept the drafter's full-context-informed guess. When a draft token is rejected, instead of falling back to the verifier's own compressed-context prediction (which would just reproduce the Floor/compressed behavior), the system emits `argmax(t + βδ)` — the verifier's logits nudged by the context-gain signal δ. This way, even rejected positions still benefit from the recovered information. The exponential form of the threshold decay is derived from a small set of axioms (continuity, monotonicity, multiplicative composition of independent divergences) and JSD is chosen specifically because it's provably bounded (≤ ln2), which guarantees the effective threshold stays within a bounded range without needing per-dataset tuning — a "parameter-free" design.

**Cross-modal extension.** Because δ and the acceptance gate operate purely on output-token logits (shared vocabulary), the same mechanism works when the drafter and verifier use *different input modalities* — e.g., a vision-language drafter reads raw images while a text-only verifier only reads captions. The image encoding is cached once per request so its cost is amortized over the whole generation.

## Key insights

- **Genuinely new framing**: prior speculative decoding work (EAGLE, Medusa, TriForce, etc.) universally assumes drafter and verifier share identical input; prior asymmetric approaches (RAPID) invert the direction (full-context verifier, truncated drafter) to preserve accuracy at full cost. AsymSpec is the first (per the paper's related-work framing) to let a cheap full-context drafter recover accuracy for a strictly compressed, cheap verifier, opening a new "compressed-cost, near-ceiling-accuracy" point on the trade-off curve.
- **The δ-fusion source matters, not just "contrastive fusion" generically**: the ablation (Table 6) shows same-model (drafter-full minus drafter-compressed) δ outperforms both a raw single-pass signal and the two-model SCD-style contrast by 3–12 F1 points, supporting the claim that isolating context-gain (not model-capacity gap) is what's doing the work.
- **The gain is diagnostic, not just a fixed boost**: it correlates with how much compression actually destroys — near-zero gain on MultiChallenge (low compression loss), monotonically increasing gain as truncation budget shrinks on LongBench (Table 2). This is decent evidence the mechanism is actually recovering discarded information rather than just adding noise/regularization.
- **Parameter-free claim is reasonably well supported**: sweeps show flat performance across β and γ ranges, and CDA matches or beats a manually-tuned λ-scaled variant in most cells (though it's not uniformly best — see caveats).
- **Cross-family and cross-modal generalization** is demonstrated (Qwen drafting for Llama verifier, VL drafter for text verifier), which is a meaningful robustness claim beyond a single same-family pairing, though the paper is candid that recovery varies a lot across pairs (10%–72%).
- **Throughput vs FLOPs distinction is well-argued**: they explain why big FLOPs savings (0.2–0.3×) don't translate to proportionally large throughput gains (only 1.3–1.7×) — decoding at 30B+ scale is memory-bandwidth-bound, not compute-bound, so this isn't a hidden inconsistency but an expected hardware effect.

## Caveats — stated and inferred

- **Requires white-box access to verifier logits** — explicitly stated as a limitation; the method cannot be applied to proprietary APIs that only return text. (stated)
- **Deterministic/greedy decoding only (τ=0)**; the method does not preserve a strict target distribution (explicitly acknowledged: "AsymSpec does not preserve a strict target distribution; it is a speculative-style steering scheme calibrated for greedy emission"), and generalizing to stochastic sampling is left as future theoretical work. This means it's not truly "lossless" the way standard SD is — a meaningful departure from the classical SD guarantee, understated by the abstract calling SD itself "lossless" while positioning AsymSpec as an extension of it. (stated)
- **Recovery is fundamentally bounded by what compression retains and what the drafter can extract**; on some cross-modal breakdowns (file-attachment GAIA subset with the smaller VL-2B drafter) AsymSpec actually falls *below* the Floor baseline. (stated)
- **Cross-family transfer requires vocabulary alignment** and shows highly variable recovery (10%–72% in Table 10) depending on model pair — not a robust, drop-in guarantee. (stated)
- **Drafter capacity floor**: models ≤0.6B fail to extract reliable signal; ≥1.7B is described as the "practical minimum" — a real deployment constraint not emphasized in the abstract. (stated)
- **Accuracy loss is still real, not solved**: the method reaches "≈90% of full-context accuracy," meaning a systematic ~10% average accuracy gap remains versus the true ceiling; on LongBench's 2WikiMQA and MuSiQue subsets the gap is much larger (66.8 vs 76.5, and 48.4 vs 55.0) — cherry-picking the average obscures meaningfully worse per-subset performance. (inferred)
- **MultiChallenge shows no benefit and sometimes underperforms Floor** (23.5 vs Floor 23.4, and in the drafter-size sweep AsymSpec is often below fixed-γ and tuned-λ) — the paper frames this as "expected" since compression is near-lossless there, but it does mean the method isn't uniformly better than simpler baselines, and the ≤3pp differences across many MultiChallenge ablation cells are within noise / judge variance, undermining fine-grained conclusions drawn from that benchmark. (inferred, partially stated)
- **Reliance on LLM-judge metrics** (MultiChallenge, SimpleQA) which the paper itself flags had "transient API degradations" requiring manual exclusion of >15% truncated judge responses in some runs — suggests some fragility/noise in the evaluation pipeline that could affect reported numbers. (stated, but the implication for result reliability is inferred)
- **No comparison against more recent/stronger compression-aware or trained speculative methods** beyond SD, SCD, and RAPID; EAGLE/Medusa-style trained drafters aren't benchmarked head-to-head even though they're discussed at length in related work — the comparison set may be somewhat narrow for such a fast-moving area. (inferred)
- **Engineering complexity is substantial and possibly fragile**: the cross-modal implementation required 5 non-trivial patches to a specific vLLM version (v0.19.0), and the paper notes these APIs are "restructured in newer vLLM releases," meaning reproducibility/maintenance could be an issue; without two of the five patches accuracy collapses from 53% to 30.5%, showing the result is sensitive to implementation details rather than the core algorithm alone. (stated)
- **All evaluation is on open-weight models the authors control** (Qwen3, Llama-3.x) in a research/benchmark harness (LongBench, GAIA, SimpleQA, etc.), not a live production deployment — real-world serving conditions (batching, concurrent requests, KV-cache pressure at scale) are not evaluated. (inferred)
- **Throughput numbers use "eager mode (no graph capture)"** and are noted to have "non-trivial per-run variance," with the authors acknowledging that "batched, graph-captured measurement would tighten these further" — meaning reported throughput gains may not reflect a fully optimized production serving stack. (stated)
- **Hyperparameter robustness claims (flat across β, γ) are demonstrated primarily on LongBench/API-Bank/MultiChallenge**, not across all six evaluation benchmarks equally, so generality of "no per-dataset tuning needed" is somewhat narrower than the headline claim suggests. (inferred)
