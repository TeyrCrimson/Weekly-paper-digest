# Prefix Sliding for efficient test-time scaling

**Authors:** Niklas Muennighoff, Zhengyang Wang, Zeyi Chen, Weijia Shi, Binyuan Hui, John Yang, Dapeng Jiang, Mika Senghaas, Fares Obeid, Johannes Hagemann, Sami Jaghouar, Ludwig Schmidt, Percy Liang, Jason Wei, Andrew Y. Ng, Luke Zettlemoyer, Yejin Choi, Mike Lewis

**Categories:** cs.CL, cs.AI, cs.LG

**Submitted:** 2026-08-26

**Relevance:** 9/10 — matched: LLM inference efficiency and long-context serving

## TL;DR
Prefix Sliding is a memory-management technique for reasoning LLMs that keeps only the prompt prefix (system/task instructions) plus a fixed-size sliding window of recent reasoning tokens, discarding everything in between, so that the cost of generating each new token stays constant no matter how long the model reasons. Without any retraining it matches full-attention accuracy while running ~3x faster, and when used during RL training it lets rollouts extend past 100,000 tokens and improve reward under a fixed memory budget. It beats other bounded-memory alternatives (summarization, last-k truncation, plain sliding window) in the paper's ablations.

## First-principles breakdown

**The problem.** Test-time scaling (letting a model "think longer" before answering) improves accuracy on hard problems, but standard transformers use full attention: every new token attends to all previously generated tokens. That means the compute and memory cost of generating token N grows linearly with N (attention is O(N) per step, O(N²) total), so very long reasoning traces become prohibitively slow and memory-hungry. This caps how far "thinking longer" can scale.

**The key empirical observation.** The authors measure attention patterns over a long reasoning trace and find: (1) the very first tokens (system prompt, task instructions — the "prefix") get outsized attention throughout generation, partly because models use early tokens as "attention sinks" (a known phenomenon where models dump excess softmax probability onto arbitrary early tokens); (2) the most recent ~1000 tokens get high attention because they represent what the model is currently working on; (3) everything in between — the bulk of intermediate reasoning — gets comparatively little attention once the model has "moved past" that step (e.g., once "42+84" is computed, the scratch work behind it is no longer needed, only the numeric result embedded in later tokens matters).

**Why prior fixes are insufficient.** Plain sliding-window attention (used in some LLMs, e.g. GPT-neo, gpt-oss) discards everything outside a fixed recent window — cheap and bounded, but it also throws away the task instructions/tools once they scroll out of the window, causing the model to "forget" what problem it's solving. Two other agent-context tricks — "last-k" (periodically wipe context except the last k tokens) and "summarization" (periodically compress history into a text summary and restart context) — are also bounded in memory, but both require reprocessing tokens (the retained tokens get processed once at generation time and again after context is rebuilt) and have irregular ("sawtooth") per-token costs, plus summarization adds hyperparameters (summary length, prompt, frequency) and models often lose information when compressed into their own summaries. None of these give a truly flat, low, per-token cost while preserving task-critical context.

**The mechanism.** Prefix Sliding keeps two things in the KV cache at all times: (a) the prefix — the fixed system instructions/task prompt/tool definitions — and (b) a sliding window of the most recent W tokens. As generation proceeds, older intermediate tokens outside the window are simply dropped from attention/memory; the prefix is never dropped. Total memory is bounded at (prefix length + W), constant regardless of total trace length — unlike full attention, whose cost grows forever.

Two implementation details matter:
- *Position embeddings*: with RoPE-style position embeddings, when tokens are dropped, you must decide whether to "reset" positions (re-number remaining tokens contiguously, more accurate to how the model was trained but expensive to recompute) or "continue" positions (keep the original position ids, cheaper since cached representations can be reused). They test both and find negligible performance difference, so they use the cheaper "Continue PE."
- *Custom attention kernel*: they extend FlashAttention with two-level filtering — masking within tiles that straddle the boundary of the allowed region (prefix ∪ window), and skipping tiles entirely outside it — to get speed close to a plain sliding-window kernel despite attending to two disjoint regions (prefix + window) instead of one contiguous block.

**Training with Prefix Sliding (RL).** Long RL rollouts (100k+ tokens) normally cause GPU out-of-memory during backpropagation, so practitioners truncate/discard overlong generations, wasting compute and biasing training against long traces. Because sliding-window attention has a limited "receptive field" across layers (theoretically W×L for L layers, empirically closer to 1.5×W due to information bottlenecks), you don't need the full generation history to compute accurate gradients for the final chunk — you only need roughly 4× the window size of preceding context. The paper uses "truncated backpropagation": pass only the prefix plus the last ~4W tokens to the trainer, mask the loss on all but the final W tokens, and let autograd backpropagate only through that final window. This gives near-equivalent gradients to full backpropagation (validated by measuring KL divergence between generator and trainer log-probs) while capping trainer memory. A more exact but costlier alternative, "chunked backpropagation" (accumulate gradients chunk by chunk across the whole trace), is described but not used in main experiments.

## Key insights

- **Novel, and empirically supported**: the core finding that intermediate reasoning tokens rapidly lose relevance while the prefix and recency window dominate attention — directly motivating a training-free memory-capping method. This is shown via attention visualization (Figure 2) and confirmed indirectly by Prefix Sliding matching full-attention accuracy at a fraction of the memory.
- **Novel and supported by benchmarks**: training-free Prefix Sliding achieves ~3x speedup with performance comparable to full attention on AIME25, GPQA, and MATH500 (Table 1) — a genuinely useful drop-in inference-time change requiring no retraining, applicable to existing pretrained models.
- **Novel, supported but more preliminary**: RL training with Prefix Sliding (using truncated backpropagation) enables rollouts beyond 100k tokens under fixed memory and yields higher reward than full attention at equal memory budget (Figure 7) — but this is demonstrated at fairly small scale (1.7B and one 7B validation run), so generalization to larger models/longer training is a claim, not yet a robust result.
- **Comparative claim, well supported by the ablation**: Prefix Sliding outperforms last-k, summarization, and plain sliding window on the same task/window-size budget (Figure 9), primarily because those alternatives reprocess tokens redundantly and/or lose task context, whereas Prefix Sliding never reprocesses and never drops the prefix.
- **Honest boundary case, not a strength claim**: the method explicitly does not solve prefill cost (long prompts are still expensive) and can lose information genuinely needed later (e.g., code being written across a long comment-heavy reasoning span on LiveCodeBench), where a window smaller than ~16384 tokens underperforms full attention (Figure 11) — this is a real, demonstrated limitation, not just a caveat.

## Caveats — stated and inferred

- **Stated**: Limited comparison set — only methods that (1) work on existing pretrained transformers out-of-the-box and (2) have bounded per-token cost were compared; alternative architectures (RNNs, SSMs, subquadratic attention variants) were excluded because a fair comparison would require pretraining from scratch.
- **Stated**: Information loss on tasks where distant intermediate context genuinely matters (LiveCodeBench requires window ≥16384 to match full attention; smaller windows lose earlier code context during long comment-heavy reasoning).
- **Stated**: Limited benefit for short generations — speedups only materialize after the sliding window "warm-up" phase is exceeded; on HealthBench (~2086 tokens average) there's little to no speedup since the window (2048) is rarely exceeded.
- **Stated**: Unresolved handling of system outputs/multi-turn scenarios — large tool outputs (e.g., web page or file contents) can flood or overflow the sliding window, and it's unclear how to handle future user turns (append to prefix? let them slide out?); authors offer only speculative fixes (step-by-step reading, guardrails), not implemented/evaluated solutions.
- **Stated**: Scale is limited — experiments go up to a 7B model and hundreds-of-thousands of tokens; the authors explicitly flag "future work is necessary to scale up Prefix Sliding further and study its trends," meaning larger-model behavior is unverified.
- **Stated**: Prefix Sliding does not address prefill cost — a very long prefix itself could still cause high memory usage, a gap the authors acknowledge without solving.
- **Inferred**: The main RL training result (Figure 7) and the larger 7B validation (Appendix E) appear to be single/limited runs without reported variance or multiple seeds — no confidence intervals or repeated-run statistics are given for these training curves, unlike the eval benchmarks which do use avg@64.
- **Inferred**: The "attention sink" / low-intermediate-attention observation is demonstrated on one specific example (a single Qwen3-1.7B AIME25 trace, Figure 2) — presented as illustrative motivation rather than a systematic, quantified study across many traces/models/tasks.
- **Inferred**: Model diversity is narrow — nearly all main results use Qwen3-1.7B (with one 7B DeepSeek-R1-Distill-Qwen model for a training validation experiment in the appendix); no results are shown for larger frontier-scale models or non-Qwen model families, limiting how far the "matches full attention" claim generalizes.
- **Inferred**: The "3x faster" headline figure depends on window size and sequence length choices (Figure 6/Appendix B show different window sizes yield different speed/accuracy tradeoffs); the specific number is a favorable operating point rather than a universal constant.
- **Inferred**: Continue-PE vs Reset-PE and window-size choices were tuned/selected based on the same benchmarks (AIME25, GPQA, MATH500) used to report final headline results, which raises some risk of implicit tuning-to-the-test-set, though this isn't confirmed as an issue in the text.
