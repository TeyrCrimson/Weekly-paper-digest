# DAVIO: Dense Monocular-Inertial SLAM with Feed-Forward Initialization and Pose-Conditioned Mapping

**Authors:** Jaafar Mahmoud, Arthur Movsesyan, Mikhail Iumanov, Sergey Kolyubin

**arXiv:** [2609.27702](https://arxiv.org/abs/2609.27702)

**Categories:** cs.RO, cs.CV

**Submitted:** 2026-09-23

**Relevance:** 9/10 — matched: Metric and temporally-consistent monocular depth

---

## TL;DR
DAVIO is a monocular-inertial SLAM system that uses a single feed-forward depth model (Depth Anything 3) both to bootstrap a classical visual-inertial filter (OpenVINS) in seconds and to condition dense mapping on the filter's metric poses afterward. On EuRoC and building-scale ORI sequences it starts up faster, lowers trajectory error, and produces denser/more accurate maps than prior feed-forward mapping baselines given the same poses. The core trick throughout is keeping scale corrections confined to depth-along-ray rather than rescaling the metric camera geometry the filter has already established.

## First-principles breakdown

**The problem.** A camera+IMU pair is the cheapest sensor combo that can, in principle, give you both metric-scale localization and a dense 3D map. But two classical pieces don't compose well:
- Visual-inertial odometry (VIO) filters (e.g., OpenVINS) need the camera to move enough for parallax to appear before they can even initialize (figure out scale, gravity direction, velocity, biases). Until then they produce nothing. Once running, they only track a sparse set of point features — not enough for dense mapping.
- Newer "feed-forward" geometry models (DUSt3R, VGGT, Depth Anything 3, etc.) are neural nets that take a handful of images and directly output dense depth/point clouds in one forward pass, without needing motion or iterative optimization. But their output is "up to an unknown scale" — no metric units, no notion of which way gravity points, no velocity/bias estimates. They're complementary to IMU data, which is exactly what supplies those missing physical quantities.

**Why not just glue them together naively?** If you fit a single global scale/rotation to align the neural depth model's guess with the VIO's poses, you distort the metric camera-to-camera distances (baselines) that the filter has already gotten right, since a single Sim(3) transform rescales everything, including the well-estimated parts.

**DAVIO's mechanism, step by step:**

1. *Feed-forward initialization (start-up).* Take 5 images spaced 0.2s apart plus preintegrated IMU data (a standard technique that integrates raw gyro/accel readings between images into a single relative-motion summary, avoiding re-processing every raw sample). Depth Anything 3 (DA3) predicts per-image depth, confidence, intrinsics, and relative poses for this small window. Because each pixel's back-projected 3D point should lie on a known viewing ray (only its depth along that ray is unknown), the authors set up a linear least-squares system where the unknowns are just 7 numbers: scale `s`, initial velocity `v0`, and gravity vector `g`. Solving this system does NOT need feature tracking across many frames — it's "feature-free."
   - *Why this is harder than it looks:* the system is much less overdetermined than the point count suggests. If the DA3-predicted relative rotations agree with IMU rotations, each image really only contributes 3 independent equations (not one per point), so you need at least 4 images, and certain smooth/simple motions (e.g., constant velocity) make the system degenerate (rank-deficient) — the scale becomes unobservable and gets silently absorbed into velocity/gravity. The paper adds explicit numerical checks (singular value ratio, baseline-to-depth ratio) to detect and reject unsolvable windows rather than propagate a wrong scale into the filter.
   - *Robust fitting:* since some depth predictions are bad (object edges, reflective/textureless surfaces, moving objects), they run LMedS (least-median-of-squares — take many random small subsets, fit each, and pick the one whose median error is smallest; more robust to outliers than standard least squares) over 100 hypotheses, then refine and sanity-check the winning solution (plausible velocity, plausible gravity direction) before accepting it.
   - *Handoff:* once accepted, this proposal is refined via a small nonlinear optimization (with priors on bias/scale since these are weakly distinguishable in under a second of data) and injected into a **fresh** OpenVINS filter instance. Buffered sensor data collected during this process is replayed faster than real-time so the new filter "catches up" without dropping data; DAVIO only switches to it once it's confirmed to track the live stream. The original OpenVINS initializer stays armed in parallel as a fallback — whichever finishes first wins.

2. *Pose-conditioned dense mapping (tracking phase).* Now the roles reverse: instead of DA3 informing the filter, the filter's already-metric camera poses are fed into DA3 as conditioning input for 5-frame sliding windows (0.5s keyframe spacing, 2 shared frames between consecutive windows — this overlap is what lets submaps be stitched together later). DA3 returns depth maps for these windows. Critically, only the depth values get rescaled to correct residual error — the camera positions/baselines coming from the filter are never touched, avoiding the naive-fusion problem described above. Within a window, feature matches (XFeat/LighterGlue) between nearby frames refine relative per-frame depth scale.
3. *Submap graph with gravity-preserving, drift-gated revisits.* Consecutive submaps get stitched via relative-scale constraints computed from shared images. When the camera revisits a previously mapped area, matches are found, verified (PnP RANSAC + several consistency checks), and only added as a *pose*-correcting constraint if the odometry's accumulated drift (estimated by a simple growth model) is large enough to exceed the uncertainty of the revisit measurement — otherwise the revisit only contributes a scale constraint, not a pose correction. This prevents low-confidence loop closures from corrupting otherwise-good VIO poses, and the optimization only adjusts translation, yaw, and depth scale per submap (not roll/pitch), preserving the gravity direction the filter already nailed down.
4. *Output.* The map-to-odometry correction is applied smoothly (interpolated) to published poses so the live trajectory doesn't jump when the graph updates; the underlying VIO filter state itself is never modified by the mapping process.

## Key insights

- **Genuinely new:** using the *same* feed-forward depth model for both initialization and mapping is the paper's central architectural claim — prior work (e.g., ScaRF-SLAM, which conditions DA3 on classical tracking poses) doesn't use the feed-forward model for bootstrapping the filter itself.
- **Genuinely new mechanism:** confining scale correction to "along the viewing ray" during mapping (rather than a global similarity transform) is a specific, well-motivated design choice that plausibly explains why DAVIO's maps stay more accurate than a comparable baseline (ScaRF's released mapper) given *identical* input poses — this is a controlled, apples-to-apples comparison and the strongest evidence in the paper.
- **Drift-gated revisit admission is a genuine contribution over naive loop closure**: the ablation shows revisits are needed for the full trajectory correction (removing them reverts MH_03 final ATE to the raw uncorrected value), while gating prevents low-value/imprecise revisits from hurting surface quality on some sequences (V1_03, V2_02 slightly improve without revisits).
- **Evidence supports the "starts earlier" claim specifically in high-parallax-starved settings** (Machine Hall: median quality-adjusted start time roughly halved, 2.30s vs 4.68s) — but in the Vicon rooms, DAVIO is actually *slower* (4.50s vs 3.15s) and has a slightly lower raw success rate (109/132 vs 111/132) than plain OpenVINS overall. The abstract's framing ("starts markedly earlier") is true on average and dramatically true in one subset, but not uniformly true.
- **Robustness to noisy real odometry (vs. ground truth) is a differentiator**: DAVIO's mapper degrades much less than ScaRF's when switching from GT poses to real VIO poses on ORI (26% error increase vs. 110%), attributed to the submap graph's drift tolerance — this is a meaningful practical advantage since real deployments never have GT poses.
- **What's claimed vs. what's shown:** the paper claims general superiority over "SOTA feed-forward mappers," but the strongest number (DAVIO beats ScaRF with matched poses) is a fair controlled test; end-to-end comparisons against MASt3R-Fusion and VGGT-SLAM2 use those systems' own (weaker) trackers, so part of DAVIO's end-to-end advantage there is inherited from OpenVINS being a mature, well-tuned filter rather than purely from DAVIO's own contribution.

## Caveats — stated and inferred

- **Numerical rejection criteria are heuristics, not guarantees (stated):** the authors explicitly say the conditioning/rank checks "are numerical safeguards, not an observability proof," acknowledging cases could exist where a technically-observable window is rejected or a degenerate one slips through.
- **Vicon-room start-up is worse than baseline (inferred):** Table IIb shows OpenVINS beats DAVIO on Vicon-room quality-penalized start time (3.15s vs 4.50s) and success count (57/65 vs 53/65); this is reported but not emphasized in the abstract/conclusion, which foreground the Machine Hall win.
- **Evaluated on only two datasets (inferred):** EuRoC (drone, small indoor rooms, well-known/heavily-used benchmark) and ORI (5 building-scale sequences from the ScaRF-SLAM authors). No outdoor, dynamic-object-heavy, low-light, or large-scale multi-building evaluation is reported — generalization beyond these controlled indoor settings is not addressed in the paper.
- **Compute/hardware dependency (inferred):** results are reported on a specific laptop GPU (RTX 3060 Laptop, 6GB) with DA3-Base; DA3-Large gives further accuracy gains, implying results are sensitive to model size/compute budget, and real-time performance on lower-end hardware is not addressed.
- **"Matched-pose" comparisons vs "end-to-end" comparisons are mixed together to build the overall narrative (inferred):** the strongest, most controlled evidence (mapper-only comparison against ScaRF with identical poses) is real but limited to two dataset families; broader end-to-end claims lean on baselines (MASt3R-Fusion, VGGT-SLAM2) run "offline from released code with their own confidence filters," and VGGT-SLAM2 is given a global Sim(3) fit to the reference trajectory that the paper itself notes "favors it" — yet DAVIO still reportedly wins, which is reasonably strong, but the baseline configurations weren't necessarily tuned as carefully as DAVIO.
- **GT-pose offline comparison undercuts DAVIO's own mapper (stated):** with reference (ground-truth) poses, ScaRF's offline mapper actually beats DAVIO's offline mapper on global and chunk error (0.040 vs 0.069m), meaning DAVIO's advantage is specifically tied to robustness under real (imperfect) odometry, not to the mapper being unconditionally more accurate.
- **Ablation on revisits shows inconsistent surface-quality effects (stated):** removing revisits improves F@10 on two of three tested sequences (V1_03, V2_02) while helping on V1_02 — the paper speculates this is because "some admitted revisits impose imprecise scale constraints," an acknowledged weakness in the revisit-gating design rather than a clean win.
- **Depth quality remains a major bottleneck (stated):** the authors note "depth quality is therefore a major remaining error source, alongside pose accuracy," implying the method's ceiling is significantly limited by the underlying feed-forward model's raw accuracy, not just by DAVIO's fusion strategy.
- **No failure-mode or robustness analysis under sensor degradation (inferred):** no experiments on IMU noise sensitivity, camera exposure/motion blur, or partial sensor dropout are reported; not addressed in the paper.
- **Runtime/latency numbers for the mapping/graph-optimization stage are not clearly reported as a full real-time budget (inferred):** the paper states the system is "real-time" and paced at sensor rate, but does not give a detailed per-component latency breakdown (e.g., DA3 inference time, graph optimization time per commit) in the excerpted text.
