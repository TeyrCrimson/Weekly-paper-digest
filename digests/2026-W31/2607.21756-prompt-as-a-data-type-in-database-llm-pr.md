**Categories:** cs.DB, cs.LG

**Submitted:** 2026-07-23

**Relevance:** 6/10 — matched: Pre-inference input sanitization for generation stability

## TL;DR
PromptDB proposes treating LLM prompts as a first-class relational data type (`PROMPT`) stored in tuples, rather than opaque strings embedded in application code, so the DBMS can inspect, rewrite, and optimize them using schema/constraint/statistics metadata. Built as a DuckDB prototype with a rule-based rewriter (PromptOpt) that injects constraints, prunes irrelevant columns, minimizes output format, and adds DB-selected few-shot examples, it shows database-guided rewriting improves task quality and output validity over static prompts, with a tunable cost-quality trade-off. Evaluation is on synthetic tickets, a small OpenML dataset, and TPC-H, using a single small local LLM (llama-3.2-3b-instruct).

## First-principles breakdown

**The problem.** Many database applications now call an LLM per-tuple: classify a support ticket, filter rows by a fuzzy natural-language condition, extract a structured attribute from free text. Today the prompt that drives this computation typically lives in application code (an f-string, a notebook cell, a config file) that gets filled with tuple values and sent to an LLM API. The database itself never "sees" the prompt — it just sees a UDF call with a string argument. That means the query optimizer, catalog, and constraint system have no way to inspect or improve the prompt, even though the database already has useful information (e.g., "the valid categories for this column are X, Y, Z") that would make the prompt better if injected into it.

**The core move: prompts as data.** The paper borrows an old database idea — Stonebraker's 1984 "QUEL as a Data Type," which let a database *query itself* by storing query commands as ordinary column values — and applies it to prompts. Concretely, they define a new logical type `PROMPT`, implemented in DuckDB as a `STRUCT` with fields: `template` (text with `{{variable}}` placeholders), `bindings` (a map from template variables to tuple column names), `model` (which LLM to use), `task`, `output_domain` (allowed output values), and a `default_strategy` (which rewrite plan to use). A table column can literally have type `PROMPT`, so a "prompt" becomes a piece of schema, not a runtime side effect.

**Rendering vs. rewriting vs. evaluating (three separate steps).**
- *Rendering* is pure string substitution: take the template and fill in the bound tuple values (e.g., `{{body}}` → "My package never arrived."). This is analogous to variable substitution in a parameterized SQL query.
- *Rewriting* transforms the *template itself* before rendering, using a "rewriting context" Ω built from database metadata: schema info (column names/comments), constraints (valid value domains), the query context (which columns/predicates are actually relevant), and statistics (sample values, label distributions, representative examples). This is the paper's central analogy: just as a relational query optimizer rewrites a SQL plan using statistics and constraints to pick a cheaper/better plan, PromptDB rewrites a *prompt* using the same kind of metadata to make LLM output more valid and reliable.
- *Evaluation* (the `EVAL` operator) is the actual LLM call: it deserializes the `PROMPT` struct and the tuple, decides on a rewrite strategy, applies it, renders the resulting template, calls the LLM, and returns a scalar value that can be used like any SQL column value.

**Four concrete rewrite rules** (each a database-metadata-driven prompt transformation):
1. *Constraint Injection (R_CI)* — since the DB knows the valid output domain (e.g., a CHECK constraint or enumerated category list), it appends "Return exactly one of: refund, delivery, other" to the prompt, closing the gap between free-text LLM output and a valid database value.
2. *Query-Aware Column Projection (R_QACP)* — analogous to projection pushdown in query optimization: only render the tuple attributes actually relevant to the task/query, dropping irrelevant columns to reduce prompt length (cost) and noise.
3. *Output Format Minimization (R_OFM)* — appends instructions like "Return label only" so the output is terse and easy to parse downstream, rather than a verbose natural-language answer.
4. *DB-Selected Few-Shot Examples (R_FSE)* — pulls representative labeled tuples from the database itself and inserts them into the prompt as in-context examples, rather than hand-crafting demonstrations in application code.

**Making this usable in SQL.** Since DuckDB won't auto-execute a UDF just because a struct column is selected, PromptDB auto-generates an `_eval` view for every table containing `PROMPT` columns. In this view, each prompt column is replaced by an expression that calls `EVAL(...)`, so a user can write ordinary SQL (`SELECT ... FROM tickets_eval WHERE semantic_filtering_prompt = 'yes'`) and the LLM call happens transparently underneath, the same way a computed/virtual column would.

**PromptOpt: treating rewrite selection as plan selection.** Rather than always applying every rule, PromptDB defines a small set of candidate rewrite plans (NoRewrite, Constraint+Format, Projection, FewShot, AllRules) and picks among them by maximizing an estimated quality-minus-cost objective, `Q̂(P,Ω) − λ·Ĉ(P,Ω)`, echoing classical cost-based query optimization (`arg max` over a plan space). In the prototype, cost is estimated from rendered prompt length and expected output length, and "quality" is a lightweight hand-coded heuristic about when a rule is likely to help (e.g., constraint injection is useful when the output domain is known) — not a learned or calibrated model.

## Key insights

- **Genuinely new framing (claimed and reasonably supported):** representing prompts as typed, self-describing, tuple-level database values (with template + bindings + model + task metadata) is a distinct positioning from prior work — LLM UDFs treat the prompt as an opaque argument; frameworks like DSPy/PromptSource treat prompts as external, unstructured assets; semantic-operator systems like LOTUS treat prompts as parameters to fixed operators (sem_filter, sem_join) rather than as queryable data itself. The comparison table (Table 1) crystallizes this distinctions along typed/optimizable/versioned/rewrite axes, though this table appears to be the authors' own characterization rather than an independently validated comparison.
- **Database-guided rewriting helps most for structured-output tasks.** The evidence (Figure 2/3) shows meaningful gains from rewriting for attribute extraction and semantic filtering, where output validity/format matters — this is a plausible and evidenced claim, since constraint injection and format minimization directly target parseability, which is easy for a small 3B model to get wrong.
- **No single rewrite rule dominates (rule ablation, Fig. 3).** This is a real, if modest, empirical finding: different rules address different failure modes depending on task, which motivates the cost-aware selection approach rather than a fixed "always apply everything" strategy.
- **PromptOpt's practical value is more limited than claimed.** The paper's own discussion admits PromptOpt sometimes picks insufficiently rich plans for attribute extraction, and that "AllRules" actually achieves the strongest raw quality (Fig. 2) — PromptOpt's contribution is really about occupying a cheaper point on the cost-quality curve, not about beating full rewriting on quality. The authors are appropriately honest that the heuristic optimizer is "incomplete" and needs to become more task-aware.
- **The system-building contribution (DuckDB integration, generated `_eval` views, EVAL UDF) is a working prototype**, demonstrated by SQL examples and an execution-metadata log, but this is engineering demonstration rather than a rigorously benchmarked systems contribution (e.g., no discussion of overhead vs. raw UDF calls, concurrency, or query-optimizer integration beyond the rewrite layer).

## Caveats — stated and inferred

- **Single, very small LLM used throughout** — all experiments use `llama-3.2-3b-instruct` via LM Studio locally. `stated` (explicitly named in section 4), but the implication that results may not transfer to larger/production-grade models (GPT-4, Claude, etc.) is `inferred` — the paper never tests whether rewriting benefits shrink as base model capability increases.
- **Heuristic, non-learned cost/quality model** — the authors explicitly state ˆQ is a "lightweight heuristic based on rule applicability" and that "learned or calibration-based quality estimation could be applied here" and is left to future work. `stated`.
- **PromptOpt admittedly underperforms on attribute extraction** — the paper states PromptOpt "does not always choose sufficiently rich rewrite plans" and that the heuristic estimator "should be made task-aware." `stated`.
- **Small, narrow evaluation datasets** — synthetic tickets (self-generated, so ground truth and difficulty are author-controlled), a small OpenML Car Evaluation table, and DuckDB's synthetic TPC-H generator. None are large-scale, real-world noisy text corpora typical of production semantic-operator workloads (e.g., no comparison to LOTUS's or EVAPORATE's benchmark datasets). `inferred` (not explicitly flagged as a limitation by the authors, but evident from the datasets section).
- **No statistical significance testing or variance reporting** — figures report single point estimates (e.g., "0.73," "1.00") with no error bars, confidence intervals, or repeated-run variance, and temperature=0.0 is used, which reduces stochasticity but also means only one sample per condition was likely evaluated. `inferred`.
- **Fixed, small candidate rewrite-plan set (5 plans)** — PromptOpt only searches over 5 predefined combinations rather than a genuine combinatorial or learned search space; the paper calls the optimizer "intentionally lightweight." `stated`.
- **No comparison against actual competing systems** (DSPy, LOTUS, SPEAR, EVAPORATE) empirically — these are discussed only qualitatively in Related Work; no experiment benchmarks PromptDB's rewriting against, e.g., LOTUS's semantic operators or DSPy's optimized prompts on the same tasks. `inferred`.
- **Cost model is simplistic** — estimated cost ˆC is based only on rendered prompt length and expected output length, not actual latency/dollar cost variance across models or providers, despite the paper reporting latency and token counts as metrics. `inferred` (there's a mismatch between what's measured in experiments and what the optimizer's cost function actually uses).
- **Single-machine, in-memory, small-scale execution** — "All experiments run on a single commodity workstation" using DuckDB in `:memory:` mode; no evaluation of behavior at real database scale (large tables, concurrent queries, persistent storage, query planning interaction with EVAL calls). `stated` (workstation detail) / `inferred` (scale limitation not discussed as a caveat).
- **This is presented as a prototype/position paper**, and the authors' own conclusion frames results as showing "potential" and identifying "concrete directions for improving the optimizer and rewrite rules" — i.e., the system is explicitly early-stage rather than production-validated. `stated`.
