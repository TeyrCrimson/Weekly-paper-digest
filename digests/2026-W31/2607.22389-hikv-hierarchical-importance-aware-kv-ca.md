# HiKV: Hierarchical Importance-Aware KV Cache with Hardware Acceleration for LLM Decoding

**Authors:** Chao Fang, Jun Yin, Man Shi, Marian Verhelst

**arXiv:** [2607.22389](https://arxiv.org/abs/2607.22389)

**Categories:** cs.AR, cs.AI, cs.LG

**Submitted:** 2026-07-24

**Relevance:** 8/10 — matched: Pre-inference input sanitization for generation stability

---

## TL;DR
HiKV is an algorithm-hardware co-design that shrinks the KV cache bottleneck in LLM decoding by pruning redundancy at two levels: evicting unimportant tokens (Stage I) and then loading only the important elements within each surviving token (Stage II). Paired with a custom accelerator built around a reconfigurable importance sorter (RIS) that switches between heap-based and chunk-based sorting, HiKV reports up to 7.95× speedup, 90% energy reduction, and 1.82–4.87× more memory-access reduction than prior importance-based methods, all within 1% accuracy loss and only 8% extra chip area.

## First-principles breakdown

**The problem.** LLMs generate text one token at a time (decoding). To avoid recomputing attention over the whole sequence at every step, they cache the Key (K) and Value (V) vectors of all previous tokens — the "KV cache." This cache grows linearly with sequence length and multiplies with batch size (each concurrent request needs its own cache), so at long contexts and large batches it dominates memory traffic — the paper shows KV cache can be >90% of memory accesses at batch size 64, versus ~20% at batch size 1. Since decoding is memory-bound (compute units sit idle waiting for data), shrinking KV cache traffic directly speeds up and reduces energy of inference.

**Why prior approaches fall short.** Two families exist:
- *Heuristic eviction* (e.g., StreamingLLM: keep only recent + a few initial "sink" tokens) is cheap but blind — it can throw away tokens that matter, hurting accuracy when relevant info sits outside the fixed window.
- *Importance-aware eviction* (e.g., H2O): dynamically scores each token by accumulating how much attention it receives, then evicts low-scoring tokens. This is more accurate but (a) requires expensive re-sorting of scores across potentially thousands of tokens at every decoding step, and (b) — the key gap this paper identifies — only operates at token granularity. Once a token is "kept," its entire K and V vector must be loaded, even though (as the paper shows empirically) many individual elements within a token's vector contribute negligibly to attention.

Hardware accelerators exist to cut the sorting overhead of token-level scoring, but none exploit the additional element-level redundancy, so they still hit a bandwidth ceiling from loading full vectors of "important" tokens.

**HiKV's mechanism.** The core idea is hierarchical compression: coarse-grained token pruning composed with fine-grained element pruning, which multiply together for a higher total compression ratio than either alone.

- *Stage I (token-level, coarse)*: Maintains a fixed budget of tokens split into a "recent bank" (a FIFO of the most recent tokens) and an "important bank" (tokens with historically high importance scores, tracked via a min-heap). Importance is computed only by accumulating attention weights within the recent bank window (not globally, unlike H2O), reducing eviction maintenance cost from O(B) to O(log B) using heap operations.
- *Stage II (element-level, fine)*: Within tokens that survive Stage I, only a subset of vector elements is loaded. For the Query vector (Q), since its dimension is small (64–128), a global top-k magnitude sort selects which elements of K to load. For the attention-probability vector (P), which can be much longer, a full sort is too expensive, so P is split into chunks (sized to match the head dimension) and each chunk is sorted independently in parallel — a cheaper approximation validated to retain >95% recall relative to a true global sort.

- *Hardware*: A reconfigurable importance sorter (RIS), built from a common 2-input "bitonic sorter" primitive, is time-multiplexed across three roles per decoding step: chunk/global sort for Stage II element selection on Q, heap maintenance for Stage I token eviction, and chunk sort for Stage II selection on V/P. Supporting circuits (Token Importance Score Generator, Scoreboard buffer) track scores, while the actual K/V tensors stay in external (off-chip) memory — only lightweight metadata (indices/scores) is kept on-chip. Off-chip K and V cache layouts are also redesigned (element-first for K, chunk-indexed for V) to make the selective loads efficient DRAM bursts.

The net effect: instead of loading entire K/V vectors for a fixed set of "important" tokens, HiKV loads only a fraction of elements from only a fraction of tokens, cutting DRAM traffic (the dominant energy/latency cost) far more aggressively than token-only methods, while a dedicated circuit keeps the extra sorting overhead small.

## Key insights

- **Genuinely new**: the observation/exploitation of redundancy at *two independent granularities* (token and within-token element) simultaneously, rather than just token-level — prior importance-aware and hardware-accelerated methods (H2O, StreamingLLM, Token-Picker, MATA, VEDA, etc.) all stop at token granularity. The paper's own attention-score visualization (removing 50% of tokens and separately 50% of elements, then both together) supports that this redundancy is real and roughly orthogonal/multiplicative.
- **Hardware novelty**: a single reconfigurable sorter circuit (RIS) serving two structurally different sorting problems (heap-based token eviction vs. chunk-based parallel element selection) with claimed minimal overhead (RIS itself ~1.5% of chip area, all HiKV-specific components combined ~8.6%). This unification is the paper's architectural contribution, avoiding two separate dedicated sorting units.
- **Evidence supports**: on the algorithmic side, the Pareto-frontier plots (Fig. 15) do show HiKV sustaining higher total compression ratios than H2O/StreamingLLM at matched accuracy loss across several LLMs and tasks, and the chunk-based P-sort recall (>95% vs. global sort) is directly measured, not just asserted. On system-level numbers, the paper decomposes the 7.17× memory-access reduction and 5.70× speedup into separate Stage I/Stage II multiplicative contributions, which is a reasonably rigorous ablation of the two-stage design.
- **Claimed vs. evidenced**: the headline "7.95× speedup / 90% energy reduction" figures are best-case single-model numbers (mistral-7b, longchat-7b respectively), not averages — the reported averages are lower (5.70× speedup, 80–90% energy reduction range). The "1.82–4.87×" additional memory-access reduction over SotA is asserted based on the paper's own re-implementation of baselines on a unified hardware platform, not independently reported baseline numbers.

## Caveats — stated and inferred

- **Accuracy threshold is per-task and self-defined** (stated): the "1% accuracy loss" ceiling is applied per task/model combination, and the authors note the attainable compression ratio varies widely (2× on sensitive multi-hop reasoning tasks to 16× on tolerant ones) — the single headline compression/speedup numbers are best cases, not representative averages.
- **Baselines re-implemented, not independently sourced** (inferred): S-LLM, H2O, and Token-Picker are reimplemented "on this identical platform" for fair comparison; this is reasonable methodology but means head-to-head numbers depend on the authors' own reimplementation fidelity rather than each baseline paper's original reported results.
- **Simulation-based system evaluation** (inferred): end-to-end speedup/energy numbers come from LLM-Viewer plus DRAMSim3 simulation with HBM2 parameters "following" other papers, not measurement on physical silicon — actual hardware is only synthesized/post-layout (area/power), not fabricated and run.
- **Hardware comparison table uses technology-node scaling estimates** (stated): area/power/energy-efficiency of competing accelerators (Token-Picker, Titanus, MATA, VEDA, etc.) are normalized to 16nm via DeepScaleTool rather than measured on a common process, and several competitor entries are pre-layout while HiKV's is post-layout — an apples-to-oranges comparison basis that the paper flags with bracketed "scaled" superscripts but doesn't fully resolve.
- **Fixed evaluation setup**: prefill length fixed at 4096 tokens, batch size of 1, single-request inference (stated) — the paper's own motivation section emphasizes that KV cache dominance is worst at large batch sizes (up to 64), yet the accuracy/compression evaluation itself doesn't test batched/multi-request scenarios, so benefits under the very regime motivating the work (large-batch serving) are not directly demonstrated for the algorithmic accuracy results (inferred).
- **Recall approximation error unquantified downstream** (inferred): the >95% recall of chunk-based P-sort versus global sort is validated only on 8 samples from one task/model (Qwen2.5-0.5B, 2wikimqa); generalization of this approximation quality across models/tasks is not separately verified beyond the downstream accuracy plots.
- **Multi-turn recomputation cost not quantified** (inferred): the paper states HiKV "recomputes the IS of all prior tokens at each turn boundary" for multi-turn conversations but does not report the overhead or latency impact of this recomputation.
- **Persistence-of-importance assumption** (stated): Stage I freezes importance scores in the important bank for efficiency, relying on the "persistence of importance" hypothesis from prior work; the authors acknowledge this has only "minor effect on adaptivity" within a single turn but don't quantify cases where it could fail.
- **No fabricated chip / no power measurement on real workloads beyond post-layout netlists** (stated implicitly by methodology): power figures come from "activity-annotated post-layout netlists," which is a standard but still simulation-adjacent (not silicon-measured) methodology.
