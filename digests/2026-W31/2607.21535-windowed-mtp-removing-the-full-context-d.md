# Windowed-MTP: Removing the Full-Context Draft-KV Tax at Million-Token Context

**Authors:** Alagappan Valliappan

**arXiv:** [2607.21535](https://arxiv.org/abs/2607.21535)

**Categories:** cs.LG, cs.CL, cs.PF

**Submitted:** 2026-07-23

**Relevance:** 6/10 — matched: Pre-inference input sanitization for generation stability

---

## TL;DR
Built-in speculative-decoding draft heads (MTP/NEXTN) attend over the *entire* KV cache at every draft step, so at million-token context this "free" draft becomes a major cost, sometimes making speculation slower than not speculating at all. The paper applies StreamingLLM-style sliding-window + attention-sink to the draft's attention only (leaving the target's verification untouched), which is provably lossless and cuts per-decode-step cost by 28–44% at 1M context across three model families, while also reclaiming ~99% of the draft's now-unread KV cache via a ring buffer.

## First-principles breakdown

**The problem: speculative decoding and why "free drafts" stop being free.**
Speculative decoding speeds up LLM generation by having a cheap "draft" model guess several future tokens, then having the expensive "target" model verify all of them in one parallel forward pass, accepting the longest correct prefix. Because the target still decides what's accepted, the output is mathematically identical to normal decoding (it's "exact") — you just get more tokens per expensive forward pass. The key efficiency assumption baked into this idea is that the draft is cheap relative to the target.

Modern frontier models (DeepSeek-V3, Qwen3) build this draft directly into the model as a lightweight extra layer called an MTP (Multi-Token-Prediction) or NEXTN head, rather than using a wholly separate small model. That head still uses standard full (softmax) attention, meaning every draft step must read the *entire* KV cache (all previously computed key/value tensors for the whole context) — an O(context length) operation. At short contexts this read is trivial and fits in fast cache memory, so the assumption "draft is free" holds. But at 1 million tokens of context, that KV cache read becomes gigabytes, and doing it once for the draft *and* once again for the target's own verification means the draft's cost scales the same way as the target's, rather than being negligible. Worse, newer targets increasingly use hybrid or linear-attention architectures (GDN, Mamba2) specifically to make their own verification cheaper at long context — but the bolted-on MTP draft head still uses full attention, so as the target gets cheaper, the draft's now-unshrunk cost becomes a *larger* share of each step, not a smaller one. On hard tasks with low acceptance rates, this tax can make a deep draft net-negative: literally slower than just not speculating.

**The fix: window the draft's attention, not the target's.**
The paper borrows a trick from StreamingLLM: instead of letting attention look at every token in the context, restrict it to a fixed recent window (e.g., the last ~4000 tokens) plus a small set of "sink" tokens from the very beginning (which empirically stabilize attention). StreamingLLM used this to keep a full model's attention bounded during streaming generation. Here, the innovation is applying it *only* to the draft head's attention, while the target's verification step still attends to the full, true context.

Why this is safe: speculative decoding's correctness guarantee lives entirely in the verification step — the target always decides which proposed tokens are accepted or rejected, and rejected tokens are resampled from the target's true distribution. The draft is just a "proposer": a worse proposer only lowers how many tokens get accepted per step (hurting speed), it never changes *which* tokens end up in the output. So restricting what the draft can see cannot break correctness — it can only, at worst, make the draft guess worse and reduce acceptance length. The paper calls this "lossless by construction" and backs it up empirically by diffing windowed vs. native draft outputs and showing any divergence matches pre-existing floating-point non-determinism in batched verification, not a windowing effect.

Mechanically: in a paged-KV serving system (SGLang), each draft step's key set is restricted to a per-request block table containing just the sink blocks plus the most recent window's blocks, instead of the full growing table. Since positions are baked into cached keys via RoPE, this requires no retraining, no new kernels, no extra parameters — just a change to which cache pages the draft is told to read at each step. Because the intervening (dropped) KV entries are then provably never read by the draft, they can be physically discarded and replaced with a small fixed-size ("ring buffer") allocation instead of a full-length cache, freeing GPU memory (they measure the draft's cache to be 7.7–11% of total KV at 1M tokens, of which >99% becomes reclaimable).

**Why acceptance doesn't collapse.**
Intuitively, giving the draft less context should hurt its guesses. The paper argues (and measures) that it mostly doesn't: a "conditional acceptance" analysis by draft position shows the windowed draft's per-position acceptance rate tracks the native (full-context) draft closely, with the shallow, most-consequential position (position 1) essentially unaffected. Attention-mass analysis shows that on RoPE-based models the "escaping" mass beyond the window is diffuse (spread thin over many distant, low-value tokens) rather than concentrated on any one informative distant token — i.e., the far context wasn't carrying much useful signal for local next-token prediction anyway, likely because the recurrent/hybrid backbones (Gated-DeltaNet, Mamba2) already carry long-range dependencies through their recurrent state, making the full-attention re-read partly redundant. On some inputs, windowing even *improves* acceptance, apparently by removing "dilutive" distant context that was hurting rather than helping the guess. The one clear counterexample is multi-needle retrieval tasks with a strong drafter (the 122B model), where far context is genuinely informative and windowing trades away some acceptance — but even then the per-step cost savings outweigh the loss, so end-to-end latency still improves.

## Key insights

- **Genuinely new framing**: identifying and quantifying a "long-context draft-attention tax" specific to *built-in* MTP/NEXTN heads — a cost that was invisible in prior short-context speculative decoding literature because the draft's KV footprint (a few MB) used to be small enough to sit in GPU cache and be effectively free to re-read; at 1M tokens it's gigabytes and every read hits HBM.
- **The fix itself is not conceptually new** (StreamingLLM windowing existed; MagicDec and others already diagnosed KV-loading as an SD bottleneck at long context/large batch) — the contribution is applying it surgically to an *already-shipping* production draft head, keeping it training-free/drop-in, and proving losslessness carries through, rather than training a new constant-KV draft (cf. LongSpec) or using a separate retrieval-based draft (cf. SpecExtend).
- **Well-supported claims**: consistent 28–44% per-decode-step cost reduction across three distinct architecture families (two GDN-MoE Qwen variants, one Mamba2-hybrid Nemotron) at 1M context, replicated on both B200 and H100 hardware, and shown to widen with context length — this is measured directly via kernel-level (nsys) attribution, not just end-to-end timing, which strengthens the causal story.
- **The acceptance-preservation result is more nuanced than "free lunch"**: the paper is honest that the acceptance-length effect is second-order and can go either way depending on task/model, but claims (and shows across a fairly broad sweep) that the cost-side win always dominates so end-to-end speed never regresses in their tested cells.
- **Secondary reclaimed-memory benefit** (ring buffer freeing 7.7–11% of KV) is a real, implemented systems win (demonstrated via increased feasible batch size before OOM), not merely theoretical.

## Caveats — stated and inferred

- **Single-author paper, one company (NVIDIA), own benchmarks/reproduction package** — no independent replication. (inferred)
- **Measured magnitudes are framework-specific**: authors explicitly state the exact percentages are tied to SGLang's implementation of the draft path, and a more/less optimized framework would show different (possibly much smaller) gains — only the direction of the mechanism is claimed to be general. (stated)
- **Backend asymmetry**: native MTP runs on FlashInfer while windowed/ring-buffer requires the Triton backend; authors do a control ablation showing Triton is actually a *handicap*, but this cross-backend comparison is inherently harder to interpret cleanly, and they admit their windowed numbers are likely a "conservative lower bound" pending a native FlashInfer ring-buffer kernel that doesn't yet exist. (stated)
- **Configuration/depth choices could favor the method**: window size (W=4032, sink=64) is fixed globally without per-workload tuning; while they show a dose-response sweep suggesting robustness, only one input (niah_multiquery_enum) gets this fine-grained treatment. (stated, partially — sweep exists but is thin)
- **Losslessness guarantee weakens under real conditions**: exact only under greedy decoding + exact arithmetic; bf16 batched verification introduces non-determinism, and under sampling the guarantee becomes "distributional," not bit-identical. (stated)
- **Evaluation is single-seed per cell** ("a single seeded run" per benchmark cell) — no multi-seed statistical campaign; authors acknowledge this and call full multi-seed sampling "future work," leaning on cross-workload consistency instead of repeated trials to justify robustness. (stated)
- **Acceptance-preservation claim has a known failure mode**: the strongest drafter (Qwen-122B) shows real acceptance degradation on multi-needle retrieval where distant context is genuinely informative — the paper frames this as a bounded, outweighed cost, but it is a case where the core "windowing doesn't hurt" story breaks down and only the aggregate cost-latency tradeoff saves the result. (stated)
- **All evaluation is on synthetic/constructed long-context benchmarks (RULER, LongBench-v2, BABILong)** at a fixed engineered 1.04M-token input — not on live production traffic or real user query distributions. (inferred)
- **No comparison against trained long-context drafters (EAGLE-3, LongSpec) head-to-head** — authors explicitly justify this choice as "scientifically controlled" (isolating the windowing variable), but it also means the paper doesn't establish how Windowed-MTP's absolute speedups compare to the alternative research directions it discusses, only that it beats the unwindowed version of the same head. (stated as a deliberate choice, but also a limitation on comparative claims — inferred)
- **Hardware scope is narrow**: primary results are single-GPU (B200), with one H100 replication for generalization and a small TP2 batch scaling study — broader multi-node/multi-GPU serving conditions are not explored. (inferred)
- **FP8 KV analysis is caveated by the authors themselves**: their stack's fp8-KV path "lacks a fused attention kernel," inflating absolute fp8 latency, so they report deltas rather than absolute fp8 numbers and call bf16 their primary result — meaning the fp8 story is less rigorously validated. (stated)
